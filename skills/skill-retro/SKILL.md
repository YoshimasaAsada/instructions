# Skill Retro

スキルで進めた作業のうち、完走後にユーザーとのラリー（手戻り）が発生した部分を振り返り、同じラリーが次回起きないようにスキル・規約を直す。

- **目的:** スキル完走後のラリーを減らす。「何がダメだったか」を言語化し、直せるものはスキルに組み込む
- **入力:** 対象（既定: いまのセッション。ブランチ・PR 番号・セッション ID で広げられる）。起点スキル（既定: `nonstop`）
- **出力:** 振り返りレポート `{機能名}.retro.md`、承認された修正の反映、累積台帳 `ledger.md`（このスキルのディレクトリ）の更新

---

## 起動方法

| 指示 | 動作 |
|---|---|
| `/skill-retro`（開発したセッションで呼ぶ） | いまのセッションを、`nonstop` の起動以降について振り返る。「この開発の振り返りをしたい」と頼んでも同じ |
| `/skill-retro ブランチ全体` | いまのブランチに乗った全セッション（翌日のレビュー対応など、別セッションに分かれた作業も含める） |
| `/skill-retro <PR番号>` | PR の head ブランチ（スタックPRなら全ブランチ）に乗った全セッション。別のセッションから呼ぶときに使う |
| `/skill-retro <ブランチ名>` | 指定ブランチに乗った全セッション |
| `/skill-retro 起点 implement` | 起点スキルを変える（`nonstop` を使っていない作業の振り返り） |
| `/skill-retro 分析だけ` | Phase 4 の提示で終える（反映しない） |

## 原則

1. **ラリーは履歴から拾う。記憶から拾わない。** 長い作業は compaction で前半が要約されているため、いまの会話の記憶だけで振り返ると取りこぼす。必ず `scripts/extract_rallies.py` で会話履歴（jsonl）から抽出する。
2. **減らすべきラリーと健全なラリーを分ける。** 承認・後続工程の依頼・成果物を見て初めて決められる仕様変更は手戻りではない。混ぜるとスキルが不要な規則で肥大化する。
3. **最も早く防げた地点を直す。** 実装で直したことでも、原因が要件定義での一次情報の読み落としなら要件定義側を直す。下流に対症療法を足さない。
4. **既に書いてあるのに守られなかったなら、同じ文言を足さない。** もう一度書いても守られない。履歴で「なぜ守られなかったか」（その Phase を通っていない / compaction で消えた / 他の指示と矛盾している / 判定の問いが曖昧 / 本文に埋もれている）を特定し、強制力の高い場所（工程間ゲート・完了条件・レビューサイクルの監査観点・スクリプト）へ昇格させるか、矛盾・曖昧さを解消する。
5. **知識の置き場所を守る。** スキルには工程（手順・判定の問い・ゲート）を書く。対象リポジトリの規約・既存パターン・ドメイン知識は、そのリポジトリの `AGENTS.md` / `.claude/rules/` に置く。ユーザー個人の好み（報告の書き方・粒度・進め方）は `CLAUDE.local.md` かメモリに置く。プロジェクト固有の名前をスキル本体に書かない。
6. **1件の事例に過剰適合させない。** 修正は「判定の問い」か「原則」に一般化し、今回の事例は `過去事例` として1つだけ添える。初出か再発かを台帳で確かめ、初出で一般化に自信がないものは台帳への記録だけにする。
7. **反映はユーザーの承認後。** スキルの修正は以降のすべての作業の挙動を変える。提案（Phase 4）と反映（Phase 5）を分け、承認された番号だけ反映する。

## ラリーの分類

### 種別: 減らすべきラリーか

| 種別 | 見分け方 | 振り返り対象 |
|---|---|---|
| 修正指示 | 「〜にして」「これ要らない」「違う」 | ○ |
| 成果物・報告への質問 | 「なんで〜なの」「どこを見ればいいの」「確認事項をもう一度」 | ○（報告・文書の不足を疑う） |
| 不要な停止からの再開 | 「次に進んで」「最後まで進めて」。止まらなくてよい所でスキルが止まった | ○ |
| 中断・ツール拒否 | 抽出結果の `[中断]` `[ツール拒否]` | ○（直前の行動が誤り） |
| 仮確定の差し戻し | 「D-3 は別案で」 | ○ |
| 承認・相づち | 「OK」「提案どおりで」 | × |
| 後続工程の依頼 | 「PR 作って」「テストの準備して」 | ×（毎回同じ依頼が続くなら、既定化を修正案にしてよい） |
| 仕様変更・新しい質問 | 成果物を見て初めて決まった変更、作業と無関係な質問 | ×（一次情報に書いてあったなら「一次情報の欠落」として ○） |
| 環境・障害 | `[APIエラー後の再開]`、ユーザー自身のシェル操作 | ×（同じ環境操作が繰り返されるならメモリの候補） |

### 原因: なぜ防げなかったか

複数当てはまるときは、表の上にあるもの（より上流のもの）を採る。

| 原因 | 判定の問い | 主な修正先 |
|---|---|---|
| 一次情報の欠落 | 答えが issue・Figma・Slack 等の一次情報にあったのに、読んでいない・読み違えたか | `requirements-definition` の一次情報取得 / `nonstop` Phase 0 |
| 仮確定の倒し方 | 既定案・保守側の判定が、ユーザーの判断と逆だったか | `nonstop` の仮確定ポリシー / 各スキルの既定案の作り方 |
| 手順の欠落 | このラリーを防ぐ手順・判定の問いが、どのスキルにも無いか | 該当スキルの Phase・原則 |
| 手順の不履行 | 手順はあるのに実行されなかったか | 昇格（ゲート・完了条件・監査観点・スクリプト）/ 矛盾の解消 |
| 規約の欠落 | 対象リポジトリの規約・既存パターンを知らなかったか（どこにも書かれていない） | 対象リポジトリの `AGENTS.md` / `.claude/rules/`（チーム共有） |
| 好みの不一致 | ユーザー個人の好み（報告の書き方・粒度・進め方・PR の分け方）に合っていなかったか | `CLAUDE.local.md` / メモリ |
| 報告の不足 | 成果物は正しいが、理由・根拠・リンク・並び順が足りず質問が来たか | 該当スキルの出力サマリ / テンプレート |
| 検証の不足 | チェックは通ったが、実際の画面・データでは違ったか | `implement` のブラウザ確認・完了条件 / `test-prep` |
| 防げない | 必要な情報がどこにも無く、成果物を見るまで決められなかったか | 対象外（記録だけ） |

## 実行フロー

### Phase 0: 対象の特定

- 対象の単位を決める。引数が無ければ**いまのセッション**（「この開発」「このセッション」もこれ）。「ブランチ全体」ならいまのブランチ、ブランチ名ならそのブランチ。
- PR 番号が渡されたら `gh pr view <番号> --json headRefName,baseRefName,url` で head ブランチを引く。スタックPRは上下の PR もたどり、全ブランチを集める。
- 機能名と出力先を決める。作業ディレクトリのルートで `*.decisions.md` / `*.requirement.md` を探し、同じプレフィックスを機能名にする。無ければブランチ名のスラッグを使う。
- **宣言してから Phase 1 へ進む:** 対象（セッション / ブランチ）/ 起点スキル / 機能名 / 出力先

### Phase 1: 材料の収集

1. **ラリーの抽出（必須）**

   ```bash
   # いまのセッション（既定）
   python3 ~/.claude/skills/skill-retro/scripts/extract_rallies.py [--since-skill nonstop] > <scratchpad>/rallies.md
   # ブランチ全体・PR
   python3 ~/.claude/skills/skill-retro/scripts/extract_rallies.py --branch <ブランチ> [--branch <ブランチ2>] [--since-skill nonstop] > <scratchpad>/rallies.md
   ```

   - 条件を省略すると、環境変数 `CLAUDE_CODE_SESSION_ID` のセッションを対象にする
   - `--branch` は、全プロジェクトの会話履歴から指定ブランチに一度でも乗ったセッションを集める。worktree 名と履歴のディレクトリ名は一致しないことがあるため、ブランチで引く
   - セッション単位で抽出したとき、同じブランチに乗った別のセッションがあれば一覧が出る。nonstop を起動したセッションと手戻りのセッションが分かれている場合は、ユーザーに伝えてブランチ全体へ広げるか確認する
   - 起点スキルの起動より後、`skill-retro` の起動より前のユーザーイベントを `R-n` として出す。各 `R-n` には直前のClaudeの応答（末尾）、ユーザーの発話、その後に起動したスキル・変更したファイル・ツール回数が付く
   - 起点スキルが見つからないときは全件を出す。宣言した対象と食い違っていないか確認する
2. **決定ログ** `*.decisions.md`: 「覆った仮確定」と、ユーザーが `D-n` で差し戻したもの
3. **followup** `*.followup.md`: 見送った改善のうち、ユーザーが後から「やって」と言ったものはラリーとして扱う
4. **git 履歴**: 起点以降のコミットと変更量。ラリーの時刻と突き合わせ、どのラリーでどれだけ直したかを見る

   ```bash
   git log --reverse --date=iso --format='%h %ad %s' --stat <base>..HEAD
   ```

5. **PR レビュー**（PR がある場合）: 他のレビュアーの指摘も手戻りとして扱う。`gh pr view <番号> --comments` と `gh api repos/{owner}/{repo}/pulls/<番号>/comments`

### Phase 2: ラリーの分類と手戻りの束ね

1. `R-n` を1件ずつ種別に分類する。
2. 振り返り対象を、同じ問題についての一連のやりとりごとに **手戻り `T-n`** に束ねる。1つの手戻りに何往復かかったか（ラリー数）がそのコスト。
3. `T-n` ごとに次を1行ずつ書く:
   - ユーザーが求めたこと
   - Claude がしていたこと・言っていたこと（直前の応答から）
   - 最終的に何を直したか（ファイル・コミット）

### Phase 3: 原因分析

`T-n` ごとに次を埋める。

1. **原因**: 表から1つ選ぶ。
2. **最も早く防げた工程**: `nonstop` なら Phase（入力の解決 / 要件定義 / 技術設計 / タスク分解 / テストケース / 実装 / 実装のレビューサイクル / 決定ログの提示）。単独スキルならその Phase。
3. **既存の記述**: 該当スキル（`~/.claude/skills/*/`）、対象リポジトリの規約（`AGENTS.md` / `CLAUDE.md` / `.claude/rules/`）、メモリを grep し、同じ趣旨の記述があるか確認する。
   - ある → 原因は「手順の不履行」。該当工程の実際のツール呼び出しを `--dump` で確認し、なぜ守られなかったかを特定する

     ```bash
     python3 ~/.claude/skills/skill-retro/scripts/extract_rallies.py --dump <R-n の参照パス>:<開始行>-<終了行>
     ```

   - ない → 「手順の欠落」「規約の欠落」「好みの不一致」のどれか
4. **再発か**: `ledger.md` のパターン台帳に同じ趣旨の行があるか確認する。

**推測で原因を書かない。** 「〜を読んでいなかった」「〜の Phase を飛ばした」は、`--dump` のツール呼び出しで裏付けてから書く。

### Phase 4: 修正案の作成と提示（唯一のゲート）

対象外を除く `T-n` に対して、修正案 `P-n` を作る。1つの `P-n` で複数の `T-n` を消せるならまとめる。

| 項目 | 内容 |
|---|---|
| 修正先 | ファイルパスと見出し |
| 種類 | 追記 / 書き換え / 昇格（既存の記述をゲート・完了条件・監査観点へ移す）/ 削除（矛盾・曖昧な記述）/ 台帳のみ |
| 文案 | 変更前 → 変更後。追記は周囲の書式（要点 → なぜ → 対処、表、チェックリスト）に合わせる |
| 消えるラリー | `T-n`（`R-n`） |
| 副作用 | 他のスキル・原則との矛盾、別のケースでの過剰発火、本文の肥大化 |

提示する前に、各 `P-n` を次で確認する。

- 修正先のファイルを**全文**読んだか（grep で一致した箇所だけ見て書き足さない）
- 同じ趣旨の記述がすでに無いか。あるなら「昇格」か「書き換え」にする
- 上位の原則と矛盾しないか（例: `nonstop` の「止まらないことを最優先」に対して「〜なら確認する」を足していないか）
- 規則の本体に、プロジェクト固有の名前や今回のファイル名が入っていないか
- SKILL.md の本体に長い判定リストを足していないか。長くなるなら参照資料に切り出す（`implement/defensive-code-rules.md` の形）
- 修正先が対象リポジトリの規約（チーム共有）なら、作業中のブランチには混ぜない。別ブランチ・別PRで出す前提で文案だけ作る

出力サマリの形式で提示し、**承認を待つ。** 「P-1, P-3 で」「P-2 は台帳だけ」のように番号で返せるようにする。

### Phase 5: 反映

1. 承認された `P-n` だけ反映する。反映後、修正したセクションを前後ごと読み直し、番号・相互参照・表の列が崩れていないか確認する。
2. 修正したスキルに eval（`evals/evals.json`）があれば、今回のラリーを再現する eval ケースの追加を提案する（実行は `skill-creator`）。
3. `ledger.md` を更新する。振り返り履歴に1行足し、パターン台帳は同じ趣旨の行の回数を増やすか、新しい行を足す。
4. `retro-template.md` に従って `{機能名}.retro.md` を出力先へ書く。
5. スキルの原本を別のリポジトリでも管理している場合（ミラー・プラグイン化）は、同期が必要なことを伝える。

## 完了条件

- [ ] ラリーをスクリプトで抽出し、全 `R-n` を種別に分類した
- [ ] 振り返り対象の `R-n` がすべて、いずれかの `T-n` に属している
- [ ] `T-n` ごとに、原因・最も早く防げた工程・既存の記述の有無・再発かどうかが埋まっている
- [ ] 「手順の不履行」はツール呼び出しで裏付けている
- [ ] 反映したのは承認された `P-n` だけ
- [ ] `{機能名}.retro.md` と `ledger.md` を更新した

## 出力サマリ（Phase 4 の提示）

1. 対象: ブランチ / PR / セッション数 / 期間 / 起点スキル
2. ラリー数: 全 N 件 → 振り返り対象 M 件 → 手戻り K 件。対象外の内訳（承認 a / 後続工程 b / 仕様変更 c …）
3. 手戻り一覧: `T-n / 内容 / ラリー数 / 原因 / 防げた工程 / 再発` の表
4. 修正案一覧: `P-n / 修正先 / 種類 / 要旨 / 消える T-n` の表（消えるラリー数の多い順）
5. 直さないもの: 防げない・台帳のみにしたものを、理由つきで1行ずつ
6. 次のアクション: 「P-1, P-3 を反映」のように番号で指示してもらう
