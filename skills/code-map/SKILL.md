# Code Map

既存コードを「実データで裏付けられた説明」と「読める図」に変換する。

- **入力:** 対象のファイルパス、またはクラス名・メソッド名
- **出力:** メソッド単位の説明（表・呼び出しツリー）、実データの中間値、自己完結HTMLの図
- **責務:** コードの読解、実データによる裏付け、図解
- **責務外:** コードの変更（`implement` を使う）、リファクタ提案の実施、設計変更

## 原則

1. **推測で説明しない。** 「〜だと思われます」「おそらく〜」は書かない。分からなければ実行して確かめる。
2. **数字を出す。** 「絞り込まれます」ではなく「106件が10件になります」。段階ごとの件数、変数の実際の値、クエリ回数を示す。
3. **主語を書く。** 「採点して落とす」ではなく「**商品を**採点して、**商品を**落とす」。誰が何をするかが消えると読めなくなる。
4. **図は情報を削って作る。** 1枚に詰め込まず分割する。1枚あたりノード5〜6個、線は交差させない。
5. **ユーザーが「分かりにくい」と言ったら作り直す。** 言い訳せず、何が欠けていたか（主語・具体例・粒度）を特定してから作り直す。

## 実行フロー

### Phase 1: コードを全部読む

対象ファイルを `cat -n` で**全文**読む。部分読みで説明を始めない。

そのうえで洗い出す。

- 公開メソッドと private メソッドの区分
- 定数・値オブジェクト（`Data.define` / `Struct`）
- **呼び出しツリー**（どのメソッドがどれを呼ぶか）
- DB クエリ・外部リクエストの発生箇所

呼び出しツリーはこの形で書く。

```
call
├─ target_plans
│   └─ gate_candidate_plan_ids ── DB①
└─ evaluate_plans ── DB②
    ├─ build_row
    └─ build_frames
```

### Phase 2: 実データで中間値を出す

**このスキルの中心。** コードを読んだだけでは「10件が5件になる」は分からない。スクリプトを書いて実行する。

```bash
cd <Rails アプリのディレクトリ>
cat > tmp/walkthrough.rb <<'RUBY'
Rails.logger.level = :warn
# 対象を実データで動かし、段階ごとの件数・値を出す
RUBY
bin/rails runner tmp/walkthrough.rb 2>&1 \
  | grep -viE "opensearch|^INFO|^ Container|^time=|RAILS_HOST_PORT" | head -40
```

**注意点（踏んだもの）**

- **`Rails.logger.level = :warn` を先頭に置く。** OpenSearch のリクエストログが数十KB出て出力が埋まる
- **出力フィルタの grep が自分の出力も消す。** `grep -vi opensearch` は「OpenSearch 1回」という自分の行も消す。フィルタに引っかからない語（「検索」「外部問い合わせ」）を使う
- **private メソッドは `svc.send(:method_name)` で呼べる。** 中間値を段階ごとに取り出すのに使う
- **Docker 経由で動かすリポジトリは、プロジェクトの実行コマンド（例: `just dip rails runner`）に読み替える。** `just` のテンプレート構文と `#{}` が競合する。 スクリプトはファイルに書いて `rails runner <path>` で渡す
- **外部リクエストの回数を数えるなら prepend する**

  ```ruby
  $searches = 0
  module C; def search(...) = ($searches += 1; super); end
  SearchClient.singleton_class.prepend(C) # 外部へ問い合わせるクラス
  ```

- `tmp/` 配下は git 管理外。作ったスクリプトは残してよいが、報告時に「消すか」を確認する

**出すべき数字**

| 種類 | 例 |
|---|---|
| 段階ごとの件数 | 106件 → 10件 → 5件 |
| 変数の実際の値 | `["current", "IT・デザイン"] => タグ付け5件` |
| クエリ・外部リクエスト回数 | DB 4回 + OpenSearch 1回 |
| 分岐の内訳 | `satisfied=8, duration_unmet=1, tag_unmatched=6` |
| 検算 | `8 + 6 + 6 + 2 + 6 = 28` |

### Phase 3: メソッド単位で説明する

コードの抜粋と実データを**必ず対にする**。コードだけ、数字だけ、どちらも不十分。

````markdown
## ステップ6：重み行を1本ずつ判定する

```ruby
def build_row(weight)
  matched = taggings_by_pattern_and_tag_id[[weight.pattern, weight.tag_id]]
  return Row.new(..., status: :tag_unmatched, score: 0) if matched.empty?
  ...
end
```

**実データ（SaaS プランの15本）**

```
satisfied = 8, duration_unmet = 1, tag_unmatched = 6
```

ここで押さえる点は…
````

各メソッドについて次を書く。網羅する場合は表にする。

| 列 | 内容 |
|---|---|
| メソッド | 名前とシグネチャ |
| 何をするか | 1〜2行 |
| 呼ぶもの | 依存先メソッド |
| 注意点 | 暗黙の前提、他所との結合、コードから読めない制約 |

**「注意点」に書く価値があるもの**

- 呼び出し元との暗黙の結合（`counts.fetch` が呼び出し元の絞り込みに依存、など）
- nil チェックを省いている根拠（`FRAMES` が必ず5個返すから、など）
- 変更すると壊れる箇所（`Hash.new { [] }` を `Hash.new { |h,k| h[k] = [] }` にすると読み取りで副作用が出る、など）
- DB制約・バリデータに支えられている前提（部分ユニーク索引があるから `find_by` で安全、など）

### Phase 4: 図にする

図は**自己完結した HTML 1ファイル**として出す。インライン SVG で描き、外部 CDN・フォント・ビルドに依存させない。
Mermaid は使わない（レイアウトを制御できず、ラベルが重なったまま出力されるため）。

**分割が前提。** 15メソッドを1枚に描くと線が入り組んで読めない。処理の段階ごとに3枚程度へ分ける。
1枚あたりノード5〜6個。1つの HTML に複数の図を縦に並べてよい。

図の形は目的で選ぶ。

| 見せたいもの | 形 |
|---|---|
| メソッドの呼び出し順・段階 | 横方向のフロー（レーン × 列） |
| 誰が誰に頼むか（主語が要る） | シーケンス（縦のライフライン） |
| データの変換段階 | 左→右のパイプライン |
| 1つの入力がどう分岐するか | 分岐フロー |

**必ず各図に「ここで確定すること」のカードを付ける。** 実データの数字を入れる。

#### HTML で描くときの決めごと

- **1ファイル完結。** `<style>` と `<svg>` をインラインで書く。外部スクリプト・Webフォント・画像を読み込まない
- **SVG は `viewBox` + `width="100%"` + `preserveAspectRatio="xMidYMid meet"`** にする。固定 px 幅にしない
- **文字は実表示で 12px を下回らせない。** `viewBox` の座標系とレンダリング幅から逆算して決める。
  メソッド名が長いときはノードのラベルに日本語の役割を置き、メソッド名は小さい副ラベルへ回す
- **色は `:root` の CSS 変数で定義し、`@media (prefers-color-scheme: dark)` で上書きする。** `body` に背景色を明示する
- **線を交差させない。** 行き先が同じ線は1ノードへ集約し、区別はエッジのラベルで表す。
  本流は隣接する段に置き、段を飛ばさない（飛ばすと線が回り込む）
- **エッジラベルは線の中点に置き、下地の矩形（背景色と同じ `fill`）を敷いてから文字を乗せる。** 線や他のラベルに重なって読めなくなるのを防ぐ
- **ノードの横幅はラベルの文字数から決める。** 固定幅にすると長いラベルがはみ出す

**出したら必ずブラウザで開いて目視する。** ラベルの重なり・線の回り込み・文字のはみ出しは、書いている時点では気づけない。
確認用には `file:///` から始まる実際に開けるフルパスを提示する。

### Phase 5: 報告

- 図は `SendUserFile` で送る（複数枚なら1回にまとめる）
- 図とコードの対応表を添える（どのノードが何行目か）
- 実行したスクリプトのパスを伝え、残すか消すかを確認する
- 説明の中で気づいた**コードの問題**（未使用フィールド、命名の不整合、暗黙の結合）は報告に含める。ただし**直さない**。直すなら `implement` を使う

## やってはいけないこと

- **コードを読まずに一般論で説明する。** 「一般にこの手のサービスは〜」は不要
- **図を作れないからと諦めて文章だけにする。** 読めないのは詰め込みすぎが原因。分割すれば収まる
- **1枚に詰め込む。** 「全部入りの図」は誰も読めない
- **書いた SVG が意図どおり描けているはずだと判断する。** 必ずブラウザで開いて見る
- **コードを変更する。** 説明の過程で直したくなっても、報告に留める

## 完了条件

- [ ] 対象コードを全文読んだ
- [ ] 実データで中間値を出し、段階ごとの件数・値を数字で示した
- [ ] メソッドごとにコード抜粋と実データを対にして説明した
- [ ] 図を分割して自己完結HTMLで作り、**ブラウザで開いて目視した**（ラベルの重なり・線の回り込み・文字のはみ出しがない）
- [ ] 図とコードの対応を示した
- [ ] 気づいたコードの問題を報告した（変更はしていない）
