# Implement

承認済みのタスクリストを、CI相当チェックとレビューサイクルを通過した実装コードへ変換する。

- **入力:** `*.task.md`。対応する `*.spec.md` / `*.requirement.md` があれば併読する
- **出力:** 実装コードとテスト、Status を更新した `*.task.md`
- **責務:** タスクの実装、テスト、CI相当チェックの全通過、レビューサイクルによる品質収束
- **責務外:** 要件追加、設計変更、タスクリストの再分解、指示のないコミット・PR作成・デプロイ

## 自律実行の原則

1. **入力を自動探索する。** 明示されたタスクリストを優先する。未指定なら `*.task.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。
2. **文書間の矛盾はコードと要件を根拠に解決する。** タスクリストと実コードが食い違う場合、コードの現状を正として実装方法を調整し、逸脱として記録する。要件・受け入れ条件を変えないと実装できない場合だけ、推奨案つきで確認する。
3. **プロジェクト規約を既定値にする。** 対象リポジトリの指示書（`CLAUDE.md`、`AGENTS.md`、`.claude/rules/` 等）と既存の類似実装に、命名・構成・テスト方法・エラー処理を合わせる。
4. **安全に推定できる事項は質問しない。** 可逆で局所的な実装判断は最も整合する案を採用して進める。質問は公開仕様・データモデル・権限境界・不可逆な移行に関わるブロッカーだけに限定する。
5. **上流文書の未決事項を勝手に確定させない。** タスクリスト・設計書・要件定義書に未決事項・確認事項が残っている場合、実装内容が変わるものは既定案で実装せず、着手前に推奨案つきで確認する。実装に影響しないものは記録して続行する。
6. **設計にない改善を混入させない。** リファクタや追加機能を思いついても実装せず、出力サマリで後続候補として報告する。
7. **中断からの再開に耐える。** タスク完了ごとに `*.task.md` の Status を更新し、どこまで終わったかを常にファイルへ反映する。

## コメント・トレーサビリティ規律

- **仕様書・タスクの識別子（REQ-001 / AC-002 / TASK-003 等）や「設計書 X 章参照」の類を、コードコメント・テスト名・docstring に書かない。** 文書との対応は `*.task.md` 側で管理する。コードは文書がなくても読めるように書く。
- コメントはコードから読み取れない制約・理由のみに使い、対象プロジェクトの言語・密度の規約に従う。

## 実行フロー

### Phase 1: 入力とチェック手段の把握

- タスクリストから、タスクの依存関係、対象ファイル、検証コマンド、完了条件を抽出する。設計書・要件定義書から設計判断と受け入れ条件を引き継ぐ。
- 上流文書に未決事項・確認事項が残っていないか確認する。実装内容が変わるものがあれば、着手前に推奨案つきで確認する（原則5）。
- **CI相当チェックをプロジェクトに合わせて特定する。** 次の優先順で調べ、ローカルで再現可能な「チェック一式」を確定してから実装に入る。
  1. 各タスクの `検証:` に書かれたコマンド
  2. リポジトリの指示書に定められた品質チェック（例: lint、型検査、テスト、フォーマット、コード生成、専用チェッカー agent）
  3. CI設定（`.github/workflows/` 等）で PR に対して走るジョブのローカル等価コマンド
- 変更が複数プロジェクト・言語にまたがる場合、それぞれのチェック一式を持つ。コード生成（GraphQLスキーマ等）を伴う変更は、生成コマンドもチェック一式に含める。

### Phase 2: タスク実装ループ

依存関係順に、1タスクずつ次を繰り返す。

1. タスクの対象ファイルと既存の類似実装を読み、書き始める前に差分の形を決める。
2. 実装とテストを書く。挙動変更に対応するテストはタスク内で完結させる。
3. そのタスクの検証コマンドを実行し、通るまで修正する。
4. `*.task.md` の Status を `[x]` に更新する。

- 実装中に発見した設計の抜けは、既存パターンで安全に補完できるなら補完して逸脱として記録する。補完がスコープや公開仕様を変えるなら手を止めて確認する。
- コミットは指示された場合のみ、プロジェクトのコミット規約・スキルに従って行う。

### Phase 3: CIループ（100%まで）

全タスク完了後、Phase 1 で確定したチェック一式を**変更範囲全体に対して**実行する。

- 失敗が1件でもあれば、修正してチェック一式を再実行する。**全チェックが通るまでこのループを抜けない。**
- 修正は失敗の原因に限定する。チェックを通すためにテストを弱める・skip する・lint を無効化することはせず、そうせざるを得ない場合は理由を記録して報告する。
- 同じ失敗が3回連続で解消しない場合は、アプローチを変える（実装方針の見直し、影響範囲の再調査）。それでも解消しなければブロッカーとして状況と試行内容を報告する。

### Phase 4: レビューサイクル

CIが全通過した状態から、次のサイクルを回す。

1. **一般的なコードレビューを行う。** 利用可能なコードレビュースキル・レビュー agent があればそれを使い、なければ変更差分に対して新鮮な目で「正しさ・エッジケース・N+1等の性能・セキュリティ・テスト網羅・可読性」を観点にレビューする。
2. **各指摘をプロジェクト方針と突き合わせる。** 指摘を鵜呑みにせず、リポジトリの指示書・`.claude/rules/`・レビュー規約文書・既存コードの慣例と照合し、「採用 / 不採用」を理由つきで判定する。一般論としては正しくてもプロジェクト方針と矛盾する指摘（例: 方針上書かないテスト、意図的に使わないパターン）は不採用とする。方針・既存コードに根拠が見つからず採否を判定できない指摘は、勝手に決めず「要確認」として出力サマリで推奨案つきで報告する（修正はブロックしない範囲で続行する）。
3. **採用した指摘を修正する。** 修正後は Phase 3 のCIループへ戻り、全チェックが通るまで修正する。
4. サイクルの結果（指摘数、採用数、不採用の理由）を記録する。

**収束条件:** 採用すべき指摘が出なくなるまで繰り返す。既定の上限は3サイクルとし、上限到達時点で未解決の採用指摘が残る場合はその内容を報告する。指摘ゼロのサイクルが1回あれば収束とみなす。

## 完了条件

- [ ] タスクリストの全タスクが完了し、Status がファイルへ反映されている
- [ ] プロジェクトのCI相当チェック一式が全て通っている
- [ ] レビューサイクルが収束している（最終サイクルで採用すべき指摘がない）
- [ ] コードコメント・テスト名に仕様書・タスクの識別子が含まれていない
- [ ] 設計からの逸脱・補完した前提が記録されている
- [ ] スコープ外の変更を混入させていない

## 出力サマリ

完了後は次だけを簡潔に報告する。

- 実装したタスクと変更ファイルの概要
- 実行したチェック一式と最終結果
- レビューサイクル数と、採用/不採用にした主な指摘
- 設計からの逸脱、残った未決事項、後続候補（スコープ外改善など）
