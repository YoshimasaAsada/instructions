# Implement

承認済みのタスクリスト、または修正・変更依頼を、CI相当チェックとレビューサイクルを通過した実装コードへ変換する。

- **入力:** `*.task.md`。該当するタスクリストがない修正・変更依頼は、依頼そのものを入力とする（**修正モード**）。対応する `*.spec.md` / `*.requirement.md` があれば併読する
- **出力:** 実装コードとテスト、Status を更新した `*.task.md`（タスクリストがある場合）、見送った改善・知見をまとめた `*.followup.md`（該当がある場合）
- **責務:** タスクの実装、テスト、CI相当チェックの全通過、レビューサイクルによる品質収束、実装中に得た知見の文書化
- **責務外:** 要件追加、設計変更、既存実装のリファクタリングやアーキテクチャ変更（それ自体が依頼された場合を除く）、タスクリストの再分解・新規作成、指示のないコミット・PR作成・デプロイ

## 自律実行の原則

1. **入力を自動探索する。** 明示されたタスクリストを優先する。未指定なら `*.task.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。選択した入力ファイルのパスとタイトルは、作業開始時に1行で宣言する（誤った文書を掴んだまま進まないため）。該当するタスクリストがない修正・変更依頼は**修正モード**で進める: 依頼を1件のタスクとみなし、対象範囲・検証方法・完了条件を依頼内容と既存コードから定義する（タスクリストは新規作成しない）。
2. **文書間の矛盾はコードと要件を根拠に解決する。** タスクリストと実コードが食い違う場合、コードの現状を正として実装方法を調整し、逸脱として記録する。要件・受け入れ条件を変えないと実装できない場合だけ、推奨案つきで確認する。
3. **プロジェクト規約を既定値にする。** 対象リポジトリの指示書（`CLAUDE.md`、`AGENTS.md`、`.claude/rules/` 等）と既存の類似実装に、命名・構成・テスト方法・エラー処理を合わせる。
4. **安全に推定できる事項は質問しない。** 可逆で局所的な実装判断は最も整合する案を採用して進める。質問は公開仕様・データモデル・権限境界・不可逆な移行に関わるブロッカーだけに限定する。
5. **上流文書の未決事項を勝手に確定させない。** タスクリスト・設計書・要件定義書に未決事項・確認事項が残っている場合、実装内容が変わるものは既定案で実装せず、着手前に推奨案つきで確認する。実装に影響しないものは記録して続行する。
6. **既存の実装・アーキテクチャを生かす。** リファクタ・共通化・追加機能を思いついても実装しない。変更してよい範囲は「変更範囲の原則」で判定し、気づいた改善やベストプラクティスは Phase 5 で文書化する。
7. **中断からの再開に耐える。** タスク完了ごとに `*.task.md` の Status を更新し、どこまで終わったかを常にファイルへ反映する（修正モードでは対象外）。

## 変更範囲の原則（既存の実装・アーキテクチャを生かす）

これは**実装**のスキルであり、設計でもリファクタでもない。既存コードの構造・命名・レイヤリング・パターンは、より良い書き方を思いついたとしても踏襲する。

**基本則: 既存コードへの変更は、タスク・依頼を満たすために必要なものだけに限る。「こうした方が良くなる」は変更してよい理由にならない。**

### 差分ごとの判定

書いた差分のハンクごとに次を問い、答えが「いいえ」なら元に戻す。

> このハンクを元に戻したら、受け入れ条件・タスクの完了条件・CI相当チェックのいずれかが破れるか？

この判定で迷ったら、このスキルの `scope-rules.md` にある「混入しやすい変更」リストと突き合わせる。

### 例外（既存コードを変更してよい場合）

次のいずれかに当たる場合だけ既存コードへ手を入れる。いずれも**必要な最小範囲**に留め、逸脱として記録する。

- その変更なしには要件・受け入れ条件・タスクの完了条件を満たせない
- その変更なしには CI相当チェックが通らない
- 今回の変更が原因で既存コードが壊れる（呼び出し側の追随、型の追随、テストの追随など）
- 依頼そのものがリファクタ・移行である（例: 「Base コンポーネントへ置き換えて」）。この場合は依頼された範囲がスコープであり、その外側には引き続きこの原則が適用される

### 新規に書くコード

新規コードにも「自分のベストプラクティス」を持ち込まない。**隣のコードに似せる。**

- 実装を書き始める前に、参考にする既存実装を1つ以上特定する。タスク・設計書の `参考実装` を優先し、記載がなければ同レイヤーの類似実装を自分で探して読む
- 命名・ディレクトリ・レイヤ分割・エラー処理・テストの書き方を参考実装に揃える
- 参考実装から意図的に外れる場合は、理由を逸脱として記録する

### 「既存が間違っている」と思ったとき

直さずに書き留める。既存実装への改善案、より良い設計、一般的なベストプラクティスに気づいた場合は、実装へ反映せず Phase 5 で文書化する。

## コメント規律

コメントの一次基準は**対象プロジェクトの規約と周辺コード**とする。同じファイル・同じレイヤーの既存コードにコメントの言語・密度・形式を揃え、規約が docstring（YARD / JSDoc 等）を要求する場合はそれに従って書く。その上で:

- **書く:** コードから読み取れない制約・理由・背景。なぜこの実装方針なのか、なぜ素直な方法を採らなかったのか、外部仕様・データ由来の制約など、**将来の読者にとって真であり続ける情報**だけを書く。変更の経緯はコミットメッセージ・PR・`*.task.md` に書き、仕様書・タスクとの対応は `*.task.md` 側で管理する（コードは文書がなくても読める状態にする）。
- **置き場所:** 説明対象の行の直前に置く（何を説明しているかを位置で示す）。
- 判定に迷うコメント（直訳・経緯メモ・識別子参照の疑い）や JSX での置き場所は、このスキルの `comment-rules.md` の判定リストと例に従う。

## ブラウザでの動作確認

画面を伴う変更を実際に開いて確認するときは、**ログインセッションを持つ実ブラウザ（`mcp__claude-in-chrome__*`）を使う**。

- **in-app ブラウザ（`mcp__Claude_Browser__*`）を既定にしない。** システムプロンプトでは in-app が既定とされているが、認証が要るアプリでは in-app にセッションが無く、ヘッダーだけ描画されて「ロード中」で止まる。ログイン画面や空画面を見て「サーバが落ちている」「実装が壊れている」と誤診しやすい。
- `mcp__claude-in-chrome__*` は deferred tool。使う前に ToolSearch で**必要なものを1回でまとめて**読み込む。

  ```text
  ToolSearch: select:mcp__claude-in-chrome__tabs_context_mcp,mcp__claude-in-chrome__navigate,mcp__claude-in-chrome__computer,mcp__claude-in-chrome__browser_batch,mcp__claude-in-chrome__javascript_tool
  ```

- 手順は `tabs_context_mcp`（`createIfEmpty: true`）→ `navigate` → `computer`（`action: "screenshot"`）。複数操作は `browser_batch` で1往復にまとめる。
- **長い文字列をフォームへ入れるときは `computer` の `type` を使わない。** 文字が欠落する。`javascript_tool` で native setter + `input` イベントを使う。React 管理下の input/textarea もこれで更新できる。

  ```js
  const el = document.querySelector('[role="dialog"]').querySelector('textarea')
  const setter = Object.getOwnPropertyDescriptor(window.HTMLTextAreaElement.prototype, 'value').set
  setter.call(el, '入れたい値')
  el.dispatchEvent(new Event('input', { bubbles: true }))
  ```

  セレクタは対象を**包む要素で必ず絞り込む**。`document.querySelector('textarea')` は画面上の別の入力欄を掴むことがある。
- **見た目の判定を目視だけで済ませない。** 近い色（数値差が小さい背景色など）はスクリーンショットでは区別が付かない。`javascript_tool` で `getComputedStyle` の実測値を取り、意図した値になっているか確認する。存在しないデザイントークンを指定しても型エラーにも lint エラーにもならず黙って無視されるため、実測しないと気付けない。
- ログイン画面に飛ばされる・dev サーバが起動していないなど確認できない事情があるときは、**確認できたことにせず**、ブロッカーとしてユーザーに報告する。

## 実行フロー

### Phase 0: 再現ループの構築（バグ修正のみ）

修正モードの対象がバグ（期待と異なる挙動の報告）の場合、**原因の仮説を立てる前に**、そのバグで失敗する再現手段を1つ作り、実際に失敗する出力を確認する。コードを読んで仮説を組み立て始めている自分に気づいたら、手を止めて再現に戻る。

- 再現手段は次を満たす最小のものでよい: このバグで確実に失敗する / 決定的 / 数秒〜数十秒で完了する / エージェントが無人で実行できる。失敗するテスト、curl、CLI 実行と出力確認など。
- 再現できたら「修正後に同じ手段が通ること」を完了条件へ加え、恒久化する価値があれば回帰テストとしてタスクのテストに含める。
- 再現手段を作れない場合は、そのことを明言して手を止め、再現条件をユーザーに確認する（仮説だけで修正へ進まない）。

バグ以外の修正依頼・タスクリスト実装ではこの Phase は不要。

### Phase 1: 入力とチェック手段の把握

- タスクリストから、タスクの依存関係、対象ファイル、検証コマンド、完了条件を抽出する。設計書・要件定義書から設計判断と受け入れ条件を引き継ぐ。修正モードでは、依頼内容と対象コードの現状から対象範囲・完了条件を定義する。
- 上流文書に未決事項・確認事項が残っていないか確認する。実装内容が変わるものがあれば、着手前に推奨案つきで確認する（原則5）。
- **CI相当チェックをプロジェクトに合わせて特定する。** 次の優先順で調べ、ローカルで再現可能な「チェック一式」を確定してから実装に入る。
  1. 各タスクの `検証:` に書かれたコマンド
  2. リポジトリの指示書に定められた品質チェック（例: lint、型検査、テスト、フォーマット、コード生成、専用チェッカー agent）
  3. CI設定（`.github/workflows/` 等）で PR に対して走るジョブのローカル等価コマンド
- 変更が複数プロジェクト・言語にまたがる場合、それぞれのチェック一式を持つ。コード生成（GraphQLスキーマ等）を伴う変更は、生成コマンドもチェック一式に含める。

### Phase 2: タスク実装ループ

依存関係順に、1タスクずつ次を繰り返す。

1. タスクの対象ファイルと、タスク・設計書に記載された `参考実装` / `参考にした既存実装` を読み、書き始める前に差分の形を決める。参考実装の記載がない場合（修正モード含む）は既存の類似実装を自分で探して読み、どのファイルの何を参考にしたかを記録する。命名・構成・エラー処理・テストの書き方は参考実装とプロジェクト規約に揃える。
2. **触る範囲を先に線引きする。** 「変更範囲の原則」に照らして、どの既存ファイル・既存関数へ手を入れる必要があるかを実装前に決める。ここで挙がらなかった既存コードは触らない。
3. 実装とテストを書く。挙動変更に対応するテストはタスク内で完結させる。テストは設計書の `テスト戦略` に記載されたシーム（振る舞いを観測する公開境界）に置き、記載がなければ既存の類似テストが使うシームに揃える。内部実装の詳細（内部コラボレータ・private メソッド）にはテストを張らない。
4. そのタスクの検証コマンドを実行し、通るまで修正する。
5. **`git diff` で自分の差分を読み直し、「差分ごとの判定」に掛ける。** 要件・完了条件・CIのどれも破らないハンク（整形、リネーム、ついでの共通化など）は元に戻す。戻した内容のうち記録に値するものは Phase 5 の候補として控える。
6. `*.task.md` の Status を `[x]` に更新する（修正モードでは省略）。

- 実装中に発見した設計の抜けは、既存パターンで安全に補完できるなら補完して逸脱として記録する。補完がスコープや公開仕様を変えるなら手を止めて確認する。
- コミットは指示された場合のみ、プロジェクトのコミット規約・スキルに従って行う。指示がある場合は**1タスク = 1コミット**を既定とし、タスク完了（検証通過・Status 更新）ごとにコミットする。

### Phase 3: CIループ（100%まで）

全タスク完了後、Phase 1 で確定したチェック一式を**変更範囲全体に対して**実行する。

- 失敗が1件でもあれば、修正してチェック一式を再実行する。**全チェックが通るまでこのループを抜けない。**
- 修正は失敗の原因に限定する。チェックを通すためにテストを弱める・skip する・lint を無効化することはせず、そうせざるを得ない場合は理由を記録して報告する。
- 同じ失敗が3回連続で解消しない場合は、アプローチを変える（実装方針の見直し、影響範囲の再調査）。それでも解消しなければブロッカーとして状況と試行内容を報告する。

### Phase 4: レビューサイクル

CIが全通過した状態から、次のサイクルを回す。

1. **スコープ監査を行う。** ベースブランチとの差分（`git diff`）を通して読み、「変更範囲の原則」に照らして不要なハンクが残っていないか確認する。見つかったら元に戻す。戻した理由が「良くなる変更だが今回は不要」であれば、その内容を Phase 5 の候補として控える。
2. **コメント監査を行う。** 変更差分に含まれる全コメントを棚卸しし、「コメント規律」に照らして直訳コメント・経緯メモ・識別子を削除する。1件ずつ「コードだけを読む将来の読者に必要か」「周辺コードの密度・形式と揃っているか」で判定する。
3. **2軸レビューを並列サブエージェントで行う。** 自分の実装に引っ張られたレビューを避けるため、変更差分（`git diff` の範囲）と根拠資料のパスだけを渡した2つのサブエージェントを**並列**に走らせ、結果は統合・再ランクせず両軸をそのまま受け取る（一方の軸の合格がもう一方の不合格を隠さないようにするため）。利用可能なコードレビュースキル・レビュー agent があれば軸のレビュアーとして使う。サブエージェントが使えない場合は2軸を順に自分で消化する。
   - **規約軸（正しく書けているか）:** リポジトリの指示書・`.claude/rules/`・既存コードの慣例・コメント規律への適合。正しさ・エッジケース・N+1等の性能・セキュリティ・テスト網羅・今回追加したコードの可読性。加えて**今回追加したコードに限り**、次を判断事項（違反ではない）として当てる: コードスメル（不可解な命名 / 差分内の重複 / 同じ数個の値の引き回し / 投機的な一般化 / 1つの変更が多数ファイルへ散る）と、テストのアンチパターン（**実装結合** = 内部コラボレータのモック・private のテスト・リファクタで壊れるテスト / **トートロジー** = 期待値をコードと同じ手順で再計算していて構造上必ず通るテスト）。既存コードの設計の良し悪しは観点に含めない。
   - **仕様軸（正しいものを作ったか）:** タスクの完了条件・受け入れ条件・依頼内容に対する充足。(a) 未実装・部分実装の要件 (b) 依頼されていない挙動（スコープクリープ）(c) 実装済みだが挙動が誤っているもの、をそれぞれ根拠（仕様・タスクの該当箇所）つきで報告させる。
4. **各指摘を3つに仕分ける。** 指摘を鵜呑みにせず、リポジトリの指示書・`.claude/rules/`・レビュー規約文書・既存コードの慣例と照合した上で分類する。
   - **欠陥（修正する）:** 今回の変更に起因する不具合・エッジケース漏れ・性能退行・セキュリティ問題・テスト不足、プロジェクト規約への違反、コメント規律への違反。
   - **改善提案（修正しない）:** 今回の変更がなくても成立する既存コードの問題、設計をより良くする案、一般論としてのベストプラクティス、将来的な共通化・抽象化・リネーム。実装へ反映せず Phase 5 で文書化する。**「ついでに直せる」「差分が小さい」「レビューで指摘されたから」は修正してよい理由にならない。**
   - **不採用:** プロジェクト方針・既存パターンと矛盾する指摘（例: 方針上書かないテスト、意図的に使わないパターン）。理由を記録する。
   - 方針・既存コードに根拠が見つからず欠陥か改善提案か判定できない指摘は、**改善提案として扱う**。Phase 5 に「要確認」として記録し、出力サマリでも推奨案つきで報告する。
5. **欠陥に仕分けた指摘だけを修正する。** 修正後は Phase 3 のCIループへ戻り、全チェックが通るまで修正する。
6. サイクルの結果（指摘数、修正した欠陥数、改善提案として記録した数、不採用の理由）を記録する。

**収束条件:** 欠陥として修正すべき指摘が出なくなるまで繰り返す。既定の上限は3サイクルとし、上限到達時点で未修正の欠陥が残る場合はその内容を報告する。欠陥ゼロのサイクルが1回あれば収束とみなす（改善提案が残っていても収束判定には影響しない）。

### Phase 5: 見送った改善・知見の文書化

実装中および Phase 2・Phase 4 で「改善提案」に仕分けたものと、実装中に気づいたベストプラクティス・既存実装の問題を1つの文書へまとめる。**候補が1件もなければ文書は作らない**（空ファイルを量産しない）。

**出力先:**

- タスクリストがある場合: タスクリストと同じディレクトリに、ベース名の `.task.md` を `.followup.md` へ置換したファイル
- 修正モード: 作業ディレクトリのルートに `<ブランチ名またはトピックのスラッグ>.followup.md`
- 同名ファイルが既にあれば追記・更新する（既存の項目を消さない）

**構成:** このスキルの `followup-template.md` に従う（既存実装への改善提案 / 横展開したいプロジェクト規約の候補 / 用語集への追加候補 / 要確認）。該当がないセクションは省略する。

**規約ファイル・CLAUDE.md を直接編集しない。** `.claude/rules/` や `CLAUDE.md` はチーム共有の資産のため、この文書へ「候補」として書くまでに留め、実際の追記はユーザーの承認を得てから行う。対象領域に専用スキル（`codify-review-learnings` 等）がある場合はそちらの手順に従う。

**書かないもの:** 今回の実装で採用した内容の解説、コミットメッセージ・PR に書くべき変更の経緯、コードを読めば分かること、根拠を伴わない好みの主張。

## 完了条件

- [ ] タスクリストの全タスクが完了し、Status がファイルへ反映されている（修正モードでは、依頼された修正が完了条件を満たしている）
- [ ] プロジェクトのCI相当チェック一式が全て通っている
- [ ] 画面を伴う変更をブラウザで確認した場合、`mcp__claude-in-chrome__*` を使い、色などは `getComputedStyle` で実測した（確認できない事情があればブロッカーとして報告した）
- [ ] レビューサイクルが収束している（最終サイクルで修正すべき欠陥がない）
- [ ] 既存コードへの変更が「変更範囲の原則」の必要範囲に収まっている（依頼にないリファクタ・共通化・リネーム・整形が混入していない）
- [ ] 新規コードが参考実装とプロジェクト規約に揃っている（外れた箇所は理由を記録した）
- [ ] 変更差分のコメントが「コメント規律」を満たしている（識別子・経緯メモ・直訳コメントが残っておらず、周辺コードの規約に揃っている）
- [ ] 見送った改善提案・ベストプラクティスが `*.followup.md` に記録されている（候補がない場合を除く）
- [ ] 設計からの逸脱・補完した前提が記録されている
- [ ] スコープ外の変更を混入させていない

## 出力サマリ

完了後は次だけを簡潔に報告する。

- 実装したタスクと変更ファイルの概要
- 参考にした既存実装（タスク・設計書に記載がなく自分で選んだ場合は、そのファイルパスと参考にした点）
- 実行したチェック一式と最終結果
- レビューサイクル数と、修正した欠陥／改善提案として記録したもの／不採用にした指摘とその理由
- 生成・更新した `*.followup.md` のパスと、記録した提案の件数（該当がなければ「なし」）
- 設計からの逸脱、残った未決事項、要確認として残した指摘
