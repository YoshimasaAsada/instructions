# 防御コードの判定リスト

`SKILL.md` の「防御コードの原則」の参照資料。ガード・分岐・バリデーションを書くか迷ったとき、および Phase 4 の防御コード監査で1件ずつ判定するときに使う。

## 判定の問い

> このコードが防ぐ状態に、実際に到達する経路を示せるか？

示せなければ書かない。「念のため」「将来変わるかもしれない」「型の上では起こりうる」は経路ではない。

## 到達しない根拠（書く前にここを調べる）

- **DB 制約:** NOT NULL / FK / UNIQUE / CHECK / default（`db/schema.rb`・マイグレーション）
- **モデル:** optional でない `belongs_to`、presence 等のバリデーション、enum の値域
- **型:** GraphQL の non-null（`null: false` / 生成された TS 型）、引数の型
- **呼び出し元:** 全呼び出し元が何を渡しているか（grep で全件確認する）。内部からしか呼ばれないメソッドで、引数を再検証しない
- **上流の処理:** 認可（`ready?` 等）、親コンポーネントの条件付き描画、早期 return、フォームのバリデーションを通過済みの値
- **フレームワーク:** Rails / React / Apollo 等が既に吸収・保証している挙動

## 到達しうる状態（扱ってよい）

- ユーザー入力・URL パラメータ・外部 API や外部サービスの応答・Webhook
- 既存データ: NULL を書き込む経路がある nullable カラム、制約を後から足したカラムの古い行、jsonb の中身
- 同時操作・再試行・ジョブの重複実行
- フレームワーク由来の過渡状態（例: Next.js の初回レンダーで `router.query` が空、Apollo の `loading` 中で `data` が undefined）
- プロジェクトの規約が明示的に要求しているもの（例: 動的ルートパラメータの id ガード）

## 混入しやすい防御コード

- 必須の関連・NOT NULL カラムへの `&.` / `?.` / `try` / `presence` / `|| ''` / `?? ''`
- non-null 型のフィールドへの存在チェックや、空表示・代替文言の分岐
- enum や固定の選択肢に対する「想定外の値」の `else` 分岐・raise
- 呼び出し元が検証済みの値を、呼び出し先で再検証する
- 発生しない例外の `rescue`、例外を握りつぶして nil・空配列を返す `rescue`
- 親が条件付きでしか描画しないコンポーネントの中で、同じ条件を再チェックする
- 上記の状態を作るためだけのテスト（factory の上書きや `update_column` で制約を迂回して作ったデータを使うもの）

## 型の都合で扱いが必要なとき

型が nullable でも業務上 null にならない値は、空表示・代替文言・早期 return などの分岐を作り込まない。周辺コードと同じ最小の書き方で型を満たす。

## なぜ書かないか

到達しない状態へのガードは、データ不整合が起きたときに例外を出さず処理を続け、バグを隠す。落ちるべきところで落ちれば監視（Bugsnag 等）で検知できる。さらに、読む人に「この状態がありうる」という誤った前提を伝え、分岐とテストの保守コストだけが残る。
