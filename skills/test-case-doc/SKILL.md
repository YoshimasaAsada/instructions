# Test Case Doc

要件・設計・実装を、網羅性を検証できるテストケース一覧へ変換する。

- **入力:** `*.spec.md`。対応する `*.requirement.md` があれば併読する。実装済みなら対象コードと既存テストも調査する
- **出力:** 入力と同じベース名の `*.testcase.md`
- **責務:** テスト観点の導出、テストケースの網羅的な列挙、要件との対応付け、自動/手動の区分
- **責務外:** テストコードの実装、テストの実行、要件・設計の変更
- **関連:** 作成済み文書の独立監査（漏れチェック）には `test-case-review` を使う。監査で採用された指摘の反映は、このスキルの更新フロー（原則7）で行う。上流文書が無く、実装差分から「この変更で何が壊れうるか」を軸に手動確認シナリオを起こしたい場合は `test-scenario-from-diff` を使う

## 自律実行の原則

1. **入力を自動探索する。** 明示された文書を優先する。未指定なら `*.spec.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。spec が無ければ `*.requirement.md`、それも無ければ対象機能の実装コード（PR差分・ブランチ差分）を入力にする。
2. **関連文書を自動で読む。** 同じベース名の `*.requirement.md` から要件ID・受け入れ条件・スコープ外を、`*.task.md` から実装単位を引き継ぐ。文書同士が矛盾する場合（task.md が旧方式のまま等）は、最新版の requirement / spec と実コードを正とし、食い違いは `仕様上の確認事項` に記録する。
3. **コードベースで裏取りする。** 分岐条件、バリデーションの実値（上限・下限・正規表現・enum値）、権限判定、エラーメッセージは文書の記述ではなく実コードを根拠にする。文書と実装が食い違う場合はコードを事実とし、食い違いを `仕様上の確認事項` に記録する。
4. **既存の自動テストを調査する。** 対象機能の自動テスト（RSpec / Vitest 等、プロジェクトのテストフレームワークに従う）を読み、既にカバーされているケースを特定する。テストケース一覧はゼロから空想せず、「自動でカバー済み / 自動で追加すべき / 手動でしか確認できない」を区別して価値を出す。
5. **安全に推定できる事項は質問しない。** テストデータや操作手順は既存の factory・seed・画面構成から推定し、前提条件に明記する。質問はテストの合否基準（期待結果）を一意に決められない仕様の穴だけに限定し、推奨案を添える。
6. **要件・設計を勝手に変更しない。** テスト設計中に仕様の欠落（未定義のエラー挙動・境界値の扱い・競合時の優先順位など）を見つけたら、期待結果を勝手に決めず `仕様上の確認事項` に推奨案つきで残す。仕様の穴の発見はこのスキルの重要な成果物であり、失敗ではない。
7. **既存ファイルがあれば更新する。** 実施済みチェックや利用者の追記を保持しつつ、要件・設計・実装の差分に対応するケースを追加・修正する。

## テストケース網羅の基準

網羅性は「思いつき」ではなくテスト技法で機械的に担保する。

- **同値分割:** 入力を有効/無効の同値クラスへ分割し、各クラスから最低1ケース。
- **境界値分析:** 上限・下限・0・空・最大長・日付境界（当日/前日/月末/年跨ぎ）はクラスの内側ではなく境界の両側を狙う。境界の実値はコードから取る。
- **デシジョンテーブル:** 条件が複数絡む分岐（権限×状態×入力など）は条件の組合せ表を作り、実行不能な組合せを理由つきで除外した上で全組合せをケース化する。異種条件の組合せだけでなく、同種条件同士の複合（例: 複数の検索条件を同時指定）も象限として検討し、空いた象限は理由つきで対象外にする。
- **状態遷移:** ステータスを持つ対象は「許可された遷移すべて」と「禁止された遷移の代表」をケース化する。
- **エラー推測:** 権限不足、対象不存在（404）、重複操作、同時更新の競合、部分失敗、再試行、空状態、外部依存の失敗を既定の観点として必ず検討する。

観点カタログ（該当しない観点は理由つきで対象外にする）:

正常系 / 異常系（入力不正・権限不足・不存在・競合・部分失敗）/ 境界値 / 状態遷移 / 権限・ロール別 / 表示・UI（空状態・ローディング・エラー表示・レスポンシブ）/ データ移行・後方互換 / 回帰（既存機能への影響）/ 性能（大量データ・N+1）/ 非同期・ジョブ / 通知・外部連携

## 実行フロー

### Phase 1: 入力の把握

- 要件定義書から要件ID・受け入れ条件・スコープ外を抽出する。
- 設計書から分岐、バリデーション、エラーハンドリング、権限、状態遷移、移行手順を抽出する。
- 「テスト対象の機能一覧」と「観点カタログ」の掛け合わせで観点マトリクスの骨子を作る。

### Phase 2: コードベース調査

- 対象コードの分岐条件・バリデーション実値・enum値・権限判定を実ファイルで確認し、境界値の根拠とする。
- 対象機能の既存自動テストを読み、カバー済みケースを洗い出す。
- 手動確認の手順に必要な情報（画面URL、操作導線、必要なロール・テストデータの作り方）を既存実装から特定する。
- プロジェクトのテスト実行方法（`just rspec` / `pnpm test` 等）と、類似機能の既存テストケース文書があればその書式を確認する。

### Phase 3: テスト観点の導出とケース設計

- 観点マトリクス（機能×観点）を埋め、空欄は「ケース化する」か「理由つきで対象外」のどちらかに倒す。漏れの検出はこのマトリクスで行う。
- 各観点をテスト技法でケースへ展開する。ケースの重複は統合し、1ケース1検証目的にする。
- 各ケースに種別を付ける: **自動（済）** = 既存テストでカバー済み / **自動（要追加）** = 自動テストで書くべきもの / **手動** = ブラウザでの見た目・導線・外部サービス連携など自動化に向かないもの。
- 自動（済）の参照は「テストファイルパス＋describe/context 名」の粒度で記録する。行番号はファイル変更で腐るため書かない。
- 手動ケースの期待結果（ヒット件数・表示内容）は、前提条件に書いたテストデータ定義と1件ずつ突き合わせて数え上げる。ここが最も誤りやすい。
- 優先度を付ける: **High** = 受け入れ条件そのもの・データ破壊やセキュリティに関わる / **Mid** = 主要な異常系・境界値 / **Low** = 表示の細部・稀な組合せ。

### Phase 4: テストケース文書の作成

**ファイル名:** 設計書の `.spec.md` を `.testcase.md` に置換する（spec が無い場合は `{機能名}.testcase.md`）。
**作成場所:** 原則として入力文書と同じディレクトリ。同じディレクトリなら入力文書へのリンクは相対パス、別ディレクトリへ出力する場合は絶対パスまたはリポジトリルート相対で書く（壊れた相対リンクを作らない）。

**構成:** このスキルの `template.md` を読み、その構成に従う。該当しない項目は理由つきで `N/A` とする。

書き方のルール:

- 期待結果は「正しく動く」ではなく観測可能な形で書く（「保存される」→「一覧に表示され、DBの status が `active` になる」）。
- 手順は再現可能な粒度で書くが、自動（済）のケースはテストファイルパスの参照で足りるため簡潔でよい。
- **前提条件・テストデータ準備には実在する手段だけを書く。** ファイルパス・コマンド・スクリプトは実行前に実在を確認する。準備用スクリプトを新しく作る必要があるなら、既存物のように書かず「要作成」と明記して `対象外・後続対応` に引き継ぐ（このスキル自身はスクリプトやテストコードを作らない）。
- ケース数を稼ぐための重複や、フレームワーク標準機能（Rails の presence validation 等）だけを確認するケースは作らない。対象リポジトリのテスト方針（`CLAUDE.md` / テスト規約文書等）と整合させる。

### Phase 5: レビューサイクル

`doc-review-cycle` スキルを起動し、次を渡して収束するまで回す。

- **対象:** 作成・更新した `*.testcase.md`
- **根拠資料:** 要件定義書・設計書・実コード・プロジェクト規約（`CLAUDE.md` 等）
- **記録先セクション:** `仕様上の確認事項`
- **観点:**
  - 全要件・受け入れ条件のカバレッジ
  - 観点マトリクスの空欄（対象外理由の妥当性）
  - 境界値・条件組合せの漏れ
  - 期待結果の観測可能性
  - **手動ケースの期待結果とテストデータ定義の整合（ヒット件数の数え上げ）**
  - 種別・優先度の妥当性
  - 準備手順・実値の実在性（存在しないスクリプトを前提にしていないか）
  - 手動チェックリストだけでリリース前確認が完結するか

仕様の変更を要する指摘は不採用とし、`仕様上の確認事項` へ残す。`doc-review-cycle` が使えない場合は、同スキルのサイクル（レビュー → 突き合わせ → 修正 → 上限3サイクル）を自分で実行する。

## 完了条件

- [ ] 全要件ID・受け入れ条件が最低1つの TC に対応している
- [ ] 観点マトリクスに空欄がない（ケース化 or 理由つき対象外）
- [ ] 境界値・条件組合せをテスト技法で導出し、実値をコードで裏取りした
- [ ] 全ケースに種別（自動（済）/ 自動（要追加）/ 手動）と優先度がある
- [ ] 期待結果がすべて観測可能な形で書かれている
- [ ] 自動（済）のケースに実在するテストファイルパスを記録した
- [ ] 前提条件・準備手順に実在しないスクリプト・コマンドを書いていない（要作成のものは明記した）
- [ ] 仕様の穴を期待結果に勝手に埋めず `仕様上の確認事項` に分離した
- [ ] レビューサイクルが収束している（最終サイクルで採用すべき指摘がない）
- [ ] 手動確認チェックリストがそのままリリース前確認に使える

## 出力サマリ

完了後は、作成・更新したファイルパス、ケース数（観点別＝文書のセクション単位、種別別＝自動（済）/自動（要追加）/手動 の内訳）、要件カバレッジの充足、仕様上の確認事項のハイライトだけを簡潔に報告する。安全に推定した事項について確認を求めない。
