# Task Breakdown

技術設計書を、依存関係順に実行でき、完了を検証できる実装タスクリストへ変換する。

- **入力:** `*.spec.md`。対応する `*.requirement.md` があれば併読する
- **出力:** 入力と同じベース名の `*.task.md`
- **責務:** 設計をレビュー可能な実装単位へ分解し、要件・設計・検証を対応付ける
- **責務外:** 要件追加、設計変更、コード実装

## 自律実行の原則

1. **入力を自動探索する。** 明示された設計書を優先する。未指定なら `*.spec.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。
2. **関連文書を自動で読む。** 同じベース名の `*.requirement.md` があれば併読し、要件ID・受け入れ条件・スコープ外を引き継ぐ。
3. **コードベースで具体化する。** 設計書にパスがない場合は関連コードを調査し、既存の構成と依存関係から対象ファイル、テスト、検証コマンドを補う。
4. **安全に補完できる事項は質問しない。** 既存規約や設計から一意に推定できる内容は補完し、`実行上の注意` に前提として記載する。
5. **設計を勝手に変更しない。** 軽微な抜けは既存パターンで補完する。公開仕様、データモデル、権限境界を変える必要がある欠落だけをブロッカーとして、推奨案つきで確認する。
6. **既存ファイルがあれば更新する。** 完了済みチェックや利用者の追記を保持しつつ、設計差分に対応するタスクを追加・修正する。

## タスク分解の基準

- 実際の依存関係順に並べる。一般的には契約・型 → DB → バックエンド → フロントエンド → 統合・移行の順だが、設計に合わせて変える。
- 1タスクは、独立して実装・レビュー・検証できる成果物単位にする。
- 単なるファイル単位の細分化や、実装方法を判断できない大項目を避ける。
- 挙動変更には対応する自動テストを同じタスクまたは直後の依存タスクとして含める。
- スキーマ生成、マイグレーション、データ移行、設定、文書、リリース作業も漏らさない。
- 各タスクに対象ファイル、具体的な実装内容、テスト、検証方法、完了条件を書く。
- 全要件ID・受け入れ条件と設計セクションを、少なくとも1つのタスクへ対応付ける。
- 承認済みスコープ外の改善や無関係なリファクタを追加しない。

## 実行フロー

### Phase 1: 入力の把握

- 設計書から変更対象、依存関係、移行順序、テスト戦略、リスク、未決事項を抽出する。
- 対応する要件定義書から要件ID、受け入れ条件、スコープ外を抽出する。
- 未決事項のうち実装を妨げないものは注意事項として残し、分解を続ける。

### Phase 2: リポジトリ確認

- 対象ファイルとテストファイルが実在するか確認する。
- package scripts、ビルド、lint、型検査、テスト、コード生成、マイグレーションの実行方法を確認する。
- 設計とコードが食い違う場合はコードを根拠にタスクを具体化し、食い違いを注意事項へ記録する。仕様判断が必要な食い違いだけ確認する。

### Phase 3: 依存関係とカバレッジの整理

- タスク間の依存をDAGとして考え、前提タスクが先に来るよう並べる。
- 要件・受け入れ条件・設計セクションとタスクの対応を確認する。
- DB移行やAPI互換など、デプロイ順序に制約がある作業は分離して明示する。
- 最後に統合検証、手動確認、リリース・ロールバック確認を置く。

### Phase 4: タスクリストの作成

**ファイル名:** 設計書の `.spec.md` を `.task.md` に置換する。
**作成場所:** 原則として設計書と同じディレクトリ。

```markdown
# 実装タスク: <機能名>

## 実行上の注意

## タスク

### TASK-001: <検証可能な成果物>

- Status: [ ]
- 依存: なし
- 対応要件: REQ-001, AC-001
- 設計参照: <設計書のセクション>
- 対象ファイル:
  - `path/to/file`
- 実装内容:
  - <具体的な変更>
- テスト:
  - <追加・更新するテスト>
- 検証:
  - `<実行コマンドまたは確認方法>`
- 完了条件:
  - <観測可能な完了状態>

## 要件カバレッジ
## 最終検証
## 手動確認
## リリース・ロールバック確認
## 対象外・後続対応
```

## 完了条件

- [ ] 全要件・受け入れ条件・設計要素をタスクでカバーした
- [ ] タスクが依存関係順に並んでいる
- [ ] 各タスクに対象ファイル、実装内容、テスト、検証、完了条件がある
- [ ] 実在するパスとプロジェクト固有の検証方法を使っている
- [ ] 移行、生成、設定、リリース作業を必要に応じて含めた
- [ ] スコープ外や設計変更を混入させていない
- [ ] 実装担当者が追加の分解作業なしで着手できる

## 出力サマリ

完了後は、作成・更新したファイルパス、タスク数、主要な依存関係、実装を止めるブロッカーだけを簡潔に報告する。安全に推定した事項について確認を求めない。
