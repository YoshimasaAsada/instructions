# Task Breakdown

技術設計書を、依存関係順に実行でき、完了を検証できる実装タスクリストへ変換する。

- **入力:** `*.spec.md`。対応する `*.requirement.md` があれば併読する
- **出力:** 入力と同じベース名の `*.task.md`
- **責務:** 設計をレビュー可能な実装単位へ分解し、要件・設計・検証を対応付ける
- **責務外:** 要件追加、設計変更、コード実装

## 自律実行の原則

1. **入力を自動探索する。** 明示された設計書を優先する。未指定なら `*.spec.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。選択した入力ファイルのパスとタイトルは、作業開始時に1行で宣言する（誤った文書を掴んだまま進まないため）。
2. **関連文書を自動で読む。** 同じベース名の `*.requirement.md` があれば併読し、要件ID・受け入れ条件・スコープ外を引き継ぐ。
3. **コードベースで具体化する。** 設計書にパスがない場合は関連コードを調査し、既存の構成と依存関係から対象ファイル、テスト、検証コマンドを補う。
4. **安全に補完できる事項は質問しない。** 既存規約や設計から一意に推定できる内容は補完し、`実行上の注意` に前提として記載する。
5. **設計を勝手に変更しない。** 軽微な抜けは既存パターンで補完する。公開仕様、データモデル、権限境界を変える必要がある欠落だけをブロッカーとして、推奨案つきで確認する。
6. **既存ファイルがあれば更新する。** 完了済みチェックや利用者の追記を保持しつつ、設計差分に対応するタスクを追加・修正する。

## タスク分解の基準

- **縦スライス優先。** 1タスクは、関係する全レイヤー（スキーマ・API・UI・テスト）を貫く細いが完結した経路とし、そのタスク単体で動作をデモまたは検証できる状態にする。「DBだけ」「APIだけ」のレイヤー単位の分割（横スライス）は、縦に切れない場合の次善とする。
- **1タスク = 1コンテキスト。** 新規セッションのエージェントが上流文書と当該タスクだけを読んで完了できるサイズに収める。収まらないタスクは分割する。
- **prefactor は先頭に置く。** 変更を簡単にするための準備作業があれば、それを最初のタスクにする（変更を easy にしてから、easy な変更をする）。
- **横断リファクタは expand–contract で並べる。** リネーム・共有型の変更など影響範囲がコードベース全体に及ぶ機械的変更は縦スライスにせず、① 新形式を旧形式と並置する expand → ② 呼び出し側をバッチ移行（パッケージ・ディレクトリ単位で各バッチを1タスクとし、expand に依存させる）→ ③ 全バッチ完了後に旧形式を削除する contract、の順に分解し、各段階で CI が通る状態を保つ。
- 実際の依存関係順に並べる。
- 単なるファイル単位の細分化や、実装方法を判断できない大項目を避ける。
- 挙動変更には対応する自動テストを同じタスクまたは直後の依存タスクとして含める。
- スキーマ生成、マイグレーション、データ移行、設定、文書、リリース作業も漏らさない。
- 各タスクに対象ファイル、参考実装、具体的な実装内容、テスト、検証方法、完了条件を書く。参考実装は設計書の `参考にした既存実装` から該当するものを引き継ぎ、該当がなければ `なし` と明記する。
- 全要件ID・受け入れ条件と設計セクションを、少なくとも1つのタスクへ対応付ける。
- 承認済みスコープ外の改善や無関係なリファクタを追加しない。

## 実行フロー

### Phase 1: 入力の把握

- 設計書から変更対象、依存関係、移行順序、テスト戦略、リスク、未決事項を抽出する。`準拠するコーディング規約`・`参考にした既存実装` も抽出し、各タスクへ引き継ぐ。`対象外・後続改善` があれば、タスク化せず `対象外・後続対応` へそのまま引き継ぐ。
- 対応する要件定義書から要件ID、受け入れ条件、スコープ外を抽出する。
- 未決事項のうち実装を妨げないものは注意事項として残し、分解を続ける。

### Phase 2: リポジトリ確認

- 対象ファイルとテストファイルが実在するか確認する。
- package scripts、ビルド、lint、型検査、テスト、コード生成、マイグレーションの実行方法を確認する。
- 設計とコードが食い違う場合はコードを根拠にタスクを具体化し、食い違いを注意事項へ記録する。仕様判断が必要な食い違いだけ確認する。

### Phase 3: 依存関係とカバレッジの整理

- タスク間の依存をDAGとして考え、前提タスクが先に来るよう並べる。
- 要件・受け入れ条件・設計セクションとタスクの対応を確認する。
- DB移行やAPI互換など、デプロイ順序に制約がある作業は分離して明示する。
- 最後に統合検証、手動確認、リリース・ロールバック確認を置く。

### Phase 4: タスクリストの作成

**ファイル名:** 設計書の `.spec.md` を `.task.md` に置換する。
**作成場所:** 原則として設計書と同じディレクトリ。
**構成:** このスキルの `template.md` を読み、その構成に従う。

### Phase 5: レビューサイクル

`doc-review-cycle` スキルを起動し、次を渡して収束するまで回す。

- **対象:** 作成・更新した `*.task.md`
- **根拠資料:** 設計書・要件定義書・リポジトリの実コードと規約
- **記録先セクション:** `実行上の注意` または確認事項
- **観点:**
  - 要件・受け入れ条件・設計セクションのカバレッジ
  - 依存関係順の正しさ
  - タスク粒度（縦スライスになっているか / 1コンテキストに収まるか / 独立して実装・レビュー・検証できるか）
  - 設計書の `参考にした既存実装` の各タスクへの引き継ぎ漏れ
  - 移行・生成・設定・リリース作業の漏れ
  - スコープ外や設計変更の混入

設計の変更を要する指摘は不採用とし、記録先セクションへ残す。`doc-review-cycle` が使えない場合は、同スキルのサイクル（レビュー → 突き合わせ → 修正 → 上限3サイクル）を自分で実行する。

## 完了条件

- [ ] 全要件・受け入れ条件・設計要素をタスクでカバーした
- [ ] タスクが縦スライス（単体でデモ・検証可能）になっている。横スライスにした箇所は理由を `実行上の注意` に記録した
- [ ] タスクが依存関係順に並んでいる
- [ ] 各タスクに対象ファイル、参考実装、実装内容、テスト、検証、完了条件がある
- [ ] 実在するパスとプロジェクト固有の検証方法を使っている
- [ ] 移行、生成、設定、リリース作業を必要に応じて含めた
- [ ] スコープ外や設計変更を混入させていない
- [ ] レビューサイクルが収束している（最終サイクルで採用すべき指摘がない）
- [ ] 実装担当者が追加の分解作業なしで着手できる

## 出力サマリ

完了後は、作成・更新したファイルパス、タスク数、主要な依存関係、実装を止めるブロッカーだけを簡潔に報告する。安全に推定した事項について確認を求めない。
