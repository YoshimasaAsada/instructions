# Diff Map

PR の差分を「差分を開く前に読む1枚」に変換する。

- **入力:** PR番号・ブランチ・コミット範囲。指定がなければ現在のブランチ（`git merge-base develop HEAD` 〜 HEAD と作業ツリー）
- **出力:** 自己完結 HTML 1ファイル。リポジトリルートの `tmp/diff-map/<PR番号またはブランチのスラッグ>.html`（`tmp/*` は git 管理外で、作業ディレクトリ内なのでアプリのファイルペインでも開ける）
- **責務:** 差分の意味と周辺の読み取り、実データでの裏付け、DBアクセスの要約、図解、読む順と読まなくてよい箇所の提示
- **責務外:** コードの変更（`implement`）、不具合探しのレビュー（`code-review`）、手動確認シナリオ（`test-scenario-from-diff`）、差分ではない既存コードの解説（`code-map`）

## なぜ差分の地図が要るか

セルフレビューで時間がかかるのは差分を読む量ではなく、「何を作ったか」と「その周りがどうなっているか」の理解。AI が書いたコードは書いた本人の頭に全体像がない。差分はファイル順の断片で処理の流れ順になっておらず、データの出どころや既存の型が発行するクエリは差分に一行も出てこない。

この地図はその理解を差分を開く前に済ませるためのもの。だから書くのは**差分の逐行解説ではなく、差分を読むための前提知識**で、読者がこれを読んだ後に差分を開くと「どこを読めばよく、どこは読まなくてよいか」が分かっている状態を目指す。

## 原則

1. **読む順に並べる。** 挙動（画面・API の入出力）→ データの出どころ → 処理の流れ → コード、の順。ファイル順・diff 順にしない。人は「何が起きるか」を掴んでからでないとコードを読めない。
2. **推測で書かない、数字で書く。** `code-map` と同じく、件数・値・SQL 回数は実行して取る。確かめられないものは「未確認」と明記する（例: 本番の件数）。開発DBのデータが動作確認用のテストデータだった場合はそう書く。テストデータの件数を本番の傾向として読ませると判断を誤らせる。
3. **差分の外を書く。** 理解のボトルネックは差分に写らない部分にある。データを作る側、制約（索引・バリデーション）、同じデータの既存の利用箇所、発火タイミング、業務上の約束を、差分と同じ重さで扱う。
4. **読まなくてよいものを明示する。** 生成物、既存コードのコピー、機械的な変更は「読まない」と書き、本当に読む必要のある行数を出す。コピーはコピー元と差分（何を足した・外したか）だけを示す。
5. **DB に触れるならクエリごとに要約する。** 「SQL 5回」とテーブル名を並べるだけでは、なぜそのクエリが出るのかが分からない。1本ずつ目的・条件・件数・索引・発行元を書く（Phase 5）。
6. **疑問には根拠で答える。** セルフレビューで浮かぶ疑問への答えには `file:line` を添える。根拠のない「大丈夫です」は理解の代わりにならない。
7. **直さない。** 気づいた問題は「気づいた点」に書くだけにする。直すなら `implement` を使う。
8. **共有DBに書き込まない。** 開発DBは他の worktree・セッションと共有している。スクリプトは読み取りだけにする（Phase 4）。

## 実行フロー

### Phase 1: 範囲を宣言して差分を全部読む

- PR番号があれば `gh pr view <n> --json title,body,files,mergeCommit,baseRefName` で本文と関連 issue を読み、`gh pr diff <n>` で差分を取る。マージ済みなら `git diff <mergeCommit>^1 <mergeCommit>` でもよい。
- 指定がなければ `git merge-base develop HEAD` を base にし、`git diff --stat <base>` と作業ツリーを対象にする。
- **base・ファイル数・PR/issue番号を作業開始時に1行で宣言する。** 範囲を取り違えると成果物が丸ごと無駄になる。
- 生成物以外の差分を全部読む。新規ファイルは全文を読む。
- 未マージの PR は `git fetch origin <head ブランチ>` で取り、`git merge-base origin/develop <head>` を base にする。PR の時点のファイルは `git show "${rev}:<path>"` で読む（zsh では `$rev:path` の `:t` などが修飾子として解釈されるので、必ず `${rev}` と引用符で囲む）。
- Phase 4・5 で PR のコードを Rails で動かす必要があるときは、worktree が clean なことを確かめてから `git checkout --detach <head>` する。stash は使わない（他の worktree と共有している）。**作業の最後に必ず元のブランチへ戻す。**

### Phase 2: 差分を仕分ける

各ファイルを **ロジック / テスト / 生成物** に分け、追加・削除の行数を集計する（HTML の内訳バーに使う）。

- **生成物の例:** `**/graphql/generated.ts`、`apps/*/generated/*.ts`、`**/generated/types.ts`、`schema.graphql`、`db/schema.rb`、annotate の注釈だけの変更
- **コピーの検出:** 新規ファイルや大きな追加ハンクは、特徴的な識別子・文言・JSX の構造で grep し、既存に同型のコードがないか探す。見つかったら「◯〜◯行は `<コピー元>` から △△ を外したもの」と書き、読む範囲を新しいロジックに絞る。
- **テスト:** `describe` / `context` / `it`（Vitest なら `describe` / `it`）のケース名だけを抜き出す。中身の正しさは CI に任せ、地図では観点が揃っているかを見せる。
- **移動とインデント:** レイアウトの組み替えは、同じコードの移動と字下げの変更で行数が膨らむ。`git diff -w --numstat` で空白を無視した行数も出して併記し、「◯〜◯行は位置を移しただけ」と書く。読者には `git diff -w` で見るよう案内する。

### Phase 3: 周辺を読む

変更した識別子（GraphQL フィールド、メソッド、スコープ、コンポーネント、カラム、enum）ごとに、差分の外を少なくとも次の観点で読む。対象ファイルは全文を読み、部分読みで説明を始めない。

| 観点 | 探すもの |
|---|---|
| データの出どころ | そのレコードを作成・更新するコード（mutation・job・form・batch）。いつ・誰が・どんな形式で作るか |
| 制約 | 関連（`has_one` / `has_many`）、UNIQUE 索引、バリデーション、NOT NULL。「なぜ1件でよいか」「なぜ nil にならないか」の根拠になる |
| 既存の利用箇所 | 同じデータを表示・処理している別の画面・API。今回の実装と見比べる対象 |
| 発火タイミング | タブの `lazyMount` / `unmountOnExit`、Apollo の `fetchPolicy`（Apollo Client を初期化するコードの `defaultOptions`）、`skip` 条件、ジョブのスケジュール |
| 業務上の約束 | ユーザー向け文言・docs・issue にある約束（例: 「出品者には購入者の連絡先を共有しない」）。どこに出してよいデータかが決まる |
| 追随の仕組み | 型の網羅チェックや規約で、差分の一見無関係な行が必要になる理由（例: GraphQL 型にフィールドを足すと監査ラベルの `never` チェックに掛かる） |

### Phase 4: 実データで裏付ける

Rails アプリの `tmp/diff_map_<slug>.rb` にスクリプトを書き、プロジェクトの実行コマンド（`bin/rails runner tmp/diff_map_<slug>.rb`、Docker 経由なら `just dip rails runner ...` のようなラッパー）で実行する。出力の扱い（`Rails.logger.level = :warn`、grep フィルタ）は `code-map` の Phase 2 に従う。

- worktree の非対話シェルで `dip: command not found` のようにコマンドが見つからず、リポジトリが mise を使っているなら `mise exec -- <コマンド>` にする。`mise.toml` が未信頼なら先に `mise trust`。
- スクリプトの編集は Write で書き直す。sed で部分置換すると引用符を壊しやすい。
- **クエリキャッシュを外す。** rails runner の中でもクエリキャッシュが効き、同じ SQL の2回目以降はキャッシュから返る。本数を数える処理は `ActiveRecord::Base.uncached { ... }` で囲む（囲まないと、2本目のクエリが「SQL 0本」のように少なく出る）。
- **時間は1回空打ちしてから測る。** 最初の実行にはスキーマ読み込みなどの準備が乗る。時間はローカルの参考値として扱い、比較の主役は SQL の本数にする。
- 並び順付きのスコープ（`visible` など）に `distinct` や `group` を重ねると PostgreSQL がエラーにする。集計のときは `reorder(nil)` で並び順を外す。

出すもの:

- **ファネル:** 対象データができるまでの段階ごとの件数（例: 注文 70,000 → 発送済み 4,600 → 依頼送信済み 2 → 回答 4）
- **分岐の内訳:** 差分の各分岐を通るデータの件数（例: 「発送日が空: 0件 → この分岐は今のデータでは通らない」）
- **実際の入出力:** 変更後のコードに実データを流した結果を、分岐ごとに1例ずつ（あり / なし など）。GraphQL なら FE と同じクエリを `AppSchema.execute(query, variables:, context: { current_user: })` で実行する（スキーマ名・context のキーはプロジェクトに合わせる）
- **変更前:** `git show <base>:<path>` の実コードから、同じデータで何が返っていたかを導く。追加だけの変更なら「なかった」でよい
- **データの素性:** 件数が少ない・作成日時が集中している・本文に `[tp-xxxx]` のような接頭辞がある場合は、動作確認用データかを確かめて明記する

create / update / destroy / ジョブ投入を伴う処理は実行しない。変更後の値を見たいだけならコードから導く。

バックエンドを通らない差分（FE だけの見た目の変更など）は、このフェーズと Phase 5 を省き、その理由を根拠セクションに書く。

### Phase 5: DB アクセスを要約する

処理の流れが DB に触れる場合は必ず行う。対象は、今回追加・変更したフィールド・スコープ・クエリと、**その下で既存の型やローダーが発行するクエリ**の両方。後者こそ差分から読めない。

1. このスキルの `sql_capture.rb` を Rails アプリの `tmp/diff_map_<slug>_sql.rb` にコピーし、「対象の処理」の部分を書き換えて実行する。SQL ごとに名前・SQL・バインド値・返した行数・発行元（`app/` 配下の呼び出しフレーム）・実行計画の1行目と実行時間・テーブルの総行数が出る。
2. 発行元が `AssociationLoader` などの共通部品になっているものは、どのフィールド定義（`load: true` や自前のリゾルバメソッド）から呼ばれたかをコードで特定する。
3. 次の表にする。

   | # | 何のために | テーブルと条件 | 件数・索引 | 発行元 |
   |---|---|---|---|---|
   | ② | その注文のレビューを取る（**今回追加** `review`） | `reviews` / order_id = ①の id | 1行（最大1行）/ order_id の UNIQUE 索引 | `AssociationLoader`（`order_type.rb:126` の `load: true`） |

   「何のために」には、どの GraphQL フィールド・メソッドの解決で出たかと、今回追加か既存かを書く。「テーブルと条件」には、前の SQL の結果とどうつながるかを書く。

4. 表の上に3行のまとめを置く。
   - **いつ発行されるか:** 初回だけか毎回か、何がきっかけか（タブを最初に開いたとき、ページを開き直すたび、日次ジョブ など）。`lazyMount` や `fetchPolicy` をコードで確かめてから書く
   - **重さ:** 索引の有無、実行時間、全カラム読み込みや件数に比例する N+1 の有無
   - **今回の差分が直接発行するのはどれか**
5. SQL 全文と実行計画は `<details>` に入れる。

「なぜこの SQL が出るのか」が差分から分からないもの（例: 商品名を出すために `products` を経由して `product_details` を引く）は、発行元のコードを読んで理由を書く。

**実際の画面のクエリで変更前後を比べる。** 差分がクエリの本数や重さを変えるもの（`load: true`・`includes`・ローダーの追加、N+1 の解消、取得フィールドの追加）なら、手で書いた縮小版のクエリだけでなく、画面が実際に送るクエリで本数を比べる。

1. このスキルの `assemble_gql.py` で、フロントの `.gql` から画面の操作と使用フラグメントを集めたクエリ文書を Rails アプリの `tmp/` に書き出す（使い方はファイル先頭）
2. そのクエリを、件数の多いデータ（最大）と典型的なデータ（中央値）の2つで実行し、SQL の総数と名前ごとの本数を出す
3. worktree を base に `git checkout --detach` して同じクエリ文書を流し、変更前の本数を取る（フロントは PR 版のクエリのまま、BE だけ変更前にする）。終わったら元に戻す
4. 「変更前 → 変更後」と「減った・増えた SQL の名前」を表にして、図2の「ここで確定すること」に載せる

**件数に比例する SQL は発行元まで辿る。** 1件ごとに出ている SQL（同じ名前が件数と同じ本数ある）は、`caller_locations` を `app/(models|graphql)` で絞って発行元のメソッドを特定し、今回の差分によるものか既存のものかを書き分ける（例: `ProductDetail#shop_name` が商品ごとに `shop` を読む）。原因まで特定できなければ「原因は未調査」と書く。

### Phase 6: 図を描く

図は `code-map` の Phase 4「HTML で描くときの決めごと」に従う（インライン SVG、`viewBox`、実表示 12px 以上、線を交差させない、エッジラベルに下地、1枚あたりノード5〜6個）。この地図で使う図は次の3種類で、該当しないものは省く。

| 図 | 形 | 描くもの |
|---|---|---|
| 周辺の流れ | 左→右のパイプライン | データが作られてから、今回の表示・処理に届くまで。今回の変更箇所だけ色を変える |
| 入口から DB まで | 3レーン（画面 FE / API BE / DB） | 処理の経路。ノードを **新規・変更・既存** で色分けする。ノードを階段状に置くと線が交差しない |
| 出し分け | 分岐フロー | 1つの入力が条件ごとにどう描画・処理されるか。分岐ラベルにデータの条件を書く |

各図の下に「ここで確定すること」のカードを付け、Phase 4・5 の数字を入れる。

画面が変わる差分は、変更前と変更後の画面を HTML で簡易に再現し、追加・変更した部分を赤枠で囲む。表示値は実データと実際の整形関数（例: `timeText`）の出力にそろえ、日付の見え方が「いつ開いたか」で変わるならその基準日を書く。

### Phase 7: 疑問と周辺の事実をまとめる

- **セルフレビューで浮かびそうな疑問（3〜6個）と答え。** 根拠は `file:line`。典型的な疑問:
  - なぜこの件数・この形でよいのか（制約の根拠）
  - ガード（`skip`・nil チェック・権限）が無いが大丈夫か（なぜ到達しないか）
  - N+1 や重いクエリにならないか（Phase 5 を参照させる）
  - 一見無関係な行は何のためか（追随の仕組み）
  - この値はどのデータを指しているか（作成時点の値か、現在の値か）
- **周辺で知っておくこと:** コードから読み取りにくい事実（データの形式、ユーザーへの約束、レート制限、ジョブの対象条件など）。
- **気づいた点（直していない）:** 重複、規約とのずれ、マスク漏れなど。PR の範囲外なら範囲外と書く。

### Phase 8: HTML を組み立てて目視する

このスキルの `template.html` を読み、そのスタイルとセクション順で書く。セクション順は次のとおりで、該当しないセクションは省く。

1. 30秒サマリ（何が変わったか / 変更の中心と読む必要のある行数 / 今のデータで見えるもの）
2. 変更前 → 変更後（画面・挙動）
3. 周辺の流れ（図）
4. 処理の流れ（図）、DB アクセスの要約、出し分け（図）
5. 差分の読み方（ファイル別。◎ 読む / ○ 確認 / △ 名前だけ / × 読まない）
6. セルフレビューで浮かびそうな疑問
7. 周辺で知っておくこと
8. 気づいた点（直していない）
9. 根拠（実行したスクリプト、読んだファイル、データを取った DB と日時）

画面を確認する URL は、そのままブラウザに貼れるフルパスで書く。ローカルのフロントの URL は `just hosts` で確かめ、dev サーバーが起動していなければパスだけを書いてその旨を添える。

**目視:** 内蔵ブラウザは `file://` のページを撮影できないので、静的サーバーで配信して確認する。

1. `.claude/launch.json` に一時的な構成を書く（`"runtimeExecutable": "python3"`、`"runtimeArgs": ["-m", "http.server", "<port>", "--bind", "127.0.0.1", "--directory", "<保存先ディレクトリ>"]`）。既に launch.json があれば構成を追記し、元の内容を覚えておく
2. `preview_start` で開き、デスクトップ幅（`resize_window` で 1200px）と狭い幅（375px 前後）の両方で、このスキルの `layout_check.js` を `javascript_exec` に丸ごと渡す。SVG ノードからの文字のはみ出し、文字同士やエッジラベルとノードの重なり、実表示 12px 未満の文字、ページ全体の横はみ出し（原因の要素つき）を返す。`ok: true` になるまで直す
3. スクリーンショットでも見る。ペインが狭いと 1200px の指定は縮小表示されて読めないので、デスクトップ幅は `layout_check.js` の結果で判断し、見た目は狭い幅で確かめる。`scrollIntoView` 直後のスクリーンショットはスクロール前の画面が撮れることがあるため、`window.scrollTo` のあと1秒待ってから撮る
4. 確認後は `preview_stop` でサーバーを止め、`resize_window` を `desktop` に戻し、launch.json を元に戻す（新規に作ったなら消す）

狭い幅で崩れやすいもの（`template.html` には対策済み）: 長い `code` の文字列（`overflow-wrap: anywhere`）、列の多い表（最小幅を持たせて枠内でスクロール）、画面イメージ（`.screen` 内でスクロール）、絶対配置のラベル（`white-space: nowrap`）。

### Phase 9: 報告

`SendUserFile`（`display: "render"`）で HTML を送る。本文は短くする。

- 対象範囲（PR・base・ファイル数）
- 地図で分かった、差分からは読めない事実の上位2〜3個
- 未確認の事項（本番の件数など）と、データがテストデータだったかどうか
- 気づいた点の件数
- 作ったスクリプトのパス（Rails アプリの `tmp/` 配下。残すか消すかを確認する）
