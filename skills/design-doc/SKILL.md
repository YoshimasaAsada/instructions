# Design Doc

承認済みの要件定義書を、既存コードに整合する実装可能な技術設計へ変換する。

- **入力:** `*.requirement.md`、対象リポジトリ、関連資料
- **出力:** 入力と同じベース名の `*.spec.md`
- **責務:** 実装方式、責務境界、データ・API・UI・テスト・移行方法を決める
- **責務外:** 要件の新規作成、実装タスクへの分解、コード実装、要件充足に不要な既存実装のリファクタリング・アーキテクチャ変更

## 自律実行の原則

1. **まず探索し、確認より先に進める。** 入力パス、対象リポジトリ、機能名、出力先は会話・カレントディレクトリ・Gitブランチ・既存文書から推定する。
2. **入力を自動選択する。** 明示された要件定義書を優先する。未指定ならリポジトリ内の `*.requirement.md` を探索し、現在のブランチ名または依頼内容と一致するものを選ぶ。選択した入力ファイルのパスとタイトルは、作業開始時に1行で宣言する（誤った文書を掴んだまま進まないため）。
3. **プロジェクト規約と既存コードを既定値にする。** 対象リポジトリのコーディング規約（`CLAUDE.md`、`AGENTS.md`、`.claude/rules/`、lint・formatter設定等）に設計を準拠させ、命名、ディレクトリ構成、アーキテクチャ、エラー処理、テスト方法は既存の類似実装に合わせる。準拠した規約と参考にした類似実装は、具体的なファイルパスつきで設計書へ記録する。
4. **安全に推定できる事項は質問しない。** 可逆で局所的な実装判断は最も整合する案を採用する。不足情報は `前提` または `未決事項` として明示して作業を継続する。
5. **質問はブロッカーだけに限定する。** ユーザー価値や公開仕様が変わる選択、権限・セキュリティ境界、不可逆なデータ移行、複数候補の誤選択が重大になる場合のみ質問する。質問には推奨案を添える。
6. **既存ファイルがあれば更新する。** 全面作り直しではなく、要件とコードの現状に合わせて必要箇所を修正し、内容の一貫性を保つ。

## 実行フロー

### Phase 1: 入力と要件の確認

- 要件定義書の対象範囲、要件ID、受け入れ条件、制約、スコープ外、未決事項を抽出する。
- 未決事項に既定案がある場合、可逆で局所的な実装判断に留まるものだけ既定案を採用し、`前提・採用した既定案` に記録する。ユーザー価値・公開仕様・権限・セキュリティ境界・不可逆なデータ移行に関わる未決事項は勝手に確定させず、`未決事項` に残した上で推奨案つきで確認する（原則5）。
- 要件同士が矛盾し設計を一意に決められない場合だけ、推奨案つきで確認する。

### Phase 2: コードベース調査

次の2つを必ず先に行ってから、関連コードを追跡する。

1. **コーディング規約の棚卸し。** 対象リポジトリの指示書（`CLAUDE.md`、`AGENTS.md`、`.claude/rules/`、README、lint・formatter設定等）を読み、今回の設計に適用される規約を出典（ファイルパス・セクション）つきで抽出する。抽出結果は設計書の `準拠するコーディング規約` に記録する。
2. **類似実装の調査。** 設計対象と同種の既存実装（同レイヤーの画面・API・モデル・バッチ等）を必ず探して読み、構成・命名・パターンを把握する。参考にする実装は「どのファイルの何を参考にしたか」まで設計書の `参考にした既存実装` に記録する。類似実装が見つからない場合は、その旨と代わりに依拠した規約を記録する。

最低限、該当する項目を調査する。

- 既存の類似機能と責務境界
- データモデル、テーブル・カラムの実名、マイグレーション規約
- API、スキーマ、サービス、認証・認可
- フロントエンドのデータ取得、状態管理、コンポーネント構成
- バリデーション、エラー処理、ログ、監視
- テスト構成、生成処理、品質ゲート
- 暗号化、テナント分離、後方互換性、性能上限、外部依存

設計判断には具体的なファイルパスを根拠として記載する。存在しないファイルや識別子を事実として書かない。

### Phase 3: 設計判断

- 各要件・受け入れ条件を設計要素へ対応付ける。
- Phase 2 で抽出した規約に設計を準拠させる。規約と矛盾する設計案は採用せず、どうしても準拠できない場合は理由と影響を `前提・採用した既定案` に記録する。
- 既存パターンを優先し、外れる場合は理由と代替案を示す。
- **要件充足に不要な既存コードの変更を設計へ含めない。** 既存実装に改善余地（重複、命名、責務の混在、より良い設計）を見つけても、それを直さないと要件・受け入れ条件を満たせない場合を除き、設計の変更範囲へ入れない。気づいた改善は `対象外・後続改善` へ根拠・影響範囲つきで記録し、次工程（`task-breakdown` / `implement`）が実装しないよう「対象外」と明示する。
- データ変更では移行順序、互換期間、ロールバックを定義する。
- APIや型の変更では呼び出し元・利用者への影響を明示する。
- 正常系だけでなく、権限不足、入力不正、部分失敗、再試行、空状態を設計する。
- **テスト戦略ではテストを置くシームを決める。** シーム（振る舞いを観測する公開境界。API・サービスインターフェース・コンポーネント境界など）を明記し、既存のシームを優先して、できるだけ高い位置の少数のシームに集約する。実装工程はここに書かれたシームにテストを置く。
- **不可逆な設計判断は ADR へ昇格させる。** 次の3条件をすべて満たす判断だけ、プロジェクトの ADR 置き場（`docs/adr/` 等。無ければ作成を提案）へ切り出す: (1) 後から変えるコストが大きい (2) 文脈を知らない読者が「なぜこうなっている？」と思う (3) 実在する代替案の中から選んだ結果である。1つでも欠けるなら設計書内の `検討した代替案` に留める。ADR は設計書が削除された後も残る前提で書く。
- **話し合いで決められない未決事項にはプロトタイプの選択肢を添える。** UIの見え方・操作感・状態遷移の妥当性など文書では決められない論点は、使い捨てプロトタイプで検証する案を未決事項へ添える。プロトタイプ由来のスニペット（状態機械・スキーマ・型など、決定を文章より正確に固定するもの）は、出典を一言添えて設計書へインラインしてよい。
- コード例は契約や難所を明確にする場合だけ使い、未確認の疑似実装で仕様を固定しない。

### Phase 4: 設計書の作成

**ファイル名:** 要件定義書の `.requirement.md` を `.spec.md` に置換する。
**作成場所:** 原則として要件定義書と同じディレクトリ。
**構成:** このスキルの `template.md` を読み、その構成とセクション別の書き方に従う。該当しない項目は理由つきで `N/A` とする。

### Phase 5: レビューサイクル

`doc-review-cycle` スキルを起動し、次を渡して収束するまで回す。

- **対象:** 作成・更新した `*.spec.md`
- **根拠資料:** 要件定義書・リポジトリの規約（`CLAUDE.md`/`AGENTS.md`/`.claude/rules/` 等）・既存の類似実装
- **記録先セクション:** `未決事項`
- **観点:**
  - 要件・受け入れ条件のカバレッジ
  - コーディング規約への準拠（`準拠するコーディング規約` の出典が実在し、設計内容と矛盾していないか）
  - `参考にした既存実装` の具体性（パスが実在し「参考にした点」が明記されているか、主要な設計要素に参考元の記載漏れがないか）
  - 既存パターンとの整合と逸脱理由の妥当性
  - **要件充足に不要な既存実装の変更（リファクタ・共通化・リネーム・構造の作り直し）が変更範囲へ混入していないか**
  - テスト戦略にシーム（テストを置く公開境界）が明記されているか
  - 異常系（権限不足・入力不正・部分失敗・再試行・空状態）の網羅
  - 移行・互換性・ロールバックの妥当性
  - 次工程がこの文書だけでタスク化できるか

要件の変更を要する指摘は不採用とし、`未決事項` へ推奨案つきで残す。`doc-review-cycle` が使えない場合は、同スキルのサイクル（レビュー → 突き合わせ → 修正 → 上限3サイクル）を自分で実行する。

## 完了条件

- [ ] 全要件IDと受け入れ条件が設計要素に対応している
- [ ] 変更予定ファイルと責務が具体的である
- [ ] データ、API、UI、権限、エラー、テストへの影響を確認した
- [ ] テスト戦略にテストを置くシームを明記した
- [ ] `準拠するコーディング規約` に適用規約を出典つきで記載し、設計が規約と矛盾していない
- [ ] `参考にした既存実装` に設計要素ごとの参考元ファイルと参考にした点を記載した
- [ ] 変更範囲が要件充足に必要なものだけで構成されている（見送った既存実装の改善は `対象外・後続改善` に記録した）
- [ ] 移行・互換性・ロールバックを必要に応じて定義した
- [ ] 推定事項と未決事項を確定事項から分離した
- [ ] レビューサイクルが収束している（最終サイクルで採用すべき指摘がない）
- [ ] 次工程の `task-breakdown` が追加調査なしでタスク化できる

## 出力サマリ

完了後は、作成・更新したファイルパス、主要な設計判断、採用した前提、実装を止める未決事項だけを簡潔に報告する。質問不要の未決事項は文書へ残し、会話を止めない。
