# PR本文テンプレート

リポジトリに `.github/PULL_REQUEST_TEMPLATE.md` が**ある場合はそちらを優先**する。無い場合にこのテンプレートを使う。

**書いてよいのは、差分・上流文書（`*.task.md` / `*.spec.md` / `*.requirement.md` / `*.testdata.md`）・実行したチェックから裏取りできる内容だけ。** 実装していない内容、「今後対応予定」、根拠のない影響範囲を書かない。該当がないセクションは省略する。

---

```markdown
## 概要

<変更の目的と背景を1〜3文。何のために何を変えたか>

<スタックの場合は、この段が担当する範囲を1文で>

## 対応要件

- REQ-001: <要件の要約>
- AC-001: <受け入れ条件>

<対応する要件定義書がない場合はこのセクションを省略する>

## 変更内容

- **<変更点>** … <一行説明。ファイル・関数名を含める>
- **<変更点>** … <一行説明>

## 影響範囲

- <影響を受けるレイヤー・機能。差分から裏取りできる範囲だけ>

## 破壊的変更

<API変更・DBスキーマ変更・環境変数追加など。無ければセクションごと省略する>

## 確認したこと

- <実行したチェックとその結果。例: lint / 型検査 / テスト（軽量チェック）>

## 動作確認

1. <手順>
2. <手順>

<*.testdata.md がある場合は、そこに記載されたフルパスのURLを列挙する>

## 関連

- 対応タスク: TASK-001, TASK-002
- 見送った改善: `<path>.followup.md`
- Issue: #<番号>

## Stack

- #101 (1/3) <段の要約>  ← このPR
- #102 (2/3) <段の要約>
- #103 (3/3) <段の要約>

> 下から順にマージしてください。

<単一PRの場合はこのセクションを省略する>

---

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

---

## 各セクションの書き方

| セクション | 書くこと | 書かないこと |
|---|---|---|
| 概要 | 目的と背景。スタックならこの段の担当範囲 | 実装手順の解説 |
| 対応要件 | 要件定義書の要件ID・受け入れ条件 | 要件定義書に無いID |
| 変更内容 | 差分から読み取れる変更点。ファイル・関数名を含める | 差分に無い変更 |
| 影響範囲 | 差分から裏取りできるレイヤー・機能 | 推測による波及範囲 |
| 破壊的変更 | API・DBスキーマ・環境変数・設定の変更 | 該当が無いのに「なし」と書くだけの節 |
| 確認したこと | 実際に実行したチェックとその結果 | 実行していないチェック |
| 動作確認 | 手動確認の手順。`*.testdata.md` のURL | 検証していない手順 |
| 関連 | タスクID・followup・Issue | 存在しないIssue番号 |
| Stack | 段の一覧と現在位置 | 未作成のPRの仮番号 |

## スタック時の注意

- **Stack セクションのPR番号は、全PR作成後の2パス目で入れる。** 仮番号やプレースホルダのまま push しない
- expand 段階で未使用コードが入るPRは、概要に「このPRで追加した <対象> は次のPR（<段の要約>）で使う」と明記する
- 束ねたタスクがある段は、`関連` の `対応タスク` に含まれる全タスクIDを列挙する
