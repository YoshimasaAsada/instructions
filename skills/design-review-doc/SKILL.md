# Design Review Doc

作成済みの要件・設計文書から、**設計上の論点だけを取り出した社内レビュー用文書**へ整形する。

- **入力:** `*.spec.md` を主入力とし、同じベース名の `*.requirement.md` / `*.task.md` があれば併読する。実装済みなら対象コードも読む
- **出力:** 入力と同じベース名の `*.review.md`（原則として入力文書と同じディレクトリ）
- **責務:** 確定した事実だけを抽出し、決められた章構成へ、省略なしで書き下す
- **責務外:** 新しい設計判断、要件の追加・変更、テスト方針・テスト項目の記述、コード実装
- **関連:** 前工程は `design-doc` / `task-breakdown` / `test-case-doc`。設計の中身を変える必要が出たら、このスキルで直さず前工程へ差し戻す

## この文書の目的

**レビュー文書は、設計上の論点をレビュアーに確認してもらうための資料である。設計の全体を説明する資料ではない。**

レビュアーは入力文書を持たないが、必要なのは設計を隅々まで理解することではなく、**確認すべき判断に集中して意見を言えること**である。したがって「これはレビューで確認したいことか」が、書くかどうかの唯一の判断基準になる。

**書くもの（論点）**

- 判断が分かれる選択と、その案を採った理由
- 規約・既定・既存の慣例から外れる選択
- 他機能へ波及する影響（既存の挙動が変わる箇所）
- 要件に根拠がなく、設計側で決めた仕様
- 間違えると壊れる前提・制約

**書かないもの（ノイズ）**

- 「普通こうなるよね」で済むもの。**誰が設計しても同じ結論になる部分は、レビューする余地がない**
- 規約・命名から導けること
- 選択の余地が実質ない箇所で、既定をそのまま使ったこと
- 既存の仕組みを、変更しないのに説明すること

網羅性は目的ではない。**書く量を増やすほど論点が埋もれる**ため、迷ったら落とす。

以下の「記述ルール」はこの目的の具体化であり、章構成や網羅性より優先して守る。

## 記述ルール

### ルール1: 確定した事実だけを書く

- **事実の出典は次の2つだけ。** (a) 実装済みのコード、(b) 入力文書のうち確定として記述された内容（`前提・採用した既定案` を含む確定事項）。この2つに根拠がない記述は書かない。
- **実装済みならコードを正とする。** 文書とコードが食い違う場合はコードを事実として書き、食い違いの内容を出力サマリで報告する。文書側の記述をレビュー文書に残さない。
- **未実装ならコードで裏取りできる範囲だけ裏取りする。** 変更対象の既存テーブル・既存クラス・既存画面の現状はコードで確認し、実在するファイルパス・カラム名・メソッド名だけを書く。
- **未確定のものは本文へ一切書かない。** 入力文書の `未決事項` / `仕様上の確認事項` / `TBD` / `要検討` / `未定` / `暫定` / `仮` とマークされた内容、および複数案が併記されたまま決まっていない内容は、レビュー文書から**除外**する。Appendix にも書かない。
- **除外したものは出力サマリで警告する。** 「未確定のため除外した項目」として、何を落としたか・どの文書のどのセクションにあるかを列挙し、レビュー前に確定させるべきものとして報告する。
- **禁止表現。** 「〜と思われる」「〜のはず」「〜する想定」「〜を検討中」「〜すべき」「必要に応じて」「将来的に」「〜かもしれない」。これらを書きたくなった時点で、それは確定事実ではないので除外対象。
- **検討経緯は書かない。採った理由は書く。** 「どう迷ったか」「何を比較したか」の経過は落とす。ただし**判断が分かれる選択については、採った案とその理由を1〜2行で書く**（それがレビューで確認したいことのため）。却下案は、採用理由の説明に必要な範囲でのみ触れる。

### ルール2: 書くと決めた内容は省略記法で代替しない

論点として書くと判断した内容に限って適用する。ルール3で落とすと決めたものを、このルールを理由に書き足さない。

- **ラベル単独参照の禁止。** `C1` `パターンA` `ケース①` `条件2` のような記号でケース・条件・パターンを指し示さない。参照するたびに条件の中身を書き下す（「C1 の場合」ではなく「求職者が退会済みの場合」）。デシジョンテーブルを転記する場合も、条件列にラベルではなく条件文そのものを入れる。
- **反復省略の禁止。** 「同上」「同左」「〃」「上記と同様」「以下同様」「（略）」「...」「〜等」「〜など」を使わない。表のセルであっても毎回フルで書く。
- **列挙の打ち切り禁止。** 書くと決めた列挙（新規に定義する enum の値、権限による表示の出し分けなど）は全件を書く。ただし**既存の型やテーブルの全項目を、変更しないのに並べない**。触る部分と、それが影響する部分だけを書く。
- **ID を主語にしない。** `REQ-001` `TASK-003` `TC-012` のような識別子は、それ単体では内容が読めない。本文では内容を書き、ID は必要なら内容の後ろに括弧で添えるだけにする。ID だけの対応表を作らない。
- **略語・社内用語は初出で展開する。** 定義を裏取りできない用語は、本文でも使わず一般的な表現に置き換える。
- **入力文書へのリンクで内容を代替しない。** 「詳細は設計書を参照」と書かない。レビュアーは入力文書を持っていない。

### ルール3: 論点でないものは書かない

**「これを読んだレビュアーに、確認・判断してほしいことがあるか」**で決める。無ければ書かない。次はいずれも典型的なノイズである。

- **命名規約から導けるファイルパス。** モデル・サービス・フォームオブジェクト・リゾルバ・ジョブ・マイグレーション・ルーティングのパスは、クラス名や URL が分かれば決まる。**規約から外れる場所に置く場合だけ**、置き場所と理由を書く。逆に、命名から導けない新規フロントエンドコンポーネントのパスや、既存コードの所在は書く。
- **テーブル定義から導ける関連。** 外部キーのカラムを表に書いたなら、対応する `belongs_to` は書かない。`class_name` / `foreign_key` の明示や `dependent` の選択など、**規約から外れる指定・選択の余地がある指定だけ**を理由つきで書く。
- **名前の言い換え。** 「`belongs_to :plan`（対向モデルは `Plan`）」の括弧書きのように、関連名・クラス名・カラム名を言い換えただけの補足は書かない。
- **存在しないものの不在宣言。** 「コールバックとスコープは定義しない」「独自スコープは無い」のような、無いことの表明は書かない。あるものだけを書く。
- **標準的な実装手段の宣言。** 「フォームは `react-hook-form` を使う」「Apollo Client でデータ取得する」のような、プロジェクトで常にそうしているものは書かない。**そこから外れる場合だけ**、外す理由とともに書く。
- **規約どおりのエラー対応表。** 権限不足・リソース不在・バリデーション違反を操作ごとに並べた表は、規約を各操作へ機械的に当てはめただけなので書かない。**規約から外れる扱いや、ガードを入れないと別のエラーになる箇所だけ**を書く。
- **テーブルを写しただけの型定義。** 入出力型・レスポンス型のフィールド表が、既に示したテーブルのカラムや、他の型の入れ子を展開しただけなら書かない。**規約と違う指定（任意にした項目、null になる条件など）が設計判断である場合だけ**、その項目を1行で書く。
- **処理手順の書き下し。** 「1. 〜を1回のクエリで読む 2. 索引を作る 3. 〜で絞る」のような番号付きの手順は、実装を追体験させるだけで論点にならない。書くのは**その処理で何が決まるか（仕様）**と、**そう作らないと成立しない非自明な判断**だけ。手順が10段あっても、レビューで確認したいのは普通そのうち2〜3点である。
- **テストに関する記述。** どのクラスにどの spec を置くか、何を検証するか、品質ゲートで何を通すかは、設計の論点ではなく実装の手順である。**テスト方針・テストファイルの一覧・テスト観点は書かない**（必要なら `test-case-doc` で別文書にする）。テストで担保することを前提に置いた設計判断がある場合だけ、その判断のほうを書く。
- **変更しない既存の仕組みの説明。** 既存テーブル・既存 API・既存画面は、今回変更する箇所と、変更によって挙動が変わる箇所だけを書く。前提として触れるだけなら1行に収める。
- **章の指示を埋めるための空振り。** 後述の「各章に書く内容」は書ける項目の一覧であって、該当が無い項目まで「無し」と埋めさせる指示ではない（`該当なし` と書くのは**章**単位の場合のみ）。

## 出力する章構成

見出しは以下で固定する。章の追加・削除・改名をしない。該当する設計がない章は削除せず、`該当なし` と書いた上で理由を1行添える。

```markdown
# <機能名> 技術設計レビュー

## 技術設計

### テーブル・モデル設計

### API設計

### サービスクラス等の設計

### バッチ設計

### 画面・コンポーネント設計

## Appendix

### 要件の詳細
```

### 各章に書く内容

**テーブル・モデル設計**

- テーブルごとに、物理テーブル名・用途・新規か既存変更かを明記する。
- カラムは表で書く（物理カラム名 / 型 / NULL可否 / デフォルト値 / 一意制約・外部キー / 説明）。既存テーブルの変更は追加・変更・削除するカラムだけを、変更前と変更後がわかる形で書く。
- インデックス（対象カラムの並び順・一意かどうか）、外部キーと削除時の挙動を書く。
- enum は**全値**を、値と意味の対応で列挙する。
- モデルの独自バリデーション（自前の `validate :method` で実装するもの）は、検証内容とエラーメッセージの実文言を書く。Rails 標準のバリデーションで足りるものは、検証内容だけを1行で書く。
- 関連・コールバック・スコープは、**テーブル定義や Rails の規約から導けないものだけ**を理由つきで書く（`class_name` / `foreign_key` の明示、`dependent` にどれを選んだか、非自明なコールバックなど）。外部キーから自動的に決まる `belongs_to` は書かない（ルール3）。
- マイグレーションの有無と、付随作業（`just dip annotate`、`docker/embulk/bigquery.sh`、`docker/dump/mask.sql`、dbt モデルの更新）の要否が確定していれば書く。

**API設計**

- GraphQL は、Query か Mutation か・操作名・エンドポイント（`/in_vision_graphql` 等）を明記する。
- 引数と戻り値は、**そのフィールドの有無や型が設計判断である場合だけ**書く。テーブルのカラムをそのまま写した入出力型や、ネストした型を階層ごとに展開した表は書かない（ルール3）。「テーブルのカラムをそのまま写す」「既存 mutation と同じペイロード」の一言で足りる。
- ただし**新規に定義する enum の値**は、それ自体が仕様（何を判別できるか）なので全件書く。
- エラーは、**プロジェクトの規約どおりに決まるものを並べない**（権限不足なら 403、リソース不在なら 404、バリデーション違反なら 422、といった対応は規約を見れば分かる）。書くのは、規約から外れる扱いにしたもの、ガードを入れないと別のエラーになるもの、業務ルール上そのエラーを返すこと自体が判断であるものだけ。
- 認証・認可の条件（誰が呼べるか、どの条件で拒否されるか）を書く。
- 既存 API を変更する場合は、破壊的変更の有無と既存の呼び出し元への影響を書く。
- REST の場合は、メソッド・パス・リクエストボディ・レスポンスボディ・ステータスコードを書く。

**サービスクラス等の設計**

- クラス・モジュールごとに、名前と責務を書く。呼び出し元は、複数から呼ばれて結果を揃える必要があるなど、それ自体が設計上の意図である場合に書く。
- そのクラスが**何を決めるか**を書く（スコアの決まり方、表示条件、並び順など、仕様として確認したいこと）。**処理を段階的に追う書き方はしない**（ルール3）。
- 引数や戻り値は、呼び分けによって挙動が変わる場合だけ書く。
- 副作用は、**あるかないかと、あるなら何に書き込むか**を1行で書く。無い場合に「無い」と列挙しない。
- 例外は、規約から外れる扱いや、握りつぶしてフォールバックする箇所だけ書く。
- フォームオブジェクト、バリデータ、コールバッククラス、ジョブクラスもこの章に含める。
- **spec の配置・検証内容は書かない**（ルール3）。

**バッチ設計**

- クラス名、繰り返し実行かワンショットか、実行契機（cron / 手動 / ジョブから）を書く。
- **何を対象に何をするか**を書く。処理を手順として追わない（ルール3）。
- 冪等性・途中失敗時の挙動は、**再実行が安全でない場合や、失敗すると手当てが要る場合だけ**書く。
- 対象件数の見積もりと想定実行時間は、実行時間が問題になりうる規模のときだけ書く。

**画面・コンポーネント設計**

- 対象アプリ（`in-vision` / `pfc` / `pfu-web` / `pfu-mobile` など）と、画面の URL・ルーティングのファイルパスを書く。
- 画面の構成要素を、上から順に、レビュアーが画面を想像できる粒度で書く。
- 新規作成するコンポーネントは、コンポーネント名・ファイルパス・責務・受け取る props を書く。再利用する既存コンポーネントは名前とパスを書く。
- データ取得方法（GraphQL の操作名、Apollo Client か SSR か）、フォームの実装方法、状態の持ち方を書く。
- ユーザー操作と、その結果の画面遷移・表示変化を書く。
- 表示の分岐条件（権限による出し分け、空状態、ローディング、エラー表示）を全件書く。
- 入力バリデーションは、条件とエラーメッセージの実文言を書く。

**Appendix > 要件の詳細**

- 要件定義書の確定した要件と受け入れ条件を、**内容を読み下せる形**で転記する。ID の一覧表にしない。
- 背景・解決したい課題を、確定している範囲で書く。
- スコープ外として確定しているものを明記する（レビューでの論点ずれを防ぐため）。

## 自律実行の原則

1. **入力を自動探索する。** 明示された文書を優先する。未指定ならリポジトリ内の `*.spec.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。同じベース名の `*.requirement.md` / `*.task.md` は自動で併読する。
2. **コードで裏取りする。** 文書に書かれたファイルパス・テーブル名・カラム名・クラス名・メソッド名・URL は、書き写す前に実在を確認する。実在しないものは書かない。
3. **設計を追加・変更しない。** 文書に書かれていない設計判断を補わない。書かれていない箇所は空欄にせず、その項目自体を落として出力サマリで報告する。
4. **質問はブロッカーだけに限定する。** 主入力の文書を特定できない場合や、確定事実がほとんど残らずレビュー文書として成立しない場合だけ確認する。それ以外は除外して継続する。
5. **既存ファイルがあれば更新する。** レビュアーの追記コメントがあれば保持しつつ、入力文書とコードの差分を反映する。

## 実行フロー

### Phase 1: 入力の特定と収集

- 主入力の設計書を特定し、同じベース名の関連文書を収集する。
- 実装済みかどうかを判定する（対象ブランチの差分、設計書に書かれたファイルの実在）。実装済みならコードを事実の一次ソースにする。
- 出力先パスを決める（`.spec.md` → `.review.md`）。

### Phase 2: 事実の抽出と裏取り

- 入力文書から、章構成に対応する記述を抽出する。
- 抽出した記述のうち、ファイルパス・テーブル名・カラム名・enum 値・クラス名・メソッド名・GraphQL 操作名・エラークラス・URL を、コードまたは `gh` で実在確認する。
- 確認できたものだけを事実として採用する。確認できなかったものは、その項目ごと落として除外リストへ入れる。

### Phase 3: 確定・未確定の仕分け

- 抽出した記述を「確定」「未確定」に仕分ける。次のいずれかに当たるものは未確定として除外する。
  - 入力文書で `未決事項` / `仕様上の確認事項` / `リスク` / `検討した代替案` に置かれている
  - `TBD` / `未定` / `要検討` / `暫定` / `仮` / 疑問符つきで書かれている
  - 複数案が併記され、採用案が明記されていない
  - コードにも文書の確定記述にも根拠がない
- 除外したものを「未確定のため除外した項目」としてリスト化する（出力サマリ用。文書には書かない）。

### Phase 4: レビュー文書の作成

- 固定の章構成で作成する。該当なしの章は `該当なし` と理由を書く。
- 記述ルール1・2・3 を守って書き下す。特に、表のセルでの「同上」と条件のラベル参照（ルール2違反）、規約から導けるファイルパスと関連の書き下し（ルール3違反）が混入しやすいので、書きながら潰す。

### Phase 5: レビューサイクル

作成後、次のサイクルを収束するまで回してから完了とする。

1. **文書をレビューする。** 新鮮な目で（可能なら同期実行のレビュー用サブエージェントで。非同期起動して待ち合わせない）レビューする。観点:
   - **省略記法の混入。** `C1` のようなラベル単独参照、「同上」「〃」「等」「など」「（略）」「...」、ID 単独参照、「詳細は設計書を参照」が残っていないか。
   - **未確定の混入。** 「〜と思われる」「〜する想定」「要検討」「TBD」「必要に応じて」「将来的に」などの表現、および検討経緯（どう迷ったか・何を比較したか）が残っていないか。判断が分かれる選択の**採用理由**は残してよい。
   - **自明な記述の混入。** 命名規約から導けるファイルパス、外部キーから導ける `belongs_to`、名前を言い換えただけの括弧書き、「〜は定義しない」という不在宣言が残っていないか。
   - **実在性。** 記載した全てのファイルパス・テーブル名・カラム名・クラス名・メソッド名・URL・チケット番号が実在するか。
   - **列挙の完全性。** 書くと決めた列挙（新規 enum の値、権限による表示の出し分けなど）が全件書かれているか。規約から機械的に決まる列挙まで書いていないか。
   - **論点の埋没。** レビューで確認すべき判断が、ノイズに埋もれていないか。逆に、確認したい論点が落ちていないか。
   - **ノイズの混入。** 「普通こうなるよね」で済む記述、変更しない既存の仕組みの説明、標準的な実装手段の宣言が残っていないか。
   - **章構成の遵守。** 見出しが固定どおりか、該当なしの章が削除されていないか。
2. **各指摘を入力文書・実コードと突き合わせる。** 指摘を鵜呑みにしない。設計の中身を変える指摘は不採用とし、前工程へ差し戻すべき事項として出力サマリで報告する。
3. **採用した指摘を修正し、完了条件を再検証する。**
4. **収束条件:** 採用すべき指摘が出なくなるまで繰り返す（上限3サイクル）。

## 完了条件

- [ ] 章構成が固定どおりで、該当なしの章も理由つきで残っている
- [ ] 未確定・推測・提案・検討経緯が本文に1つも残っていない（判断が分かれる選択の採用理由は除く）
- [ ] ラベル単独参照（`C1` 等）、「同上」「〃」「等」「など」「（略）」、ID 単独参照が1つも残っていない
- [ ] 規約から導けるファイルパス・関連、名前の言い換え、不在宣言、変更しない既存の仕組みの説明が1つも残っていない
- [ ] 新規に定義する enum の値・権限による表示の出し分けなど、書くと決めた列挙が全件書かれている
- [ ] 記載した全てのファイルパス・識別子・URL・チケット番号の実在を確認した
- [ ] 「普通こうなるよね」で済む記述が1つも残っていない
- [ ] レビュアーが確認すべき論点を、この1枚で判断できる
- [ ] レビューサイクルが収束している（最終サイクルで採用すべき指摘がない）

## 出力サマリ

完了後に報告する内容は次の4つに限る。

1. 作成・更新したファイルパス
2. **未確定のため除外した項目**（内容 / どの入力文書のどのセクションにあったか）。レビュー前に確定させるべきものとして明示する
3. **裏取りできず除外した項目**（文書には書かれていたが、実在確認できなかったファイル・識別子・URL）
4. 入力文書と実コードの食い違い（実コードを事実として書いた箇所）

安全に推定した事項について確認を求めない。
