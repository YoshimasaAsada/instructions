# Design Review Doc

作成済みの要件・設計・テスト文書を、**単体で読み切れる社内レビュー用文書**へ整形する。

- **入力:** `*.spec.md` を主入力とし、同じベース名の `*.requirement.md` / `*.task.md` / `*.testcase.md` があれば併読する。実装済みなら対象コードも読む
- **出力:** 入力と同じベース名の `*.review.md`（原則として入力文書と同じディレクトリ）
- **責務:** 確定した事実だけを抽出し、決められた章構成へ、省略なしで書き下す
- **責務外:** 新しい設計判断、要件の追加・変更、テストケースの新規導出、コード実装
- **関連:** 前工程は `design-doc` / `task-breakdown` / `test-case-doc`。設計の中身を変える必要が出たら、このスキルで直さず前工程へ差し戻す

## この文書が満たすべき前提

レビュー文書は**入力文書を持たないレビュアーに、これ1枚だけを見せる**。したがって次の2つが最優先の制約になり、他のすべての判断に優先する。

1. **確定した事実だけを書く**（未確定・推測・提案を混ぜない）
2. **省略記法を使わない**（記号・ID・「同上」で内容を代替しない）

以下の「記述ルール」はこの2点の具体化であり、章構成や網羅性より優先して守る。

## 記述ルール

### ルール1: 確定した事実だけを書く

- **事実の出典は次の2つだけ。** (a) 実装済みのコード、(b) 入力文書のうち確定として記述された内容（`前提・採用した既定案` を含む確定事項）。この2つに根拠がない記述は書かない。
- **実装済みならコードを正とする。** 文書とコードが食い違う場合はコードを事実として書き、食い違いの内容を出力サマリで報告する。文書側の記述をレビュー文書に残さない。
- **未実装ならコードで裏取りできる範囲だけ裏取りする。** 変更対象の既存テーブル・既存クラス・既存画面の現状はコードで確認し、実在するファイルパス・カラム名・メソッド名だけを書く。
- **未確定のものは本文へ一切書かない。** 入力文書の `未決事項` / `仕様上の確認事項` / `TBD` / `要検討` / `未定` / `暫定` / `仮` とマークされた内容、および複数案が併記されたまま決まっていない内容は、レビュー文書から**除外**する。Appendix にも書かない。
- **除外したものは出力サマリで警告する。** 「未確定のため除外した項目」として、何を落としたか・どの文書のどのセクションにあるかを列挙し、レビュー前に確定させるべきものとして報告する。
- **禁止表現。** 「〜と思われる」「〜のはず」「〜する想定」「〜を検討中」「〜すべき」「必要に応じて」「将来的に」「〜かもしれない」。これらを書きたくなった時点で、それは確定事実ではないので除外対象。
- **代替案・却下案・検討経緯は書かない。** レビュー対象は確定した設計のみ。

### ルール2: 省略記法を使わない

- **ラベル単独参照の禁止。** `C1` `パターンA` `ケース①` `条件2` のような記号でケース・条件・パターンを指し示さない。参照するたびに条件の中身を書き下す（「C1 の場合」ではなく「求職者が退会済みの場合」）。デシジョンテーブルを転記する場合も、条件列にラベルではなく条件文そのものを入れる。
- **反復省略の禁止。** 「同上」「同左」「〃」「上記と同様」「以下同様」「（略）」「...」「〜等」「〜など」を使わない。表のセルであっても毎回フルで書く。冗長になっても書き下す。
- **列挙の打ち切り禁止。** enum の値、バリデーションエラーの種類、権限ロール、画面の表示条件は全件を列挙する。件数が多い場合も省略せず、全部書く。
- **ID を主語にしない。** `REQ-001` `TASK-003` `TC-012` のような識別子は、それ単体では内容が読めない。本文では内容を書き、ID は必要なら内容の後ろに括弧で添えるだけにする。ID だけの対応表を作らない。
- **略語・社内用語は初出で展開する。** 展開したうえで Appendix の用語集にも載せる。定義を裏取りできない用語は、本文でも使わず一般的な表現に置き換える。
- **入力文書へのリンクで内容を代替しない。** 「詳細は設計書を参照」と書かない。レビュアーは入力文書を持っていない。

## 出力する章構成

見出しは以下で固定する。章の追加・削除・改名をしない。該当する設計がない章は削除せず、`該当なし` と書いた上で理由を1行添える。

```markdown
# <機能名> 技術設計レビュー

## 技術設計

### テーブル・モデル設計

### API設計

### サービスクラス等の設計

### バッチ設計

### 画面・コンポーネント設計

## 動作テスト項目

## Appendix

### 要件の詳細

### 参考資料

### 用語集

### 関連するリンクやチケット
```

### 各章に書く内容

**テーブル・モデル設計**

- テーブルごとに、物理テーブル名・用途・新規か既存変更かを明記する。
- カラムは表で書く（物理カラム名 / 型 / NULL可否 / デフォルト値 / 一意制約・外部キー / 説明）。既存テーブルの変更は追加・変更・削除するカラムだけを、変更前と変更後がわかる形で書く。
- インデックス（対象カラムの並び順・一意かどうか）、外部キーと削除時の挙動を書く。
- enum は**全値**を、値と意味の対応で列挙する。
- モデルのリレーション（`has_many` / `belongs_to` などの関連名と対向モデル）、独自バリデーション、コールバック、スコープを書く。
- マイグレーションの有無と、付随作業（`just dip annotate`、`docker/embulk/bigquery.sh`、`docker/dump/mask.sql`、dbt モデルの更新）の要否が確定していれば書く。

**API設計**

- GraphQL は、Query か Mutation か・操作名・エンドポイント（`/in_vision_graphql` 等）を明記する。
- 引数は表で書く（引数名 / 型 / 必須かどうか / 説明）。戻り値も型と全フィールドを書く。
- エラーは、発生条件・使用する例外クラス・対応する HTTP ステータスの対応を全件書く。
- 認証・認可の条件（誰が呼べるか、どの条件で拒否されるか）を書く。
- 既存 API を変更する場合は、破壊的変更の有無と既存の呼び出し元への影響を書く。
- REST の場合は、メソッド・パス・リクエストボディ・レスポンスボディ・ステータスコードを書く。

**サービスクラス等の設計**

- クラス・モジュールごとに、名前とファイルパス・責務・呼び出し元を書く。
- 公開メソッドは、シグネチャ（引数と戻り値）と処理内容を書く。
- 副作用（DB の更新対象、外部 API 呼び出し、非同期ジョブの enqueue、メール・通知の送信、Elasticsearch の再インデックス）を全て書く。
- 発生させる例外と、その条件を書く。
- フォームオブジェクト、バリデータ、コールバッククラス、ジョブクラスもこの章に含める。

**バッチ設計**

- クラス名とファイルパス、繰り返し実行かワンショットかを書く。
- 実行契機（cron の設定・手動実行・ジョブからの呼び出し）と実行頻度を書く。
- 処理対象レコードの抽出条件を、SQL 相当の条件がわかる粒度で書く。
- 処理内容を手順として書き、冪等性（再実行しても安全か）と、途中失敗時の挙動を書く。
- 対象件数の見積もりと想定実行時間が確定していれば書く。

**画面・コンポーネント設計**

- 対象アプリ（`in-vision` / `pfc` / `pfu-web` / `pfu-mobile` など）と、画面の URL・ルーティングのファイルパスを書く。
- 画面の構成要素を、上から順に、レビュアーが画面を想像できる粒度で書く。
- 新規作成するコンポーネントは、コンポーネント名・ファイルパス・責務・受け取る props を書く。再利用する既存コンポーネントは名前とパスを書く。
- データ取得方法（GraphQL の操作名、Apollo Client か SSR か）、フォームの実装方法、状態の持ち方を書く。
- ユーザー操作と、その結果の画面遷移・表示変化を書く。
- 表示の分岐条件（権限による出し分け、空状態、ローディング、エラー表示）を全件書く。
- 入力バリデーションは、条件とエラーメッセージの実文言を書く。

**動作テスト項目**

- レビュアーが「この項目で仕様を確認できるか」を判断できる粒度で書く。表形式にする。

  ```markdown
  | No | 前提条件 | 操作手順 | 期待結果 |
  | --- | --- | --- | --- |
  | 1 | <ロール・データの状態を具体的に> | <画面操作または実行コマンド> | <観測できる結果> |
  ```

- 期待結果は観測可能な形で書く（「正しく保存される」ではなく「一覧の先頭に表示され、DB の `status` が `active` になる」）。
- 条件の組合せは、組合せごとに1行として全て書き下す。ラベルでまとめない。
- 正常系だけでなく、権限不足・入力不正・対象不存在・重複操作・空状態を、確定している範囲で全て項目化する。
- 入力に `*.testcase.md` がある場合は、そこから確定済みのケースを転記する。**新しいテストケースをこのスキルで導出しない。** 転記元がない場合は、設計上その挙動が確定しているものだけを項目にする。

**Appendix > 要件の詳細**

- 要件定義書の確定した要件と受け入れ条件を、**内容を読み下せる形**で転記する。ID の一覧表にしない。
- 背景・解決したい課題を、確定している範囲で書く。
- スコープ外として確定しているものを明記する（レビューでの論点ずれを防ぐため）。

**Appendix > 参考資料**

- 参考にした既存実装を、ファイルパスと「何を参考にしたか」の対で書く。
- 準拠したコーディング規約を、出典（ファイルパスとセクション名）つきで書く。
- 参照した外部ドキュメント（`docs/` 配下の仕様書など）をパスつきで書く。

**Appendix > 用語集**

- 本文で使った社内用語・ドメイン用語・略語を**全て**、用語と定義の対で書く。
- 定義は実コードまたは既存文書で裏取りする。裏取りできない用語は載せず、本文側の表現を裏取り可能な言い方へ置き換える。

**Appendix > 関連するリンクやチケット**

- GitHub の issue・PR は `gh` コマンドで実在とタイトルを確認してから、番号・タイトル・URL を書く。
- 元になった要件定義書・設計書・タスクリスト・テストケースのファイルパスを書く。
- Figma・Slack スレッド・外部チケットは、URL が会話または入力文書に実在するものだけを書く。**URL を推測で組み立てない。**

## 自律実行の原則

1. **入力を自動探索する。** 明示された文書を優先する。未指定ならリポジトリ内の `*.spec.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。同じベース名の `*.requirement.md` / `*.task.md` / `*.testcase.md` は自動で併読する。
2. **コードで裏取りする。** 文書に書かれたファイルパス・テーブル名・カラム名・クラス名・メソッド名・URL は、書き写す前に実在を確認する。実在しないものは書かない。
3. **設計を追加・変更しない。** 文書に書かれていない設計判断を補わない。書かれていない箇所は空欄にせず、その項目自体を落として出力サマリで報告する。
4. **質問はブロッカーだけに限定する。** 主入力の文書を特定できない場合や、確定事実がほとんど残らずレビュー文書として成立しない場合だけ確認する。それ以外は除外して継続する。
5. **既存ファイルがあれば更新する。** レビュアーの追記コメントがあれば保持しつつ、入力文書とコードの差分を反映する。

## 実行フロー

### Phase 1: 入力の特定と収集

- 主入力の設計書を特定し、同じベース名の関連文書を収集する。
- 実装済みかどうかを判定する（対象ブランチの差分、設計書に書かれたファイルの実在）。実装済みならコードを事実の一次ソースにする。
- 出力先パスを決める（`.spec.md` → `.review.md`）。

### Phase 2: 事実の抽出と裏取り

- 入力文書から、章構成に対応する記述を抽出する。
- 抽出した記述のうち、ファイルパス・テーブル名・カラム名・enum 値・クラス名・メソッド名・GraphQL 操作名・エラークラス・URL を、コードまたは `gh` で実在確認する。
- 確認できたものだけを事実として採用する。確認できなかったものは、その項目ごと落として除外リストへ入れる。

### Phase 3: 確定・未確定の仕分け

- 抽出した記述を「確定」「未確定」に仕分ける。次のいずれかに当たるものは未確定として除外する。
  - 入力文書で `未決事項` / `仕様上の確認事項` / `リスク` / `検討した代替案` に置かれている
  - `TBD` / `未定` / `要検討` / `暫定` / `仮` / 疑問符つきで書かれている
  - 複数案が併記され、採用案が明記されていない
  - コードにも文書の確定記述にも根拠がない
- 除外したものを「未確定のため除外した項目」としてリスト化する（出力サマリ用。文書には書かない）。

### Phase 4: レビュー文書の作成

- 固定の章構成で作成する。該当なしの章は `該当なし` と理由を書く。
- 記述ルール1・2 を守って書き下す。特に、表のセルでの「同上」と、条件のラベル参照が混入しやすいので、書きながら潰す。
- 用語集は本文を書き終えてから、本文をなめて拾い上げる（先に作ると漏れる）。

### Phase 5: レビューサイクル

作成後、次のサイクルを収束するまで回してから完了とする。

1. **文書をレビューする。** 新鮮な目で（可能なら同期実行のレビュー用サブエージェントで。非同期起動して待ち合わせない）レビューする。観点:
   - **省略記法の混入。** `C1` のようなラベル単独参照、「同上」「〃」「等」「など」「（略）」「...」、ID 単独参照、「詳細は設計書を参照」が残っていないか。
   - **未確定の混入。** 「〜と思われる」「〜する想定」「要検討」「TBD」「必要に応じて」「将来的に」などの表現、および代替案・検討経緯が残っていないか。
   - **実在性。** 記載した全てのファイルパス・テーブル名・カラム名・クラス名・メソッド名・URL・チケット番号が実在するか。
   - **列挙の完全性。** enum 値・エラー種別・権限ロール・表示条件が全件書かれているか。
   - **自己完結性。** 入力文書を持たないレビュアーが、この1枚だけで設計を理解し、動作テスト項目を実行できるか。
   - **章構成の遵守。** 見出しが固定どおりか、該当なしの章が削除されていないか。
2. **各指摘を入力文書・実コードと突き合わせる。** 指摘を鵜呑みにしない。設計の中身を変える指摘は不採用とし、前工程へ差し戻すべき事項として出力サマリで報告する。
3. **採用した指摘を修正し、完了条件を再検証する。**
4. **収束条件:** 採用すべき指摘が出なくなるまで繰り返す（上限3サイクル）。

## 完了条件

- [ ] 章構成が固定どおりで、該当なしの章も理由つきで残っている
- [ ] 未確定・推測・提案・代替案・検討経緯が本文に1つも残っていない
- [ ] ラベル単独参照（`C1` 等）、「同上」「〃」「等」「など」「（略）」、ID 単独参照が1つも残っていない
- [ ] enum 値・エラー種別・権限ロール・表示条件が全件列挙されている
- [ ] 記載した全てのファイルパス・識別子・URL・チケット番号の実在を確認した
- [ ] 動作テスト項目の期待結果が全て観測可能な形で書かれている
- [ ] 本文に出てくる社内用語・略語が全て用語集に載っている
- [ ] 入力文書を持たないレビュアーが、この1枚だけで理解できる
- [ ] レビューサイクルが収束している（最終サイクルで採用すべき指摘がない）

## 出力サマリ

完了後に報告する内容は次の4つに限る。

1. 作成・更新したファイルパス
2. **未確定のため除外した項目**（内容 / どの入力文書のどのセクションにあったか）。レビュー前に確定させるべきものとして明示する
3. **裏取りできず除外した項目**（文書には書かれていたが、実在確認できなかったファイル・識別子・URL）
4. 入力文書と実コードの食い違い（実コードを事実として書いた箇所）

安全に推定した事項について確認を求めない。
