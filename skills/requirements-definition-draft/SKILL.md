# Requirements Definition Draft

Slack、チャット、口頭メモ、雑な依頼文、ビジネス要望から、開発に渡せる要件整理メモを作成する。

- **目的:** 曖昧な依頼を、背景・目的・スコープ・要件・受け入れ条件・確認事項に分解する
- **入力:** 依頼文、背景、制約、参考資料、URL、既存ドキュメント
- **基本出力:** 要件整理メモを Markdown ファイルとして保存し、会話内にも整理結果を返す
- **ファイル出力:** 常に Markdown ファイルとして保存する（保存先・ファイル名は Phase 3 を参照）
- **正式文書化:** ユーザーが正式な `requirement.md` 作成を求めた場合は `requirements-definition` に引き継ぐ

---

## 基本方針

情報が不足していても、作業を止めずに Draft として整理する（壁打ちモードを除く）。
未確定の情報は、推測で埋めたうえで `前提・仮説` と `確認事項` に分けて明示する。

ただし、以下のいずれかが不明で要件の方向性が大きく変わる場合のみ、最初に最大3問まで質問する。

1. 対象システムまたは対象ユーザーが特定できない
2. やることとやらないことの境界が決められない
3. 成果物の形式が大きく変わる可能性がある

質問は番号付きの固定フォーマットで出し、推奨案（仮説・選択肢）を必ず添える。ユーザーが番号だけで回答できるようにする:

```
❓ **Q1** — **<論点>**: <本文。選択肢があれば併記>
➡️ <推奨案>
```

**事実の調査はエージェントの仕事、意思決定はユーザーの仕事。** コード・環境・添付資料・URLを調べれば分かることは質問せず自分で調べる。

---

## モード

### 1. 要件整理メモモード（デフォルト）

ユーザーが「この要件を整理して」「Slackの依頼をまとめて」などと言った場合のデフォルト。
質問を最小限に抑えて自走し、**整理結果を Markdown ファイルとして保存し**、あわせて会話内にも整理結果を返す。
保存先・ファイル名は Phase 3 を参照する。

### 2. 整理メモ保存モード

ユーザーが「この整理をファイルにして」「整理メモとして保存して」などと言った場合も同様に、
整理結果を Markdown ファイルに保存する（正式な要件定義書ではない）。

### 3. 壁打ちモード

ユーザーが「壁打ちしたい」「相談しながら決めたい」「質問しながら詰めて」などと言った場合。
仮説で埋めて自走せず、ラウンド制のインタビューで要件を固める。

- 要件を**決定の木**として捉える。各決定の下に、その決定に依存する決定がぶら下がる。
- **フロンティア**（前提となる決定がすべて確定していて、今答えを聞ける質問の集合）を、1ラウンドにまとめて全部出す。回答が同ラウンド内の別の質問に依存する質問は、このラウンドに入れず次のラウンドに回す。質問数の上限は設けない。
- 各質問は基本方針の `❓ / ➡️` フォーマットで番号付きで出す。
- 調べれば分かる事実は質問せず自分で（必要ならサブエージェントで）調べる。調査中の事実に依存する質問だけを待たせ、残りのフロンティアは先に聞く。
- ラウンドの回答を受けて決定の木を再計算し、次のフロンティアを出す。
- フロンティアが空になったら Phase 2 の形式で整理して提示し、**ユーザーが「認識が揃った」と確認してから**保存・次工程へ進む。勝手に requirements-definition へ進まない。

## 実行フロー

### Phase 0: 一次情報の取得（Source Grounding）★省略禁止

依頼文に Slack / Notion / スプレッドシート / Figma / GitHub のリンクが1つでもあれば、**整理を書き始める前に必ず実際にアクセスを試みる**。依頼文は要約であることが多く、目的・スコープ・期日・詳細仕様は一次情報側にしか無いのが普通。

**「アクセスできない」と結論してよいのは、実際にツールを叩いて失敗したときだけ。** セッション開始時のシステム通知（「この MCP は未認証」等）や「社内限定だから無理だろう」という推測で諦めない。次の順で試す。

1. **専用 MCP / CLI** — Slack のスレッド読み取り、`gh issue view` など。Slack の URL `…/archives/{channel_id}/p{17桁}` からは `channel_id` と `message_ts`（`p` を除き下6桁の前に小数点。`p1786319654495319` → `1786319654.495319`）を復元できる
2. **接続済みブラウザ（Claude in Chrome 等）** — 社内 Notion・スプレッドシート・Figma はここで読める。ユーザーのログイン済みセッションを使うため認証壁を越えられる
3. **WebFetch** — 公開ページのみ。認証が要る URL はログイン画面が返るだけなので、失敗しても「アクセス不可」の結論にしない

ツールが手元に無いように見えても、まず探す（MCP ツールは遅延ロードされていることがある）。全手段が失敗したときだけ、「どのリンクに・どの手段で・どう失敗したか」を明示してユーザーへ共有を依頼し、その前提で置いた推測は `前提・仮説` に記録する。

### Phase 1: 依頼文の分解

入力された依頼文から、以下を抽出する。

- 背景・課題
- 目的
- 想定ユーザー
- 依頼者・ステークホルダー
- 期待される成果物
- やること
- やらないこと
- 制約条件
- 期限・優先度
- 成功条件
- 未確定事項

明示されていない項目は `不明` では終わらせず、妥当な仮説を置ける場合は `前提・仮説` に記録する。

**参照画像・添付ファイルの記録（必須）:**
依頼に画像・スクリーンショット・添付ファイルが伴う場合（プロンプトにファイルパスが含まれる、IDE で画像を開いている、`Downloads` 等のパスが提示される 等）、
**その絶対パスを必ず整理メモに残す**。後から「どの画像を指していたか」を参照できるようにするため、整理メモ冒頭に `## 参照画像` 節（表形式: パス / 内容）を設け、各ファイルのパスと、画像から読み取った要点を1行で記録する。
画像の内容（UI構造・項目・データ等）は、該当する `機能要件` / `参照UI` 等の節にも展開する。

### Phase 2: 要件整理メモの作成

まず以下の形式で整理結果を会話内に返す。この内容はそのまま Phase 3 でファイルに保存する。

```markdown
# 要件整理メモ: {件名}

## 依頼の一言要約

（何をしたい依頼かを1〜2文で要約）

## 参照画像
（画像・添付がある場合のみ。無ければ節ごと省略）

| パス | 内容 |
|------|------|
| {絶対パス} | {画像から読み取った要点} |

## 背景・目的

- 背景:
- 解決したい課題:
- 達成したい目的:

## スコープ

### やること

- {今回対応すること}

### やらないこと

- {今回対応しないこと}

## 想定ユーザー・関係者

- エンドユーザー:
- 要件提供者:
- 実装・運用関係者:

## 機能要件

- **FR-001:** {実装可能な粒度の要件}（優先度: Must / Should / Nice to Have）

## 非機能要件

- パフォーマンス:
- セキュリティ:
- 信頼性・可用性:
- 運用性:

## 受け入れ条件

- **AC-001:** {検証可能な完了条件}

## 前提・仮説

- {明示されていないが、整理上置いた前提}

## 確認事項

- **Q-001:** {ユーザーまたはステークホルダーに確認すべきこと}

## 次アクション

1. {次にやること}
2. {次に確認すること}
```

### Phase 3: 整理メモの保存

**Phase 2 の整理結果は、毎回 Markdown ファイルとして保存する**（ユーザーからの明示的な依頼を待たない）。
ファイル名は `{topic}.requirements-notes.md` とし、英小文字 kebab-case を推奨する。
例: `user-onboarding.requirements-notes.md`

保存先はプロジェクトルートを既定とし、既存のドキュメント配置規約（`docs/` など）があればそれに従う。
保存内容は Phase 2 で会話に返した整理結果と同一でよい。より詳細にまとめ直す場合は、このスキルの `template-extended.md` の拡張テンプレートを使う。
正式な要件定義書として起こす場合は `requirements-definition` を使う。

## 妥当性チェック

提出前に以下を確認する。

- 依頼文に含まれる一次情報リンクすべてに実際にアクセスを試み、内容を反映した（取れなかったものはリンク・試した手段・失敗内容を明示した）
- 機能要件が実装可能な粒度に分かれている
- 受け入れ条件が検証可能である
- スコープ外が明示されている
- Must / Should / Nice to Have が区別されている
- 不明点が `確認事項` に集約されている
- 推測で補った内容が `前提・仮説` に明記されている
- 詳細設計や実装方法に踏み込みすぎていない

---

## 出力サマリ

毎回ファイルを作成するので、最後に以下を簡潔に伝える。

- 作成したファイルのパス
- 要件の要約
- 主要な未確定事項
- 次に進めるべき作業

整理メモには `確認事項` と `次アクション` を必ず含める。
