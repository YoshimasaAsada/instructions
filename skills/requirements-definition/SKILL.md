# Requirements Definition

整理済みのビジネス要件や合意済みの要件メモから、設計・実装・レビューの基準となる正式な要件定義書を作成する。

- **目的:** 要件を「設計に進める状態」まで構造化する
- **入力:** 整理済みのビジネス要件・要件メモ・背景・制約・参考資料
- **出力:** `{機能名}.requirement.md`（ひな形はこのスキルの `template.md`）

> 雑な依頼をまず壁打ちする段階なら `requirements-definition-draft` を使う。

---

## コア原則（これが品質を決める）

1. **一次情報は自分で取りに行く。「アクセスできない」と書いてよいのは、実際にツールを叩いて失敗したときだけ。** 依頼に Slack / Notion / スプレッドシート等のリンクがあれば、Phase 0-A で必ず実際にアクセスを試みる。セッション開始時のシステム通知（「この MCP は未認証」等）や「社内限定だから無理だろう」という推測で諦めない。一次情報を取らずに書いた要件は、目的・スコープ・期日・受け入れ条件がすべて推定になり、後から全面書き直しになる。
2. **推測で書かない。コードで裏取りする。** 要件を書く前に必ず Phase 0 で関連コードを調査する。「現状どう動いているか」「既存基盤は何か」「**要件を覆す制約はないか**」を事実で確認してから書く。机上で書いた要件は、設計着手時に前提が崩れて手戻りする。
3. **確認事項は「既定案つき」で列挙する。** 判断が割れる点は、`論点 / なぜ確認が必要か / 想定デフォルト案` の3点セットで出す。これがユーザーの意思決定を最速にする。会話上で確認する場合は番号付きの固定フォーマットで出し、ユーザーが「1はい、2はB案」のように番号だけで回答できるようにする:

   ```
   ❓ **Q1** — **<論点>**: <本文。選択肢があれば併記>
   ➡️ <想定デフォルト案>
   ```

   また、**事実の調査はエージェントの仕事、意思決定はユーザーの仕事**。コード・環境・ドキュメントを調べれば分かることをユーザーに質問しない。
4. **前提が崩れたら設計に進まず、エスカレーションする。** 調査で要件の前提を覆す制約（暗号化・権限境界・スケール上限など）が出たら、勝手に方針を決めず、達成マトリクスや選択肢を提示して判断を仰ぐ。
5. **ユーザーの方針キーワードを軸にする。** 「minimum」「UX優先」「スケール最優先」等のスタンスを冒頭に記録し、全判断に一貫適用する。
6. **要件定義は「何を」。設計の「どう」には踏み込みすぎない。** ただし実現可能性の裏取りに必要な範囲では具体に立ち入ってよい。

## 事前確認事項（未確定なら先に聞く）

1. **機能名** — ファイル名のプレフィックスになる
2. **対象システム / 対象画面・API** — Phase 0 の調査範囲を決める
3. **ステークホルダー** — 要件提供者は誰か
4. **優先度 / スコープ** — MVP か Full Feature か
5. **方針キーワード** — minimum / UX優先 / スケール優先 など、判断の軸

## 実行フロー

### Phase 0-A: 一次情報の取得（Source Grounding）★省略禁止

依頼（issue 本文・チケット・チャット）に**一次情報へのリンクが1つでもあれば、要件を書く前に必ず実際にアクセスを試みる**。issue 本文は要約であることが多く、目的・スコープ・期日・受け入れ条件・デザインの所在は一次情報側にしか無いことが普通。

**取得手段は次の順で試す。1つ失敗しても次を試す:**

| # | 手段 | 使いどころ・コツ |
|---|------|-----------------|
| 1 | 専用 MCP / CLI | Slack はスレッド読み取りツール。URL `…/archives/{channel_id}/p{17桁}` から `channel_id` と、`p` を除いて下6桁の前に小数点を打った `message_ts` を復元する（例: `p1786319654495319` → `1786319654.495319`）。GitHub は `gh issue view` / `gh pr view` |
| 2 | 接続済みブラウザ（Claude in Chrome 等） | **社内 Notion・スプレッドシート・Figma はここで読める。**ユーザーのログイン済みセッションを使うため、認証壁を越えられる。ページを開いてテキスト抽出する |
| 3 | WebFetch | 公開ページのみ。認証が要る URL ではログイン画面が返るだけなので、これが失敗しても「アクセス不可」の結論にはしない |

**ツールが手元に無いように見えても、まず探す。** MCP ツールは遅延ロードされていることがあり、ツール検索で名前を引けば使えるようになる場合がある。「未認証」というシステム通知が出ていても、実際に叩くと通ることがある。

**全手段が失敗したときだけ**、「どのリンクに・どの手段で・どう失敗したか」を明示してユーザーへ共有を依頼する。その状態で書いた要件定義書には、**推定を含む箇所を本文に明記**する（背景・目的・成功指標など）。

取得できた一次情報からは、少なくとも次を抽出して要件定義書へ反映する: 依頼者 / 受益部門 / 目的・期待効果 / 期日・優先度 / スコープの明示（対象・対象外）/ ブロック単位や項目単位の詳細仕様 / 添付デザイン・アセットの所在と提供状況。

### Phase 0: 裏取り調査（Feasibility Grounding）★最重要・省略禁止

要件を書く前に、対象機能の関連コードを調査して現状と制約を事実で把握する。範囲が広ければ**並列調査（サブエージェント/Task）を活用**し、結論だけ集約する。

**(a) 現状把握:** 対象画面・API・サービス・スキーマ・データモデルを読み、「今どうデータを取得・加工・表示しているか」を1段落で要約できるようにする。あわせて、対象が画面やAPIなら、開発環境ですぐ動作確認できるURL（プロジェクトの起動方法・ルーティング規約から特定できるパス）を控える。バッチ処理やスキーマのみの変更など、画面・APIが存在しない場合は無理に作らない。

**(b) 既存基盤の棚卸し:** 再利用できる仕組み（ページネーション基盤・共通フック・共通コンポーネント・既存の類似実装）があるか。新規導入する技術が既に使われているか（ゼロからか）。

**(c) 要件を覆す制約の能動的探索 ←今回の肝。次を必ずチェック:**
- **データの暗号化:** 検索/ソート/集計対象の列がアプリケーション側で暗号化（フィールド暗号化ライブラリ等）されていないか。されていれば DB 側で `contains`/`ORDER BY`/集計ができず、全件メモリ処理が必須になる。
- **権限・認可境界:** ロール別の context/procedure、テナント分離など。「この操作はこのロールでは不可」がないか。
- **外部依存・非同期:** 外部API・キュー・トランスコード等のレート制限/結果遅延/失敗時挙動。
- **スケール上限:** ページング上限（1リクエストの最大取得件数の定数等）、N+1、深い `include`、全件取得前提の周辺機能。
- **既存の暗黙仕様:** 現状コードが「ある制約ゆえに」今の実装になっていないか（現状実装は仕様のヒント。例: 全件メモリ処理は暗号化が理由だった）。
- **後方互換:** 出力型・API契約を変えると波及する参照箇所。
- **データ整合性/トランザクション境界:** 原子性が要る操作か。
- **プロジェクト規約:** `AGENTS.md`/`CLAUDE.md` 等の品質ゲート・コーディング規約・テスト基準（→ 制約条件に取り込む）。

**(d) 制約が要件の前提を覆す場合:** 設計に進まず、`重大制約` セクションと「実現オプション × 達成したい価値」の達成マトリクスを用意し、ユーザーに優先順位を確認する（コア原則4）。

### Phase 1: 要件ヒアリング・整理

Phase 0 の事実をもとに、背景・課題 / ビジネス価値 / エンドユーザー / ユースケース / 成功指標 / 既知制約 / 参考実装 を整理する。不明点は確認事項の候補として控える。

### Phase 2: 要件定義書の作成

**ファイル名:** `{機能名}.requirement.md`（プロジェクトルート or ドキュメント管理ディレクトリ）
**ひな形:** このスキルの `template.md` をベースに、状況に応じてセクションを増減する。

**必須セクション:** 概要 / 背景・目的 / スコープ（対象・スコープ外・MVP vs Full）/ ステークホルダー / ユースケース（表）/ 機能要件（FR表・優先度）/ 非機能要件 / 制約条件 / **確認事項（既定案つき）** / 参考資料（**Phase 0-A の一次情報URL** と、調査で読んだ実ファイルを列挙）。

**状況に応じて足す:**
- **動作確認URL:** 対象が画面・APIで、開発環境のURLを特定できた場合は1セクション設ける（`template.md` の「動作確認」節）。バッチ・スキーマのみの変更など該当URLがない場合はこの節ごと省略する。
- **エラー / 失敗時挙動:** 失敗・リトライ・部分失敗・オフラインの挙動が論点なら必ず1セクション。
- **テストでの担保方針:** リファクタや移行を含むなら「差異を何でどう担保するか（characterization test 等）」を明記。
- **重大制約と実現オプション:** Phase 0(d) に該当する場合、達成マトリクスつきで。

**書き方のルール:**
- 機能要件は `FR-001` 形式・実装可能な粒度・`Must/Should/Nice to Have`。
- 曖昧語（「〜くらい」「〜など」「多くの場合」）を排し、検証可能な形で書く（「使いやすい」→「3クリックで完結」）。
- 非機能要件は可能な限り定量化。
- 確認事項は表で `論点 / なぜ確認が必要か / 想定デフォルト案`。

### Phase 3: レビューサイクル → 回答反映ループ

**(a) レビューサイクル（提出前に収束するまで回す）:**

`doc-review-cycle` スキルを起動し、次を渡して収束するまで回す。

- **対象:** 作成した `*.requirement.md`
- **根拠資料:** ユーザーの方針キーワード・リポジトリの規約（`CLAUDE.md`/`AGENTS.md` 等）・Phase 0 で確認した事実
- **記録先セクション:** 確認事項（既定案つき）
- **観点:** 完全性 / 検証可能性 / 実現可能性（Phase 0 の事実と矛盾しないか）/ 優先度の妥当性 / スコープ境界の明確さ / 確認事項の既定案の質 / 設計の「どう」への踏み込みすぎ

設計の「どう」に踏み込ませる指摘・合意済みスコープを広げる指摘・要件の前提を変えないと解消できない指摘は不採用とし、確認事項（既定案つき）へ残す。`doc-review-cycle` が使えない場合は、同スキルのサイクル（レビュー → 突き合わせ → 修正 → 上限3サイクル）を自分で実行する。

**(b) 回答反映:** 確認事項にユーザーの回答が付いたら、`確認事項` を `決定事項` テーブルへ昇格させ、本文（スコープ・要件）に反映し、**バージョンを上げ変更履歴に記録**する。新たな前提崩壊が判明したら Phase 0(d) に戻る。反映後に変更が大きい場合は (a) を1サイクル回してから提出する。

## 出力サマリ（作成・更新ごとにユーザーへ）

- 作成/更新したファイルのパスとバージョン
- 文書の概要（背景・目的・主要要件 3〜4行）
- **確認事項のハイライト**（特にブロッカーになる項目を既定案つきで）
- Phase 0 で見つけた重大制約があれば最優先で明示
- 次のステップ（回答待ち / 設計書 / 計測 等）

## 注意事項

- **要件と設計の区別:** 要件は「何を」、設計は「どう」。ただし裏取りに必要な範囲は具体に立ち入る。
- **バージョン管理:** 更新時は版を上げ変更履歴を残す。確認事項→決定事項の昇格も履歴に。
- **測定可能性:** 検証可能な形で書く。
- **エスカレーション:** 前提が崩れたら止まって聞く。これが手戻りを最小化する。
