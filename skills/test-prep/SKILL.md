# Test Prep

「これから手で動作確認する」状態を、環境・データ・URLの3点セットとして実際に用意する。

- **入力:** `*.testcase.md` / `*.testscenario.md`。無ければ `*.spec.md` / `*.requirement.md`、それも無ければ対象機能の実装コード（ブランチ差分・PR差分）
- **出力:** 起動済みの検証環境、投入済みの検証データ、`*.testdata.md`（環境・データ・URL・後片付け手順）
- **責務:** 検証環境の起動、検証データの設計と投入、実IDを埋めた動作確認URLの生成と到達確認、後片付け手順の提示
- **責務外:** テストケースの設計・文書化（`test-case-doc`）、テストコードの実装・実行（`implement`）、DBの復元・reindex（`restore-local-db`）、ローカル以外の環境への操作
- **関連:** DBが空・破損している場合はこのスキルの担当外。`restore-local-db` を案内して停止する

## 安全ガード（データ投入の前に必ず全て通す）

このスキルは文書生成ではなく**DBへの書き込み**を行う。次を1つでも満たせない場合は投入せず、状況を報告して停止する。

1. **接続先がローカルであること。** `DATABASE_URL` / `RAILS_ENV` / `NODE_ENV` / 接続先ホスト / コンテナ名を実際に読んで確認する。ホストが `localhost` `127.0.0.1` `db` 等のローカル向けでない、または環境名が `production` / `staging` / `prod` / `stg` を含む場合は**即座に停止**する。「たぶんローカル」で進めない。
2. **DBが実データを持っていること。** 主要テーブルの件数を数え、最小シード相当（数件〜十数件）しか無ければ投入せず `restore-local-db` を案内して停止する。復元を後から行うと、ここで作ったデータは消える。
3. **マイグレーションが適用済みであること。** 未適用のマイグレーションがあれば先に適用する。適用に失敗したら停止する。

### 投入時の原則

- **既存レコードを削除・更新しない。追加だけを行う。** 状態遷移の検証に「進んだ状態のデータ」が要る場合も、既存レコードを書き換えず、自分で作ったレコードを遷移させて用意する。
- どうしても既存データの変更が避けられない場合は、**対象・変更内容・元に戻す手順を提示して承認を得る**。承認なしに実行しない。
- **全レコードに識別できる印を付ける。** 固定プレフィックス（例: 名称に `[tp-<ブランチスラッグ>] `、メールに `test+tp-<ブランチスラッグ>-001@example.com`）を必ず入れる。これが再実行時の重複回避と後片付けの両方の根拠になる。印の規約は `*.testdata.md` に明記する。
- **再実行しても重複しない。** 投入前に印で既存を検索し、既にあれば作り直さず再利用する。作り直しが必要なら、印に一致するレコードだけを削除してから作る。

## 自律実行の原則

1. **入力を自動探索する。** 明示された文書を優先する。未指定ならリポジトリ内の `*.testcase.md` / `*.testscenario.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。選択した入力ファイルのパスは作業開始時に1行で宣言する。該当が無ければ `*.spec.md` → `*.requirement.md` → ブランチ差分の順にフォールバックする。
2. **プロジェクトの既存手段を使う。新しい仕組みを作らない。** データ投入は seed / factory / fixture / `rails runner` / 管理画面 / API のうち、そのリポジトリに既にあるものを使う。既存手段でどうしても賄えない場合だけ最小限の使い捨てスクリプトを書き、その内容と置き場所を `*.testdata.md` に記録する（リポジトリへコミットする前提の資産は作らない）。
3. **発見結果を記録し、2回目以降は再探索しない。** 起動コマンド・投入手段・ベースURLの導出根拠は `*.testdata.md` の `検証環境` へファイルパスつきで残す。既に `*.testdata.md` があれば、そこに書かれた手段を既定値として使い、差分だけ調べ直す。
4. **エッジケースは自分で発想せず `*.testcase.md` から取る。** 境界値・状態遷移・権限・空状態・異常系のケース表を読み、その前提条件欄に出てくるデータを実体化する。`*.testcase.md` が無い場合だけ、要件・設計・コードから最低限のエッジケース（境界値の両側 / 空・0件 / 権限違いのユーザー / 状態違いのレコード / 論理削除・無効フラグ）を自分で導出し、その旨を明記する。
5. **URLは推測しない。** ベースURLはプロジェクトの設定（ホスト定義・`.env`・dev サーバー設定・compose の ports）から取り、パスは routes 定義から取る。どちらも出典をファイルパスで記録する。
6. **安全に推定できる事項は質問しない。** テストデータの具体値・件数・命名は既存 factory / seed / 実データの傾向から決めて進める。質問は「安全ガードに引っかかったとき」「既存データの変更が避けられないとき」「ログインに使える認証情報がコードから特定できないとき」だけに限定する。
7. **中断からの再開に耐える。** データを投入するたびに `*.testdata.md` へ追記する。途中で失敗しても、何が作られ何が残っているかがファイルだけで分かる状態を保つ。

## 実行フロー

### Phase 1: 検証対象の把握

- 入力文書から、確認すべき機能・画面・APIと、手動確認が必要なケース（`*.testcase.md` の種別が **手動** のもの）を抽出する。
- 自動テストで既にカバーされているケースは準備対象から外す。このスキルが用意するのは**手で見ないと分からないもの**に限る。
- 対象がバッチ・スキーマ変更のみでURLが存在しない場合は、URLの節を省き、実行コマンドと確認用クエリを代わりに用意する。

### Phase 2: 検証手段の発見

次の順に読み、環境の起動・データ投入・URL組み立ての手段を特定する。上位で見つかったものを優先し、下位は補完に使う。

1. `CLAUDE.md` / `AGENTS.md` / `README` / `docs/` のセットアップ手順
2. タスクランナー・プロセス定義（`justfile` / `Makefile` / `Procfile` / `compose.yaml` / `package.json` の scripts）
3. データ投入の既存資産（`db/seeds*` / factory / fixture / `spec/factories` / 管理用 rake タスク）
4. ルーティング定義とホスト設定（routes / ページファイル構成 / `.env` / dev サーバー設定）

特定できた手段と、その根拠ファイルパスを控える。**どれも見つからない項目は「不明」として扱い、それらしいコマンドを創作しない。**

### Phase 3: 環境の起動

- Phase 2 で特定した手段で、対象機能の確認に必要なサービスだけを起動する（不要なサービスまで巻き込む全体起動コマンドは避ける）。
- 起動後、実際に応答することを確認する（トップページや health エンドポイントへのリクエスト）。応答しなければログを読み、原因と対処を報告する。
- 検索・非同期処理・外部連携など、対象機能が依存するミドルウェアの状態も確認する。インデックス未作成など、このスキルの責務外の不整合を見つけた場合は、担当スキル（`restore-local-db` 等）を案内する。

### Phase 4: 検証データの投入

- Phase 1 のケースごとに「どのデータが要るか」を表にする。1ケース1データにこだわらず、**同じデータで複数ケースを確認できるならまとめる**。
- 安全ガードを全て通してから投入する。
- 投入は印つきで行い、**生成された実IDを必ず控える**（あとで URL に埋めるため）。
- 投入後、対象データが実際に読み出せることをクエリで確認する。作ったつもりで作られていない（バリデーション落ち・トランザクションのロールバック）を検知するため、件数の突き合わせを必ず行う。
- ログインが必要な場合は、**そのまま使える認証情報**（メール・パスワード・ロール）を控える。既存の開発用アカウントがあればそれを使い、無ければ印つきで作る。

### Phase 5: 動作確認URLの生成

- Phase 2 で特定したベースURLと routes に、Phase 4 の**実ID**を埋めてURLを組み立てる。
- **`:id` や `<ID>` のようなプレースホルダを残さない。** コピペしてそのまま開ける完全なURLにする。クエリパラメータで絞り込みが要る画面は、パラメータまで含めて組み立てる。
- 各URLに「どのケース（TC-ID）の確認用か」「必要なログインユーザー」「そこで何を見れば合格か」を併記する。
- **生成した全URLの到達性を確認する。** リクエストを投げてステータスを確認し、404 / 500 を返すURLは載せない（原因を調べ、URLの誤りならば直し、実装の問題なら `*.testdata.md` に事実として記録する）。認証必須で 302 が返るものは、リダイレクト先がログイン画面であることを確認したうえで「要ログイン」と明記する。

### Phase 6: `*.testdata.md` の作成と自己検証

**ファイル名:** 入力文書の拡張子を `.testdata.md` に置換する（入力文書が無い場合は `{機能名}.testdata.md`）。
**作成場所:** 入力文書と同じディレクトリ。入力文書が無い場合はリポジトリルート。

**構成:** このスキルの `template.md` に従う。該当しない項目は理由つきで `N/A` とする。

書き終えたら、文書だけを見て次を自己検証する。1つでも破れていれば直してから完了とする。

- URL表の全URLが実IDを含む完全な形になっている（プレースホルダが残っていない）
- URL表の全URLについて到達確認の結果を記録した
- 作成データ一覧のIDが、実際にDBに存在するIDと一致している
- 後片付け手順のコマンドが、印に一致するレコードだけを対象にしている（対象件数を数えて確認する。**実行はしない**）
- この文書だけを渡された人が、環境の起動からURLを開くまでを再現できる

## 完了条件

- [ ] 安全ガードを全て通した（接続先がローカル / DBに実データがある / マイグレーション適用済み）
- [ ] 検証環境が起動し、実際に応答することを確認した
- [ ] 手動確認が必要なケースに対応する検証データを投入した（自動テストでカバー済みのケースは対象外にした）
- [ ] エッジケースを `*.testcase.md`（無い場合は要件・設計・コード）から導出して用意した
- [ ] 投入した全データに印が付いており、再実行しても重複しない
- [ ] 既存レコードを削除・更新していない（やむを得ず変更した場合は承認を得て、戻し方を記録した）
- [ ] 全URLが実IDを含むフルパスで、到達確認済み
- [ ] ログインが必要な画面について、そのまま使える認証情報を記載した
- [ ] `*.testdata.md` だけで環境起動からURLを開くまで再現できる
- [ ] 後片付け手順が印に一致するレコードだけを対象にしている

## 出力サマリ

完了後は、作成した `*.testdata.md` のパス、起動したサービス、投入したデータの件数と印、確認できるURLの本数、そして**そのまま貼れる形で主要な確認URL**を報告する。安全に推定した事項について確認を求めない。安全ガードで停止した場合は、どのガードにどう引っかかったかと次の一手だけを報告する。
