# Test Case Review

作成済みのテストケース文書を、要件・設計・実装コードを正として監査し、漏れと誤りを根拠つきで検出する。

- **入力:** レビュー対象のテストケース文書（`*.testcase.md`。他形式のテストケース表・QA項目リストでもよい）。対応する `*.requirement.md` / `*.spec.md` と実装コードを照合先にする
- **出力:** 対象と同じベース名の `*.testcase-review.md`
- **責務:** 漏れ（未カバーの要件・観点・境界・分岐）と誤り（期待結果・参照・データ整合）の検出、推奨追加ケースのドラフト提示
- **責務外:** テストケース文書本体の書き換え（採用された指摘の反映は `test-case-doc` の更新フローで行う）、テストコードの実装、テストの実行

## 自律実行の原則

1. **入力を自動探索する。** 明示された文書を優先する。未指定なら `*.testcase.md` を探索し、現在のブランチ名または依頼内容に最も一致するものを選ぶ。
2. **照合先を自動で読む。** 同じベース名の `*.requirement.md` / `*.spec.md` / `*.task.md` と、対象機能の実装コード・既存自動テストを読む。照合先文書が無い場合は実装コードだけを正として続行し、その旨をレポートに明記する。
3. **指摘は必ず根拠つきで出す。** 「〜のケースもあった方がよい」という一般論は指摘にしない。要件の文言、コードの実分岐・実値、テストデータ定義のいずれかを根拠（ファイルパス・該当箇所）として引用できる指摘だけを出す。
4. **偽陽性を自分で潰してから報告する。** 各指摘を確定する前に「対象文書の別の場所で既にカバーされていないか」「対象外セクションで理由つきで除外されていないか」を反証として探す。反証があれば指摘を取り下げる。
5. **水増ししない。** 指摘件数を稼ぐための重複指摘、フレームワーク標準機能だけを確認するケースの追加提案（プロジェクトの spec 方針に反するもの）、優先度を判断できない些末な指摘の羅列はしない。指摘ゼロなら「漏れなし」と報告するのが正しい成果である。
6. **対象文書を書き換えない。** 漏れを見つけても対象のテストケース文書には手を入れず、レポートに推奨追加ケースのドラフト（そのまま貼れる TC 表形式）として出す。反映の判断はユーザーと `test-case-doc` に委ねる。
7. **既存レポートがあれば更新する。** 前回指摘の解消状況（解消済み / 未対応）を追跡し、新規指摘と区別して記載する。

## 漏れ検出の方法

網羅性の検証は「読んで気づく」ではなく、正から逆算して機械的に照合する。

1. **要件の文言単位の逆引き:** 要件カバレッジ表が要件ID単位で埋まっていても信用しない。各要件・受け入れ条件を文単位に分解し、個々の主張（「〜の場合は…として復元する」等）ごとに検証する TC が存在するか照合する。ID 単位では対応ありでも文言単位で漏れるのが典型パターン。
2. **コードの分岐逆引き:** 実装の分岐・バリデーション実値・enum・権限判定・エラーパスを列挙し、どの TC にも踏まれない分岐を漏れ候補にする。既存自動テストがカバーしている分岐は「自動（済）として記載漏れ」か「対象外として妥当」かを区別する。あわせて**到達経路の逆引き**を行う: 変更された共通関数・共有コードの全呼び出し元・全クライアントを列挙し、スコープ外と宣言された画面・API からその変更へ到達できないか確認する。「UI は対象外」でも BE 共通変更が波及する経路は漏れの典型源。
3. **テスト技法での再導出:** 対象文書とは独立に、同値分割・境界値分析（境界の両側）・デシジョンテーブル（異種条件の組合せに加え、同種条件同士の複合も象限に含める）・状態遷移（許可された遷移すべて＋禁止の代表）・エラー推測（権限不足・不存在・重複・競合・部分失敗・再試行・空状態・外部依存の失敗）でケースを導出し、対象文書との差分を取る。
4. **観点マトリクスの検証:** 空欄・「対象外」の理由が事実（コード・要件）と整合するか。対象外理由が誤っていれば、その観点のケース群がまとめて漏れている可能性を疑う。
5. **期待結果とデータ定義の突き合わせ:** 手動ケースの期待ヒット件数・表示内容を、前提条件のテストデータ定義と1件ずつ数え上げて検算する。シードスクリプトがあれば実ファイルを読み、文書の凡例ではなくコードを正とする。
6. **実在性・参照整合の検証:** 記載されたファイルパス・テストの describe・コマンド・準備手順・URL・TC 相互参照（脚注が指す TC 番号等）が実在し、内容が一致するか確認する。
7. **仕様の穴の落とし込み確認:** 文書間の矛盾や期待結果を決められない仕様の欠落が `仕様上の確認事項` 相当のセクションに漏れなく記録されているか。入力文書側の内部矛盾（旧版の残骸等）も対象にする。

## 重大度の基準

- **High:** 受け入れ条件そのものの未カバー、期待結果の誤り（手動確認者が誤判定する）、データ破壊・セキュリティ・互換性に関わる漏れ
- **Mid:** 主要な異常系・境界値・組合せ象限の漏れ、対象外理由の事実誤認、要件文言単位の未カバー
- **Low:** 参照のズレ、表記・リンクの問題、任意で足すとより良い補足ケース

## 実行フロー

### Phase 1: 入力と照合先の把握

- 対象文書から TC 一覧、観点マトリクス、要件カバレッジ表、対象外理由、前提・テストデータ定義を抽出する。
- 照合先（要件・設計・実装コード・既存自動テスト・シード等の準備スクリプト）を特定して読む。

### Phase 2: 機械的照合

- 「漏れ検出の方法」1〜7 を順に実施し、指摘候補を根拠つきで列挙する。
- 各候補に反証探し（原則4）を行い、生き残ったものだけを指摘として確定する。

### Phase 3: レポートの作成

**ファイル名:** 対象の `.testcase.md` を `.testcase-review.md` に置換する。
**作成場所:** 原則として対象文書と同じディレクトリ。リンクは同じディレクトリなら相対パス、別ディレクトリ出力時は絶対パスまたはリポジトリルート相対で書く。

```markdown
# テストケースレビュー: <機能名>

## 概要
<対象文書・照合先・レビュー方法を3行程度で>

## 判定サマリ
<指摘件数（High/Mid/Low）と総評。指摘ゼロならその旨>

## 指摘一覧

### GAP-001: <指摘を1行で> [High|Mid|Low]
- 分類: <要件文言未カバー | 分岐未カバー | 境界値漏れ | 組合せ象限漏れ | 期待結果誤り | 対象外理由の誤認 | 参照不整合 | 確認事項の漏れ>
- 該当箇所: <対象文書の TC-ID・セクション、または「該当 TC なし」>
- 根拠: <要件文言・コードのパスと該当箇所・データ定義>
- 推奨追加ケース / 修正案:
  | ID | 対応要件 | 優先度 | 種別 | 前提条件 | 手順 | 期待結果 |
  |---|---|---|---|---|---|---|
  <そのまま対象文書に貼れる形。修正指摘なら修正後の文面>

## 検証して問題なしを確認した点
<照合したが漏れ・誤りが無かった範囲。何をどこまで検証したかが分かる粒度で>

## 前回指摘の追跡
<更新時のみ。解消済み / 未対応の別>

## 確認事項
<採否を判定できず、ユーザーの判断が必要な論点。論点 / なぜ / 推奨案>
```

書き方のルール:

- 推奨追加ケースは `test-case-doc` の TC 表と同じ列構成で書き、期待結果は観測可能な形にする。
- 「検証して問題なしを確認した点」を必ず書く。レビューの網羅範囲が分からない指摘一覧は、漏れゼロと未検証を区別できず信頼できない。
- 指摘の根拠に書くファイルパス・該当箇所は実在を確認してから書く。照合先が別ディレクトリや別 worktree にある場合は、実在確認済みの絶対パス（またはリポジトリルート相対）で統一する。
- `確認事項` セクションと指摘の書き分け: 対象文書へ追記・修正すべき具体的な文面が決まるものは指摘（GAP）の修正案側に書く。採否や方針の判断がユーザーにしかできない論点だけを `確認事項` に置く。

### Phase 4: レビューサイクル

レポートの作成後、次のサイクルを収束するまで回してから完了とする。

1. **レポートをレビューする。** 新鮮な目で（可能なら同期実行のレビュー用サブエージェントで。非同期起動して待ち合わせない）レビューする。サブエージェントが使えない場合、自分のインラインレビューは直前に書いた根拠の再確認になりがちで独立性が弱い。そのときは機械的手順で代替する: 重大度の高い指摘から順に、根拠として引用したファイルを**もう一度開き直して**原文と突き合わせ、引用の正確性と論理の飛躍を検査する。観点: 各指摘の根拠の実在性と論理の正しさ（偽陽性）/ 「漏れ検出の方法」1〜7 の実施漏れ / 重大度の妥当性 / 推奨追加ケースの期待結果がデータ定義・コードと整合するか / 水増し指摘の混入。
2. **各指摘を照合先と突き合わせ、偽陽性を取り下げる。** 指摘自体の誤りは黙って直すのではなく、取り下げた理由を作業記録として出力サマリに含める。
3. **収束条件:** 修正すべき点が出なくなるまで繰り返す（上限3サイクル）。

## 完了条件

- [ ] 「漏れ検出の方法」1〜7 をすべて実施した（該当なしの項目は理由を記録）
- [ ] 全指摘に根拠（要件文言・コード実パス・データ定義のいずれか）がある
- [ ] 各指摘の反証探しを行い、偽陽性を取り下げた
- [ ] 推奨追加ケースが TC 表形式で、そのまま対象文書へ貼れる
- [ ] 「検証して問題なしを確認した点」で検証範囲を明示した
- [ ] 対象のテストケース文書本体を書き換えていない
- [ ] レビューサイクルが収束している

## 出力サマリ

完了後は、レポートのファイルパス、指摘件数（重大度別・分類別）、High 指摘のハイライト、取り下げた偽陽性の件数だけを簡潔に報告する。指摘ゼロの場合は検証範囲とあわせて「漏れなし」を報告する。
