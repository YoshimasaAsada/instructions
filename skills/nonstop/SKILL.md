# Nonstop

要件定義から実装までの工程チェーンを、途中でユーザーの回答を待たずに完走させるオーケストレータ。

- **目的:** 「確認事項を出す → 回答待ち」で分断されていた工程を、1回の指示で最後まで通す
- **入力:** GitHub issue の URL・番号（既定の入り口）。または雑な依頼・要件メモ・Slack スレッド・既存の `*.requirement.md`
- **出力:** 作業ブランチ ＋ 各工程の文書（`*.requirement.md` / `*.spec.md` / `*.task.md` / `*.testcase.md`）＋ 実装 ＋ **決定ログ `{機能名}.decisions.md`**

> 工程の全体像と個別スキルの使い分けは `skills-map` を参照。

---

## 起動方法

**issue の URL だけを渡されたら、それ以上何も聞かず Phase 0 から Phase 6 まで走り切る。**

| 指示 | 動作 |
|------|------|
| `/nonstop <issue URL>` | ブランチ作成 → 要件定義 → 設計 → タスク分解 → テストケース → 実装 → 決定ログ提示 |
| `/nonstop <issue番号>` | 同上 |
| `/nonstop <メモのパス>` | ブランチ作成をスキップし（命名の根拠が無いため）、要件定義から実行 |
| `/nonstop <URL> 設計まで` | 指定工程で停止する（`要件だけ` / `設計まで` / `タスクまで` / `テストケースまで`） |
| `/nonstop <URL> PRまで` | Phase 7 まで進む（push と PR 作成の確認は省略しない） |
| `/nonstop <URL> ブランチはこのまま` | Phase 0 のブランチ作成をスキップし、現在のブランチで作業する |

引数が無いときだけ、対象（issue の URL / メモのパス）を聞く。**それ以外は聞かない。**

## このスキルが上書きするもの

各工程スキルは「未決事項を勝手に確定させない」原則を持つ。このスキルはそれを**仮確定ポリシー**へ置き換える。上書きするのは次の3点だけで、他の原則はそのまま守る。

| 工程スキル | 元の挙動 | nonstop での挙動 |
|---|---|---|
| `requirements-definition` Phase 3(b) | 確認事項にユーザーの回答が付くのを待つ | 既定案で仮確定し、決定事項へ昇格させて続行 |
| `design-doc` 原則5 / Phase 1 | ユーザー価値・公開仕様・権限に関わる未決事項は確認する | 保守側の案で仮確定して続行（「止まる条件」に該当する場合を除く） |
| `implement` 原則5 | 上流文書に未決事項が残っていれば着手前に確認 | 決定ログの仮確定値を確定値として実装 |

**上書きしないもの:** 各スキルのレビューサイクル（`doc-review-cycle`）、`implement` のCIループと変更範囲の原則、`test-prep` の安全ガード、`commit-and-pr` の push / PR 作成の確認。品質と外部影響の担保は落とさない。

## 仮確定ポリシー（このスキルの核心）

### 1. 既定案があるものは、すべて仮確定して進む

`論点 / なぜ確認が必要か / 想定デフォルト案` の3点セットを作るところまでは各工程スキルと同じ。違うのは**そこで止まらず、想定デフォルト案を採用して決定ログへ記録し、下流工程はその値を確定値として扱う**こと。

### 2. 既定案を作れない論点は「保守側」に倒す

判断材料が足りず既定案が定まらない場合も止まらない。次の順で倒す。

1. **可逆な側**を選ぶ（後から広げられる / 消せる / 戻せる）
2. **影響範囲が狭い側**を選ぶ（既存の挙動を変えない / 新規追加で済む）
3. **既存実装に最も似ている側**を選ぶ（このリポジトリの既存パターンを踏襲する）

倒した理由と、別案だった場合の手戻り範囲を決定ログに書く。

### 3. 止まる条件（唯一の例外）

次のいずれかに該当し、**かつ保守側の選択肢が存在しない**（どちらを選んでも不可逆・外部に影響する）場合だけ停止して確認する。

- 本番・ステージングのデータを不可逆に変更する
- 外部公開済みの API・スキーマを破壊的に変更する
- 権限・認可の境界を変更する
- 個人情報の取得・保存・外部送信の範囲を変更する（対象リポジトリの `AGENTS.md` が人間の確認を要求している）
- 課金・請求・送信（メール・通知・push）など、実行を取り消せない副作用を持つ

**保守側の選択肢がある場合は停止しない。** 保守側を採ったうえで決定ログに `⚠️` を付け、Phase 6 の提示で先頭に置く。

- 例（止まらない）: 「個人情報カラムを BigQuery 同期対象に含めるか」→ 含めない側を採って続行し `⚠️` で提示
- 例（止まる）: 「既存の本番テーブルをどちらの方式で破壊的移行するか」→ 保守側が存在しないので停止

### 4. 記録のない仮確定は禁止

仮確定は「決めた」ことではなく「決めたことにして進んだ」ことなので、追跡できなければ後から覆せない。すべて `{機能名}.decisions.md` に集約する（ひな形はこのスキルの `template.md`）。各工程文書の記録先セクションにも `D-n` を併記して相互参照させる。

| 工程 | 文書側の記録先セクション |
|---|---|
| requirements-definition | `確認事項（Open Questions）`（`C-n` を決定事項へ昇格し `D-n` を併記） |
| design-doc | `前提・採用した既定案` / `未決事項` |
| task-breakdown | `実行上の注意` |
| test-case-doc | `仕様上の確認事項` |
| implement | `*.followup.md` |

## 自律実行の原則

1. **入力とエントリ工程を自動判定する。** issue の URL・番号が渡されたらそれを一次入力とする。既存文書も探索し、`*.requirement.md` があれば設計から、`*.task.md` まであれば実装から始める。すでにある文書は作り直さず、後続工程の入力にする。
2. **一次情報は自分で取りに行く。** issue・Slack・Notion 等のリンクは `requirements-definition` の Phase 0-A に従って必ずアクセスを試みる。ここを省くと全工程の前提が推測になり、仮確定の質が落ちて手戻りが最大化する。**ノンストップにおける最大の品質リスクは一次情報の欠落**であり、確認を省くこととは別物。
3. **前工程の成果物はファイルから読み直す。** 全工程を1セッションで通すため、後半では前半の会話が要約・消失している前提で動く。各 Phase の冒頭で前工程の文書を実際に読む。会話の記憶を根拠にしない。
4. **中断からの再開に耐える。** 工程が終わるたびに決定ログの進捗表を更新する。再実行時は進捗表と既存文書を見て、未完了の工程から再開する。
5. **止まらないことを最優先する。** 質問したくなったら、まず仮確定ポリシーの 1 → 2 → 3 の順に判定する。3 に該当しない限り質問しない。「念のため確認」はしない。

## 実行フロー

各 Phase は対応する工程スキルを **Skill ツールで invoke** して実行する。invoke 時の args に、その工程の入力パスと**次のポリシー文を必ず含める**。

```
【仮確定モード / nonstop】確認事項・未決事項はユーザーに質問せず、既定案（無ければ可逆・影響最小・既存踏襲の保守側）で仮確定して続行する。仮確定は {機能名}.decisions.md へ D-n として追記し、文書側の記録先セクションから参照する。停止してよいのは「本番データの不可逆変更 / 公開APIの破壊的変更 / 権限境界の変更 / 個人情報の取扱範囲の変更 / 取り消せない送信・課金」に該当し、かつ保守側の選択肢が無い場合のみ。レビューサイクルとCIループは通常どおり回す。
```

### Phase 0: 入力の解決と作業ブランチの準備

**(a) 入力を解決する。**

引数が issue の URL・`#1234`・数字なら issue 番号を取り出し、**URL を直接開かず `gh` で取得する**（対象リポジトリの `AGENTS.md` の定め）。

```bash
gh repo view --json nameWithOwner -q .nameWithOwner
gh issue view <番号> --json number,title,body,labels,url,comments
```

- issue の本文とコメントに含まれる一次情報リンク（Slack / Notion / Figma / スプレッドシート / 関連 issue・PR）をすべて拾い出し、Phase 1 へ引き渡す。**issue 本文は要約であることが多く、目的・スコープ・受け入れ条件・デザインの所在は一次情報側にしかないことが普通。**
- ラベル・関連 issue から対象システム（api / front / ml など）を判定し、調査範囲の初期値にする。
- 引数がメモのパス・依頼文なら、それを入力とし (b) はスキップする。
- **機能名**を issue タイトルから決める（各文書のファイル名プレフィックスになる）。日本語タイトルは英小文字ケバブケースへ落とす。

**(b) 作業ブランチを用意する。**

`start-issue` を Skill ツールで invoke し、issue 番号を渡してブランチを作らせる。**ブランチ命名規約はプロジェクト側の定義（`start-issue` / `CLAUDE.md` / `CLAUDE.local.md`）に従い、このスキルでは決め打ちしない。**

`start-issue` の確認で止まらないための、nonstop での既定:

- 派生元は**既定ブランチの最新**とする（`gh repo view --json defaultBranchRef` で判定し、`git fetch` してからそこを起点に切る）。現在のブランチが既定ブランチでなくても確認しない。
- 現在のブランチが**自動生成名**（`claude/<形容詞>-<名前>-<hex>` 形式など）なら、規約準拠のブランチへ切り直す。
- 対象 issue の規約準拠ブランチが**すでに存在する**場合は、新規作成せずチェックアウトして再開扱いにする。
- **未コミットの変更が乗っている場合だけは停止して報告する。** 他人・別作業の変更を巻き込んで分岐させないため、ここは仮確定で押し切らない。
- 作成・切り替えたブランチ名を1行で宣言する。

**(c) 作業場所を決める。**

- 出力先ディレクトリを決める（既存の `*.requirement.md` があればその場所、無ければリポジトリの文書管理ディレクトリ or ルート）。
- 既存文書の有無からエントリ工程を決める。
- `template.md` から `{機能名}.decisions.md` を作成し、進捗表と issue の URL を記録する。
- **宣言してから Phase 1 へ進む:** issue番号 / 機能名 / ブランチ名 / エントリ工程 / 出力先 / 停止指定（`設計まで` 等）。

### Phase 1: 要件定義 — `requirements-definition`

- 一次情報の取得（Phase 0-A）と裏取り調査（Phase 0）は**省略しない**。
- 確認事項 `C-n` を作るところまでは通常どおり行い、回答を待たずに全件を仮確定して決定事項へ昇格させる。昇格させた項目には `D-n` を併記する。
- 調査で要件の前提が覆った場合は、覆った側を正として要件を書き直し、決定ログの `覆った仮確定` に記録する。

### Phase 2: 技術設計 — `design-doc`

- 入力は Phase 1 の `*.requirement.md`。決定ログを併せて読ませ、仮確定値を確定値として扱わせる。
- 未決事項は `前提・採用した既定案` へ倒して続行する。

### Phase 3: タスク分解 — `task-breakdown`

- 入力は `*.spec.md`。仮確定に依存するタスクには、決定ログの `D-n` をタスク側に注記させる（覆ったときの影響範囲を機械的に引けるようにするため）。

### Phase 4: テストケース — `test-case-doc`

- 入力は `*.requirement.md` / `*.spec.md` / `*.task.md`。
- 期待結果が決まらない仕様の穴も仮確定して埋める。埋めた箇所は `仕様上の確認事項` と決定ログの両方に残す。

### Phase 5: 実装 — `implement`

- 入力は `*.task.md` と決定ログ。上流の未決事項を理由に停止させない。
- CIループ（100%通過）とレビューサイクルは通常どおり収束させる。**ここを短縮しない。**
- 実装中に仮確定が成立しないと判明したら、「工程間ゲート」の差し戻し手順に従う。

### Phase 6: 決定ログの一括提示（唯一のゲート）

完走後に、仮確定を番号付きで一括提示する。ユーザーが `D-3 は別案で` のように番号だけで差し戻せる形にする。

- `⚠️` 付き（止まる条件に触れたが保守側で回避したもの）を先頭に置く
- 手戻りコストが大きい順に並べる
- 差し戻しが来たら、該当 `D-n` を起点に影響する工程から再実行する

### Phase 7: 後続工程（依頼された場合のみ）

`test-prep`（動作確認の準備）と `commit-and-pr`（コミット・PR）は既定では実行しない。依頼された場合のみ続けて呼ぶ。**この2つのユーザー確認（安全ガード / push・PR 作成の合意）は仮確定モードでも省略しない。**

## 工程間ゲート

次の工程へ進む前に機械的に確認する。1つでも欠けたら次へ進まず、前工程をやり直す。

| 進む先 | 前工程の必須条件 |
|---|---|
| 技術設計 | `*.requirement.md` が存在し、機能要件が `FR-nnn` 形式で1件以上、スコープ外が空でない |
| タスク分解 | `*.spec.md` が存在し、変更対象が実在するファイルパスで書かれている |
| テストケース | `*.task.md` のタスクが全要件 ID をカバーしている |
| 実装 | `*.testcase.md` の期待結果に「未定」「TBD」が残っていない |
| Phase 6 | `implement` の完了条件（CI相当チェック100%・レビューサイクル収束）を満たしている |

**前提が崩れた場合だけは戻る。** 下流工程で「上流の仮確定が実装上成立しない」と判明したら、その仮確定を差し替え、上流文書を更新し、決定ログの `覆った仮確定` へ記録してから再開する。**黙って実装を歪めて辻褄を合わせない。**

## 完了条件

- [ ] issue 起点の場合、規約準拠の作業ブランチ上で作業している（自動生成名のままになっていない）
- [ ] Phase 1〜5 の成果物がすべて存在し、工程間ゲートを満たしている
- [ ] `implement` の完了条件（CI相当チェック100%・レビューサイクル収束）を満たしている
- [ ] すべての仮確定が決定ログに `D-n` として記録され、根拠・由来・覆った場合の手戻りが埋まっている
- [ ] 各工程文書の記録先セクションが `D-n` を参照している
- [ ] `⚠️` 付きの仮確定が決定ログと出力サマリの先頭に並んでいる
- [ ] 決定ログの進捗表が最終状態を反映している

## 出力サマリ

1. 対象 issue（番号・タイトル）と作成した作業ブランチ名
2. 通した工程と生成した文書のパス（1行ずつ）
3. 実装内容の概要（3〜4行）
4. **仮確定の一覧**（`⚠️` を先頭、手戻りコストの大きい順）: `D-n / 論点 / 採用案 / 覆った場合の手戻り` の表
5. 停止した場合は、どの止まる条件に該当したかと選択肢
6. 次のアクション（`test-prep` / `commit-and-pr` / 差し戻し方法）

**「確認事項があります」で終わらせない。** 仮確定として提示し、ユーザーが番号で覆せる形にするのがこのスキルの成果物。
