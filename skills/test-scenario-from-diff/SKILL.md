# Test Scenario From Diff

実装した差分を、人が画面で辿れる動作確認シナリオへ変換する。

- **入力:** 現在のブランチの差分（主開発ブランチ〜HEAD）。PR番号・コミット範囲・ファイル・機能名の明示があればそれを優先する。上流文書（`*.requirement.md` / `*.spec.md`）は在れば併読するが必須ではない
- **出力:** `{機能名}.testscenario.md`（上流文書があれば同じベース名）
- **責務:** 差分の意味の読み取り（変更前→変更後）、影響範囲の特定、到達経路の特定、手動確認シナリオの設計
- **責務外:** コードの修正、テストコードの実装・実行、検証データの投入、要件・設計の変更
- **関連:** 上流文書起点の網羅的なケース表は `test-case-doc`、シナリオを動かす環境・データ・URLの用意は `test-prep`、作成済み文書の監査は `test-case-review`

## 網羅の軸が test-case-doc と違う

`test-case-doc` は「仕様書に書かれたことが満たされるか」を、要件・受け入れ条件を軸に網羅する。このスキルが答えるのは別の問いで、**「この変更で何が変わり、何が巻き添えで壊れうるか」** を `変更点 × 影響範囲` の軸で網羅する。

この違いは対象の取り方に効く。差分が触れていない機能は、要件に書かれていても対象外にしてよい。逆に、差分が触れた共有コードの利用箇所は、今回の目的と無関係でも対象に入れる。仕様書が存在しない場面（バグ修正・リファクタ・他人のPRのレビュー）でも成立するのはこのためで、**上流文書が無いことを理由に止まらない**。

## 自律実行の原則

1. **差分を特定し、範囲を宣言してから始める。** 明示があればそれを使う。無ければ `git merge-base <主開発ブランチ> HEAD` を base とし、`git diff --stat <base>..HEAD` で変更ファイルを取る。未コミットの変更があれば作業ツリーも含める。PR番号が分かるなら `gh pr view` / `gh pr diff` で本文と関連 issue も読む。**base・対象ファイル数・PR/issue番号は作業開始時に1行で宣言する。** 範囲を取り違えたまま進むと成果物が丸ごと無駄になるため、ここだけは黙って進めない。

2. **変更前の挙動を推測しない。** 「前はこうだったはず」で書いた回帰シナリオは、確認すべきものを確認しない。`git show <base>:<path>` で変更前の実コードを読み、閾値・条件・並び順・文言・デフォルト値の実値を変更前後で併記する（例: `30歳以下 → 32歳以下`）。値を並べて初めて「どのデータで差が出るか」が決まる。

3. **差分の外を必ず見る。** 差分に写っているファイルだけでシナリオを作ると、共有コードの巻き添えを丸ごと落とす。変更した識別子（メソッド・コンポーネント・GraphQLフィールド・カラム・enum値）の参照元を grep で洗い、影響先を「確認する / 理由つきで確認不要」のどちらかに必ず倒す。判断を保留した空欄を残さない。

4. **画面から到達できるかを実装で確かめる。** 成果物は人が上から実行するチェックリストなので、分岐を満たすデータ・権限・導線が実在するかまで確認する。到達手段が無い分岐は無理にシナリオ化せず「手動では確認不可」と理由つきで書き、自動テストへ回す。ここを曖昧にすると実行できない項目が混ざり、チェックリスト全体が信用されなくなる。

5. **自動テストで足りているものを手動シナリオにしない。** 差分そのものにテストの追加・修正が含まれていることが多いので（`implement` 経由なら必ず含まれる）、まず差分内のテストを読む。次に対象機能の既存テスト（RSpec / Vitest 等、プロジェクトのテストフレームワークに従う）を読み、カバー済みのものは `自動テストでカバー済み` へ分離する。手動シナリオは「人が見ないと分からないもの」に絞ったときだけ価値が出る。

6. **期待結果は画面で観測できる形で書く。** 「正しく保存される」ではなく「一覧の1行目に表示され、ステータスバッジが『対応中』になる」。DBの値やログは、画面だけでは判別できないときの補助として括弧書きで添える。

7. **仕様の穴は埋めない。** 期待結果を一意に決められない箇所（未定義のエラー挙動、競合時の優先順位、移行前データの扱いなど）は勝手に決めず `確認事項` へ推奨案つきで残す。差分だけからは意図が読み切れない箇所が出るのは正常で、それを見つけること自体がこのスキルの成果物のひとつ。

8. **実在しないものを書かない。** URL・コマンド・ロール名・データの作り方は実在を確認してから書く。既存手段で用意できないデータは「要準備」と明記し、`test-prep` への引き継ぎに回す（このスキル自身はデータを投入しない）。

9. **既存ファイルがあれば更新する。** 実施済みチェックや利用者の追記を保持したまま、差分の増分に対応するシナリオを追加・修正する。

## 実行フロー

### Phase 1: 差分の特定と意図の把握

- 対象範囲を確定して宣言する（原則1）。
- **書かれている意図を先に読む。** コミットメッセージ・PR本文・関連 issue から「何をしたかったのか」を1〜3行にまとめる。差分から意図を推測するのは、書かれた意図を読んだ後に限る。上流文書があれば併読し、実装と食い違う場合は実装を事実として `確認事項` に記録する。
- 変更ファイルを層で分類し、以降の調査範囲を絞る。
  - **Rails**: モデル / コントローラ / GraphQL（型・リゾルバ・ミューテーション）/ サービス・フォーム / ジョブ・バッチ / マイグレーション・enum
  - **フロント**: ページ（`pages/`）/ ページ配下コンポーネント / 共有コンポーネント（`components/base`・`packages/ui`）/ `*.gql`
  - **設定・生成物**: 権限定義、環境変数、feature flag、dbt / dwh_data_sync、codegen 生成物
- 生成物だけの差分（`generated.ts` / `schema.rb` / dbt生成物）はそれ自体をシナリオ化せず、生成元の変更に紐づける。生成物が生成元と食い違う（再生成漏れ）なら `確認事項` に上げる。

### Phase 2: 変更の意味の読み取り（変更前 → 変更後）

差分の各まとまりを次のどれかに分類し、**変更前と変更後を1行ずつ**書く。ここが以降のシナリオの骨になる。

| 変更の型 | 手動確認で狙うもの |
|---|---|
| 振る舞いの追加 | 新しい導線が入口から結果まで一続きで通ること |
| 既存の振る舞いの変更（条件・閾値・並び順・文言・デフォルト値） | 変更後の新挙動と、**変更前の条件に当たるデータが新挙動でどう扱われるか** の両方 |
| データ構造の変更（カラム追加・enum追加・NOT NULL・リネーム） | 移行前に作られた既存レコード（NULL・旧enum値）が壊れないこと |
| 削除・移行 | 消したものを参照していた画面・機能が落ちないこと |
| 非機能（N+1解消・キャッシュ・リトライ・非同期化） | 見た目の挙動が変わらないこと ＋ 変更の効果が観測できること |

実値（閾値・正規表現・enum値・件数上限・並び順のキー）は変更前後の両方から拾って併記する。差が出るデータの境界は、この併記からしか導けない。

### Phase 3: 影響範囲の探索

差分の外へ出る。変更した識別子ごとに参照元を洗う。

- **メソッド・関数・コンポーネント**: 名前で grep し、呼び出し元の画面・ジョブを列挙する
- **モデルのスコープ・バリデーション・コールバック**: それを使う画面・GraphQL・バッチ・ジョブ・管理機能
- **GraphQLの型・フィールド**: フロント側の `*.gql` を grep し、そのクエリを使うページを特定する
- **共有コンポーネント**（`components/base` / `packages/ui`）: 利用箇所を列挙する。全部は確認できないので代表的な利用画面を数点選び、**選んだ理由**（variant 違い・レイアウト条件違い等）を書く
- **マイグレーション・enumの追加**: リポジトリの規約文書（`AGENTS.md` / `CLAUDE.md` 等）に「マイグレーション後の追随作業」の定めがあれば、それを確認観点にする。差分に追随作業が含まれていなければ `確認事項` に上げる
- **権限判定**: 影響するロールを列挙し、ロール別シナリオの要否を決める
- **非同期・バッチ**: 変更がジョブ・バッチ経由でしか画面に現れないなら、その発火方法を調べる。手動で発火できないなら「手動では確認不可」に倒す

結果を影響範囲表にまとめ、空欄を残さない。

| 影響先 | 経路（なぜ影響するか） | 確認するか | 理由 |

### Phase 4: 到達経路の特定

シナリオを実行可能にするため、確認対象ごとに次を実装から特定する。

- **画面URL / ルート**: `pages/` のファイルパスやルーティング定義から組み立てる。ベースURLはプロジェクトの設定から取る（in-vision なら `http://in-vision.localhost:8080/...`）
- **導線**: どの画面のどのボタン・リンクから辿るか
- **必要な権限・ロール**
- **必要なデータ条件**: 分岐を通すためにレコードがどんな状態である必要があるか（ステータス・日付・件数・関連の有無）。既存の factory / seed から実在する作り方を確認する

画面から確認できないもの（管理者のみ実行可能、外部サービスの応答が必要、時刻依存、バッチ経由のみ）は理由つきで分離し、代替案（自動テスト / ログ確認 / コンソール確認）を添える。

### Phase 5: シナリオ設計

シナリオ = **1つの筋書き**。「前提（誰が・どんなデータで）→ 操作の流れ → 各ステップで見えるべきもの」を、上から順に実行できる形で書く。

粒度の目安:

- 1シナリオ = 1つの確認目的、3〜8ステップ。
- **入力値だけが違うものは1シナリオにまとめ**、ステップ内のバリエーション表で振る（シナリオを増やすより見通しが良い）。
- **前提データが違うものは分ける**（途中で前提を作り直す手順は事故のもと）。

差分起点で必ず検討する型。該当しないものは理由つきで対象外にする。

1. **主目的の通し** — 変更が意図どおり動く筋書きを、入口から結果の確認まで一続きで
2. **変更前の条件に当たるデータ** — 条件・閾値を変えたなら、旧条件のデータが新挙動でどう扱われるかを必ず1本
3. **既存データとの互換** — 移行前レコード・NULL・旧enum値
4. **巻き添えの確認（回帰）** — Phase 3 で「確認する」に倒した影響先が壊れていないこと
5. **権限・ロール別** — 見え方・操作可否が変わるロールごと
6. **境界** — Phase 2 で拾った実値の両側
7. **失敗・異常** — 入力不正、対象不存在、重複操作、外部連携の失敗、権限不足
8. **空状態・大量データ** — 0件表示、ページング、件数上限

各シナリオに付けるもの:

- **優先度**: High（変更の主目的・データ破壊やセキュリティに関わる）/ Mid（主要な異常系・境界・巻き添え）/ Low（表示の細部・稀な組合せ）
- **確認手段**: 手動 / 自動テストでカバー済み（テストファイルパス＋describe・context名）/ 手動では確認不可（理由と代替案）。自動テストの参照に行番号は書かない（ファイル変更で腐る）

### Phase 6: 文書化

**ファイル名:** 上流文書があれば同じベース名で `.testscenario.md`、無ければ `{機能名}.testscenario.md`。機能名はブランチ名・PRタイトルから決める。
**作成場所:** 上流文書と同じディレクトリ。無ければプロジェクトの文書管理ディレクトリ、それも無ければリポジトリルート。入力文書へのリンクは、同じディレクトリなら相対パス、別ディレクトリならリポジトリルート相対で書く（壊れた相対リンクを作らない）。

**構成:** このスキルの `template.md` を読み、その構成に従う。該当しない項目は理由つきで `N/A` とする。

### Phase 7: レビューサイクル

`doc-review-cycle` スキルを起動し、次を渡して収束するまで回す。

- **対象:** 作成・更新した `*.testscenario.md`
- **根拠資料:** 差分（`git diff`）・変更前のコード（`git show <base>:<path>`）・実コード・PR/issue・プロジェクト規約（`CLAUDE.md` / `AGENTS.md` / `.claude/rules/`）
- **記録先セクション:** `確認事項`
- **観点:**
  - 差分の全ハンクが、いずれかのシナリオか「対象外（理由つき）」に紐づいているか
  - **変更前の挙動が実コードで裏取りされているか**（推測で書かれた回帰シナリオが混ざっていないか）
  - 影響範囲表に空欄がないか。共有コードの利用箇所が落ちていないか
  - 各シナリオが到達可能か（前提データ・権限・導線が実在するか）
  - 期待結果が画面で観測できる形か
  - 自動テストでカバー済みのものが手動シナリオに混ざっていないか
  - 記載したURL・コマンド・ファイルパスの実在性
  - チェックリストがそのままリリース前確認に使えるか

仕様の変更を要する指摘は不採用とし、`確認事項` へ残す。`doc-review-cycle` が使えない場合は、同スキルのサイクル（レビュー → 突き合わせ → 修正 → 上限3サイクル）を自分で実行する。

## 完了条件

- [ ] 対象範囲（base・ファイル数・PR/issue）を宣言した
- [ ] 差分の全ハンクが変更の型に分類され、変更前→変更後が実コード由来の実値で書かれている
- [ ] 影響範囲表に空欄がない（確認する or 理由つきで確認不要）
- [ ] 全シナリオに優先度と確認手段がある
- [ ] 手動シナリオの前提・導線・URLが実在し、上から実行できる
- [ ] 手動では確認不可なものを、理由と代替案つきで分離した
- [ ] 自動テストでカバー済みのものを手動シナリオから外した
- [ ] 期待結果がすべて画面で観測できる形で書かれている
- [ ] 仕様の穴を期待結果に埋めず `確認事項` に分離した
- [ ] レビューサイクルが収束している（最終サイクルで採用すべき指摘がない）

## 出力サマリ

完了後は、作成・更新したファイルパス、対象差分の範囲、シナリオ数（優先度別・確認手段別の内訳）、影響範囲で「確認不要」に倒したものの件数、確認事項のハイライトだけを簡潔に報告する。安全に推定した事項について確認を求めない。データの準備が必要なら `test-prep` を、テストコードの追加が必要なら `implement` を次工程として案内する。
