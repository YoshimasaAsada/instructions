# Feature Planning

新機能の要件から、要件定義書・設計書・タスクリストの3ドキュメントを生成する。

- **目的:** 機能開発に必要なドキュメント一式を構造化して作成する
- **入力:** 機能の要件・改修対象リポジトリ・参考リポジトリ（任意）
- **出力:** `{ブランチ名}.requirement.md` / `{ブランチ名}.spec.md` / `{ブランチ名}.task.md`

---

## 事前確認事項

ドキュメント作成前に、未確定事項があれば必ずユーザーに確認する。

1. **ブランチ名** — ファイル名プレフィックス（例: `feat/add-video-watch-flags`）
2. **改修対象リポジトリ** — どのシステムを改修するか
3. **参考・別システム** — 真似したい実装があるか、あればどのリポジトリか
4. **非機能要件** — 性能目標・可用性・監査ログ要否
5. **リリース制約** — Feature Flag要否、段階リリース要否
6. **互換性方針** — 後方互換を維持するか、破壊的変更を許容するか

---

## 追加ルール（厳守）

- 推測で仕様を埋めない。未確定事項は `TBD` として列挙する。
- 仕様不明点は「要確認事項」として明示し、質問案を作る。
- すべての設計判断に根拠（`path:line`）を添える。
- 境界バリデーション（API入力、型、DB制約）の責務分担を明記する。
- 破壊的変更の有無と影響範囲を明記する。
- DB変更がある場合は、移行手順・ロールバック手順・整合性チェックSQLを必ず記載する。
- セキュリティ・性能・運用監視（ログ/メトリクス/アラート）を設計対象に含める。

---

## 実行フロー

### Phase 1: コード調査

ユーザー要件をもとに、改修対象・参考システムを調査する。可能なら並列で調査する。

**改修対象システムの調査ポイント:**

- 関連DBモデル定義（ORM使用時はテーブル名・カラム名マッピングを確認）
- 関連サービス・ユースケースの実装
- 関連スキーマ型定義
- 関連フロントエンドのhooks・コンポーネント
- 既存テスト（正常系・異常系・境界値）
- 監視・ログ出力・運用手順（該当する場合）

**参考システムの調査ポイント（ある場合）:**

- 参考にするユースケース・サービスの全文
- 関連DBモデル定義
- 使用している定数・型定義
- 差分吸収が必要な設計条件（認可、マルチテナント、RLSなど）

---

### Phase 2: 要件定義書の作成

**ファイル名:** `{ブランチ名のスラッシュをハイフンに変換}.requirement.md`  
**作成場所:** 改修対象リポジトリのルート

**必須セクション:**

- ブランチ名
- 背景・目的
- 対象リポジトリ / 参考リポジトリ（表形式）
- 改修内容（DB定義 → バックエンド → フロントエンドの順）
- 受け入れ基準（Given/When/Then）
- 非機能要件（性能・可用性・監査）
- スコープ外（別PRで対応するもの）
- リスク・未確定事項（TBD）
- 参考ファイル一覧（`path:line`）

**DBモデル名とテーブル名が一致しない場合は注意セクションを追加する。**  
不一致を発見したら、モデル名・テーブル名・カラム名のマッピング表を記載する。

---

### Phase 3: 設計書の作成

**ファイル名:** `{ブランチ名}.spec.md`  
**作成場所:** 改修対象リポジトリのルート

**必須セクション:**

- 変更ファイル一覧（表形式）
- 各ファイルの具体的変更内容（コードスニペット付き）
  - DBスキーマ変更（diff形式 or 変更後コード）
  - マイグレーションSQL（自動生成参考 + 手動追記）
  - 新規関数実装コード
  - 型定義変更（before/after）
  - サービス層変更（コードイメージ）
  - フロントエンド変更（変更箇所と内容）
- API/Schema互換性（before/after、破壊的変更の有無）
- データ移行・ロールバック手順
- 監視/運用設計（メトリクス、ログ、アラート）
- Feature Flag / リリース戦略
- テスト方針
- 実装順序（依存関係を考慮）

---

### Phase 4: タスクリストの作成

**ファイル名:** `{ブランチ名}.task.md`  
**作成場所:** 改修対象リポジトリのルート

**形式:**

- Step単位でグループ化（例: Step 1 スキーマ、Step 2 DB、Step 3 ロジック）
- 各タスクはチェックボックス形式: `- [ ] **1-1** ...`
- 各タスクに変更ファイルパスと具体的な変更内容を記載
- 必要な箇所はコードスニペットをインライン記載
- 最後に動作確認タスクを入れる
- 各タスクに完了条件（DoD）を1行で明記

**Stepの標準構成（必要に応じて調整）:**

1. スキーマ型定義変更（`schema/` 配下）
2. DBスキーマ変更 + マイグレーション生成 + データ移行SQL追記
3. バックエンド ヘルパー・共通ロジック追加
4. バックエンド サービス修正
5. フロントエンド修正
6. テスト更新・追加
7. 動作確認
8. 仕様との差分レビュー（実装diffと3ドキュメントの整合確認）

---

## 出力サマリ

3ファイル作成完了後、ユーザーへ以下を報告する:

- 作成した3ファイルのパス
- 各ファイルの概要（1〜2行）
- 実装上の注意点（例: DBモデル名とテーブル名の不一致、互換性制約、移行時の注意）
