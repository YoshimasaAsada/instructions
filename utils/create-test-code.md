# Instruction

コード変更に対して、実運用で壊れにくいテストコードを作成する。

- **目的:** 仕様を守りつつ、正常系・境界値・異常系・エッジケースを過不足なくカバーする
- **入力:** 対象コード、関連仕様（Issue/PR/設計メモ）、既存テスト
- **出力:** 追加・修正したテストコード、テスト観点一覧、実行結果サマリー

---

## 1. 事前確認

以下を先に明確化すること。

1. テスト対象の責務（何を保証すべきか）
2. 公開 API / I/O / 副作用（DB、外部API、ファイル、時刻、乱数）
3. 既存テストのスタイル（命名規則、describe 構成、モック方針）
4. 使用するテストフレームワーク（既存設定を優先）

不明点がある場合は、実装を進める前に質問して確定すること。

---

## 2. テスト観点の抽出

対象コードの分岐と仕様から、最低でも次を列挙すること。

1. **正常系:** 想定入力で期待結果になる
2. **境界値:** 0、空、最小/最大、閾値ちょうど
3. **異常系:** 不正入力、権限不足、依存失敗、例外発生
4. **エッジケース:** 並行実行、重複実行、順序依存、タイムアウト
5. **回帰観点:** 今回の変更で壊れやすい既存仕様

---

## 3. 実装ルール

1. 既存テストの構成と書式に合わせる
2. 1テスト1責務（失敗時に原因がすぐわかる粒度）
3. Arrange-Act-Assert を明確に分ける
4. 依存は必要最小限のみモックし、過剰モックを避ける
5. テストデータは再利用可能な形で整理する
6. 時刻・乱数・UUID など非決定要素は固定化する
7. 成功ケースだけでなく失敗ケースの期待値（エラー型/メッセージ）も検証する

---

## 4. 品質チェック

作成後、次を満たすこと。

1. 新規テストが今回の変更意図と対応している
2. 重要分岐に未検証パスが残っていない
3. テスト名だけで仕様が読み取れる
4. テストが不安定（flaky）にならない

---

## 5. 出力フォーマット（そのまま使う）

```md
## テスト観点
- 正常系:
  - ...
- 境界値:
  - ...
- 異常系:
  - ...
- エッジケース:
  - ...

## 追加/修正したテスト
- `path/to/test_file`:
  - `it(...)` / `test(...)`
  - ...

## 実行結果
- コマンド: `...`
- 結果: Passed/Failed
- 補足: （失敗時の原因と対応）

## 未対応（あれば）
- ...
```
